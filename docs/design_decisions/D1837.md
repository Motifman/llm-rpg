## D1837. ゲームと Being のイベント基盤を一つにする

**何を**: [Issue #1837](https://github.com/Motifman/llm-rpg/issues/1837) の決めたこと 1〜6。
次の設計を複数の PR で実装する。PR 1 では共通の基底と依存の境界だけを用意し、配送と Being の接続は後続に分ける。

1. 最上位の `eventing/` に、イベントの基底・受け手の登録・同期と非同期の配送・失敗の知らせ先を置く。`ai_rpg_world` 内では自分以外を import しない。同じプロセスの中だけを扱い、外部ライブラリは使わない。`CommandScope` と取引の outbox はゲーム側に残す。既存の確定前の連鎖は維持するが、確定前の受け手は新設せず、まず集約の規則にできるかを検討する。
2. 共通の `DomainEvent` は `event_id` と `occurred_at` だけを持つ。ゲームの `BaseDomainEvent` がそれを継ぎ、`aggregate_id`・`aggregate_type`・`occurred_tick` を加える。ゲーム側の別名 `DomainEvent` も共通型を指す。ゲームの時刻と Being のターンを一つの項目には入れない。
3. ID を持つ集約は自身の状態を書き換え、共通の基底の `add_event` / `get_events` / `clear_events` でイベントをためる。値の変わらない形は値オブジェクト・イベント・snapshot の中身に使う。ゲームの `warn_if_pending_events` はゲーム側に残す。`EventProducingAggregatePort` は維持し、取り出しと消去を行う場所を集める。
4. 非同期の受け手は確定後に `ThreadPoolExecutor` で走らせる。同じ Being は到着順、異なる Being は並行に処理し、スレッド数は実験設定に置く。裏のスレッドは結果を待ち行列に置くだけにし、集約への反映はその Being のターン開始時に行う。必須の知らせ先へ、受け手の例外・未完了件数の上限超過・終了中の受付拒否を通知する。終了時は受付停止、期限付きの待機、完了結果の反映、snapshot 保存の順とし、期限超過で捨てた結果も trace に残す。
5. 休眠している文脈の登録は文脈ごとに新しい確定前後の登録へ置き換え、試験を移してから古い経路と `is_synchronous` を消す。受け手のクラスとイベントとの対応は残す。既存の確定前登録は意味を保って移し、本番へ戻すときに必要性を見直す。再送必須の受け手の失敗で後続の配送が飛ぶ問題も配送の移行で直す。
6. Being は保存を確定の区切りとし、リポジトリが保存時にイベントを取り出して消去し、組み立て時に渡された配り手へ渡す。`PipelineEventPublisher` 内の四つの受け手も共通基盤の確定後の受け手に移し、失敗は既存の `SIDE_HANDLER_FAILED` へつなぐ。直接発行する経路と `EventPublisher` の口の整理は #1340 に分ける。

**なぜ**: ゲームの `domain/common` に基盤を置いたままでは Being がゲームに依存する。Being 専用の配送を増やすと、失敗の記録や終了処理が二重になる。共通基盤にゲーム固有の項目を持たせず、集約への書き込みをターンを進める側に絞れば、依存の逆転と並行更新による消失を避けられる。集約を値の変わらない形のまま新しい値とイベントの組を返す案は、主体の同一性と状態変更を値として扱ってしまうため採らない。

**どうしないと壊れるか**: 共通基盤からゲームを import すると Being の独立性が崩れるので、依存の境界を試験で見張る。取り出しと消去を呼び出す側へ分散するとイベントが残って重複配送される。裏のスレッドから集約へ直接書くと、ターン処理との競合で変更が消える。失敗の知らせ先を省略可能にすると trace に残らない。休眠中の登録を移す前に古い経路を消すと、受け手の対応まで失われる。

### その後: PR 2 で同期の配送を移す

**何を**: 同期の登録と配送は `eventing.EventDispatcher` に置き、確定前に渡す文脈は型引数で受け取る。ゲームの `CommandEventDispatcher` は `CommandContext` の型を指定するだけにし、配送の実装を持たない。`CommandScope` と登録のゲーム向けの口は元の場所に残す。知らせ先 `failure_observer` は組み立て時に必須とし、省略と呼び出せない値を拒否する。

再送必須の受け手が失敗しても、同じイベントの後続の受け手と後続のイベントを最後まで試す。すべての受け手の失敗を知らせ、再送必須の失敗があれば最後に最初の元の例外を投げる。初回配送と `handoff_durable` は同じ処理を使い、再送では `BEST_EFFORT` を呼ばない。worker は従来どおりイベント一件ずつ配送し、一件の一時失敗で次のイベントへ進まず再試行を待つ。

**なぜ**: 一件の失敗で無関係な観測や後続の仕事を飛ばさないため。例外をまとめる案も比べ、呼び出す側の既存の例外の扱いを保つため、ユーザーとの確認で最初の例外を返す案を採った。二件目以降の失敗も trace で調べられる。知らせ先を省略できるままでは、失敗がログだけに残る組み立てを防げない。

**どうしないと壊れるか**: 最後に例外を返さないと `CommandScope` が outbox の全行を配送済みにしてしまう。失敗があれば確定済みの業務状態は戻さず、未配送のまま残す。outbox は受け手ごとの成功を保存しないので、再送時には成功済みの再送必須の受け手も呼ばれる。受け手は従来どおり、同じイベントを繰り返し受けても結果が重複しないようにする。

取引 outbox は世界と独立に起動し、対象の世界を特定する情報も持たないため、世界の trace へ混ぜない。ユーザーとの確認で、DB の隣に起動ごとの専用 JSONL ファイル (`<DB名>.outbox-*.jsonl`) を作ることを決めた。`WorldTickFailureIsolator.record_continued_failure` へつなぎ、世界の時刻は `None` とする。過去の記録を上書きしない名前を割り当て、書き込み時だけファイルを開く。停止猶予を超えて残った再送処理も記録でき、ファイルを閉じる時期と競合しない。

### その後: PR 3 で非同期の受け手を足す

**何を**: 3a で `AsyncEventExecutor` と確定後の `AsyncDelivery` の登録を作り、3b で実験設定・trace・終了と保存への接続を行う。本人の ID を取り出す関数を登録時に渡し、共通の `DomainEvent` は変えない。同じ ID の受け手を到着順に一つずつ、別の ID は並行に処理する。結果は保留し、本人のターンの入口か終了時に、呼び出した側のスレッドで反映する。

**なぜ**: 短期記憶のイベント (`ShortTermMemoryEvent`) は既に `being_id` を持つ。取り出し方を登録する側に置けば、基盤が Being の型を import せずに済む。ID を保存の呼び出しで別に渡す案と比べ、イベントと宛先の食い違いと入口の増加を避けられる。ユーザーと確認してこの案を採った。初期値はスレッド 2 本、実行待ち・実行中・反映待ちを合わせて 100 件、終了時の待機 10 秒とする。

**どうしないと壊れるか**: 非同期の受付は完了を意味しない。今の outbox に受付の成功を配送完了として返すと後の失敗を再送できないため、ユーザーと確認し、非同期と `DURABLE_RETRY` の組み合わせを登録時に拒否する。終了期限後も実行中のスレッドそのものは止められないが、その結果は反映せず、期限時点で破棄を知らせる。反映待ちも件数に含めないと、ターンが来ない本人の結果が無制限に蓄積する。

3b では、実行時の設定に `ASYNC_EVENT_WORKERS` (既定 2)、`ASYNC_EVENT_MAX_PENDING` (既定 100)、`ASYNC_EVENT_SHUTDOWN_TIMEOUT_SECONDS` (既定 10 秒) を足す。profile から解決して記録し、未知のキーや不正な値は開始前に拒否する。ゲームで登録するときの宛先は `BeingId.value` の文字列にそろえる。ターンの入口で、その本人の完了した結果だけを取り込む。

実験の終了では受付を止め、期限まで待ち、完了した結果を呼び出す側で反映してから snapshot を保存する。途中で例外が起きた場合も終了処理を呼ぶ。失敗・受付拒否・期限による破棄は `async_event_delivery_failed` に理由、宛先、イベントの ID と型、受け手、例外の型と本文を記録する。実際の Being の受け手は後続の変更でつなぐため、スタブの実験でこの記録が出ないことと、偽の受け手を使った試験で記録されることを分けて確かめる。

### その後: PR 4 で観測の配送の受け手を移す

`PipelineEventPublisher` は独自の受け手の一覧と呼び出し処理を持たず、`eventing.EventDispatcher` の確定後へ `OBSERVATION` / `BEST_EFFORT` で登録する。既存の `register_handler` はこの登録へ委ねる口として残す。確定後に届く経路も直接発行する経路も、イベント一件ごとに受け手を登録順に呼んでから、観測の作成・追記・起床を進める。非同期にはしない。

失敗の知らせ先には従来の `SIDE_HANDLER_FAILED` の記録をつなぎ、共通基盤へ渡す呼び出しの口に元の受け手を保持し、失敗の通知で参照して従来の型名を残す。項目、例外文の長さの制限、記録先が無い場合や記録自体の失敗でも後続を続ける振る舞いを保つ。受け手を外側のコマンド配送器だけへ登録すると直接発行の経路が抜け、複数イベントをまとめて受け手へ渡すと観測との順序が変わるため、publisher 内で共通の配送器へ委ねる。経路と `EventPublisher` の口の片付けは #1340 に残す。

### その後: Being の保存先を配り手につなぐ (#1824 の F2a-1)

**何を**: Being の 3 つの保存先 (短期記憶、メモ帳、エピソード) が、保存するときに、ためたイベントを取り出して空にし、組み立てるときに渡された配り手 (`handoff`) へ渡す (`being/infrastructure/event_handoff.py`)。`create_world_runtime` が Being の配り手 (`EventDispatcher`) を組み、3 つの保存先に渡す。受け手は、短期記憶が待たずに外したこと (`FoldForced`) といきさつを捨てたこと (`StaleBackstoryDiscarded`) を trace に残す 2 つ。ほかのイベントは受け手 0 件で配る。

**なぜ**: メモ帳 (#1849) とエピソード (#1851) はイベントをためていたが、保存先は保存するときに写しを作って入れ、イベントを写さなかった。呼び手の集約に残ったイベントは誰も取り出さないので、黙って捨てられていた。短期記憶のイベントも、受け手につなぐにはこの口が要る。

**配り手の無い保存先**: イベントのたまった集約を保存しようとしたら、保存する前に止める (`RuntimeError`)。黙って捨てると、受け手を足したときに届かない理由が分からなくなる。イベントの無い集約は、配り手が無くても保存できる (snapshot の CLI など、イベントを生まない使い方のため)。

**持ち越しから戻すとき**: `replace_all_by_being` も保存と同じく、イベントがあれば配り手に渡し、配り手が無ければ入れる前に止める。snapshot から作る集約はイベントを持たないので、ふだんは何も配らない。

**配る途中の失敗**: 保存してからイベントを取り出して配るので、再送必須 (`DURABLE_RETRY`) の受け手が失敗して例外が出ても、保存は済み、集約のイベントは空になっている。呼び手が保存をやり直しても再送されない。今は再送必須の受け手が無い。足すときは、再送を配り手の側で受け持つ形にする。

**メモ帳の結果**: メモの操作の結果 (`apply_memo_operations`) は集約の最後のイベントを読んで作るが、保存より前に読む (`memo_turn.py`)。保存のときにイベントを取り出しても結果は変わらない。

**どうしないと壊れるか**: `tests/being/infrastructure` の 3 つの保存先の `TestHandoff` と、`tests/integration/test_being_event_handoff_runtime.py` が見張る。

### その後: 休眠している文脈の登録 (グループ 1)

消耗品の効果・ショップ・SNS に `register_command_handlers` を足す。既存の `is_synchronous=True` は消耗品の 1 件だけで、同じ受け手を確定前へ登録する。ショップ 4 件と SNS 6 件は確定後とし、表示用の更新は `READ_MODEL`、通知と関係の反映は `INTEGRATION` に分ける。受け手のメソッドと登録順、古い登録の口は残し、本番への接続は増やさない。消耗品の受け手は現在の本番でも使われているため、受け手自体は変えない。

確定後の失敗は、ユーザーと確認して取引と同じ `DURABLE_RETRY` とした。旧経路と同じく保存は取り消さず例外を返し、共通基盤の決まりに従って残りの受け手とイベントも試してから最初の例外を返す。必須の知らせ先は `WorldTickFailureIsolator` を通して trace に残す。今回は outbox や自動再送を本番へつながない。通知の追加や出品数の更新などは繰り返すと重複する可能性があるため、再送を接続する前に受け手の重複防止を確認する。失敗を記録するだけで正常に戻る `BEST_EFFORT` は、旧経路の例外を返す扱いが変わるため採らなかった。

本番へ戻す際は、消耗品の 1 件について「失敗したら世界があってはいけない状態になるか」を見直し、そうでなければ確定後へ移す。集約に置ける規則は集約へ戻す。試験の旧組み立ては `CommandScope` と既存のリポジトリ用の橋渡しへ移し、`register_handlers` と古い配送の削除は全グループの後に行う。
