## D1469-4. BeingId と BeingAttachment を being/ に移し、所属の付け替えを Being に頼む

**何を**: #1469 の移し替えの続き。

- `BeingId` を `being/domain/being_id.py` に移した。中身は変えていない
- `BeingAttachment` を `being/domain/being_attachment.py` に移し、世界とプレイヤーの番号を、ゲームの型 (`WorldId`、`PlayerId`) ではなく正の int で持つようにした。0 以下、bool、int でない値は `BeingAttachmentValidationException` で断る
  - ゲームの型との変換はゲームの側で行う。`BeingProvisioningService` は `WorldId` と `PlayerId` から番号を取り出して作り、`BeingAttachmentResolver.resolve_player_id` は番号を `PlayerId` に戻して返す
  - snapshot の形 (`attachment_world_id`、`attachment_player_id`) は変わらない
- `Being.move_to(attachment)` を足した。入っていれば外してから入り、入っていなければそのまま入る
- `Being.detach()` は値を返さない。入っていない Being に呼ぶと、`BeingNotAttachedException` で断る (二重に入るときの `BeingAlreadyAttachedException` と同じ扱い)
- `BeingProvisioningService.ensure_attached` は、「入っているかを聞いて外してから入れる」分岐を消し、`move_to` を呼ぶだけにした
- import の境界の試験の一時的な例外は、例外のモジュール (`domain/being/exception/being_exceptions.py`) だけになった

**なぜ**:

- 所属を int で持つ (ユーザーと決めた案 A): Being はゲームのパッケージを import しない。番号のまま持てば、挙動も snapshot の形も変えずに移せる。「世界とプレイヤー」というゲームの言葉は Being に残る。所属を契約の言葉 (環境の名前とその環境での呼び名など) で表す案 B は #1928 で検討する
- `move_to`: application が「入っているか」を聞いてから外すかどうかを決めていた。所属の付け替えの決まりは Being に置き、application は頼むだけにする (CLAUDE.md の「tell, don't ask」)
- `detach` の返り値をやめた: 状態を変える操作は値を返さない (CLAUDE.md の集約の決まり)。返り値を使っているところは無かった

**書き換えなかったもの**: `docs/experiments/issue_1509_miss_material_timeline/probe.py` は旧い `BeingId` のパスを import したまま残した。この PR の前から、消したモジュール (`in_memory_semantic_memory_store` など) を import していて動かない、当時の記録だから。

**まだしないこと**: 外したことを知らせるドメインイベントは足さない。反応する処理がまだ無いため。反応する処理ができたときに `BeingDetachedEvent` を足す。

**関連**: Issue #1469、#1928、design_decisions D1469-1。

**その後 (design_decisions D1928-2)**: `BeingAttachment` は、世界とプレイヤーの番号ではなく、環境の識別子と表示の名前で持つようになった。誰がどのプレイヤーを動かしているかは、ゲームの側の対応表 (`PlayerBeings`、D1928) が持つ。
