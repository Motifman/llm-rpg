# 取引の識別・金額・検索条件の試験所有権

## なぜ

公開値オブジェクトの試験を読むと、既存の生成メソッド試験が同じ入力・同じ構築・同じ確認を持つ直接構築試験が3件あった。また要求金額の1件は「値が異なればhashも異なる」と要求していた。ハッシュの衝突は許され、値の等価性で区別されるため、この要求は公開契約より強い。

単純な構築・ID・既定値の確認をまとめて削除するのではなく、全67宣言を読み、実際に守る契約と保持先を区別した。独立した第二読により、初期の66保持/1削除候補から、63保持/3統合/1削除へ訂正した。

## 範囲

基準は `ba942f5a9cad4b6d362c9e2ce59566cc8ce3396f`。対象は次の4所有者と対応する4試験である。

- `TradeId`: 15宣言、すべて保持
- `TradeRequestedGold`: 17宣言のうち16保持、1削除
- `TradeScope`: 17宣言のうち16保持、1統合
- `TradeSearchFilter`: 18宣言のうち16保持、2統合

試験は67→63宣言/実行ケース、481→458行（追加0・削除23）。製品4所有者249行、専用支援0行は変更していない。廃止ファイル・追加の恒久試験・試験専用の製品口は無い。

`TradeAggregate`のイベント生成、同席取引の`PendingTradeOffer`、市場板の`MarketBoard`/`MarketOrder`は別所有者であり、編集も今回の完了件数への追加もしない。今回の判断はこの文書に残す。

## 3件の統合

1. `test_trade_scope.py::test_create_global_trade`
   - 旧入力は`TradeScope(TradeType.GLOBAL, None)`。種別GLOBALと宛先Noneを確認する
   - 保持する`test_global_trade_factory_method`は`global_trade()`から同じ`cls(trade_type=GLOBAL, target_player_id=None)`を構築し、同じ2値に加えて返却型も確認する
   - 位置引数の受理・順序は、残すDIRECT/PlayerId123の直接構築と、直接構築の拒否2件にも残る
2. `test_trade_search_filter.py::test_create_filter_with_item_name`
   - 旧入力は`item_name="sword"`、確認は名前が`sword`であること
   - 保持する`test_by_item_name_factory_method`は同じ入力を同じ構築へ渡し、同じ値を確認する
3. `test_trade_search_filter.py::test_create_filter_with_price_range`
   - 旧入力は`min_price=100, max_price=500`、確認は両方の値
   - 保持する`test_by_price_range_factory_method`は同じ上下限を同じ構築へ渡し、両方を確認する

既存保持先が旧入力と全確認を含むため、追加ケースや確認の移管は不要である。生成メソッドだけの引数欠落・交換は保持先で検出し、直接構築側では検出できない。公開生成メソッドを消す判断はしていない。

## 1件の過剰制約の除去

`test_trade_requested_gold.py::test_hash_different_for_different_values`は100G/200Gのhashが異なることだけを確認していた。異なる値どうしが衝突しない契約や、その2値のhash値を固定する保存形式は無いので、この確認は移さない。

Gold自身の保持先は次のとおりである。

- `test_equality_with_same_value`: 別実体の200/200は等しい
- `test_equality_with_different_values`: 旧削除対象と同じ100/200は異なる
- `test_equality_with_non_trade_requested_gold`: 無関係な型とは異なる
- `test_hash_consistency`: 別実体の150/150は同じhashを持つ

Goldに既存の恒久的な集合試験は無い。別型であるTradeIdの集合確認をGoldの保持先として数えない。今回削除する試験も集合や辞書を確認していなかった。

## 63件を残す理由

- IDの整数生成、文字列変換、不正文字列を専用例外へ変える処理、1/0/負数/大きな値、型を区別する比較、不変性は独立した契約である。保存辞書・コマンド・JSON復元だけでは全経路を代替しない
- 金額の直接構築と`of`にはそれぞれ不正入力の拒否があり、1Gを許す境界と0/負数の拒否を残す。表示・同値性・同値hash・代入拒否も維持する
- ScopeのGLOBAL/DIRECTと対象有無の組合せは値の所有者が守る。集約の受諾権限やJSONの型付き復元とは別の責務である
- 空の検索条件は7属性すべてのNoneを確認する。`from_primitives()`の空入力は2属性だけなので、前者の代わりにはならない。後者も変換入口自身の既定引数を守る
- `from_primitives`は2つの実検索サービスから呼ばれ、4種類の列挙値変換、名前・上下限の引渡し、専用例外を保護する。`by_*`とは別の引渡し箇所である
- 表示・比較・代入拒否がdataclassを使っていても、製品が比較対象や不変性を選ぶ契約である。標準ライブラリの試験という理由で削除しない

上位の検索試験には、空結果でも成功する全称確認が一部にある。その弱い確認をこの4値オブジェクトの強い代替として扱わない。今回の3統合は同一ファイル内の直接値比較にのみ吸収する。

## 実証

- 未編集の対象67件と、対象を含まない関連327件が成功
- GLOBALの構築後宛先を999へ変える、名前をswordからaxeへ変える、下限100を99へ変える、上限500を501へ変える4つの一時変異を実施
- 4変異それぞれで旧直接構築・旧保持先・削除後保持先を個別実行し、同じ対象値の断言で失敗した（計12実行）。検証例外や別のガードの失敗ではない
- Goldのhashだけを定数0へ変える対照では、旧67件中の削除対象1件だけが失敗し、削除後63件はすべて成功
- 同じ定数hash下の一時診断では、集合が100/100を1件、100/200を2件として保持し、辞書が再構築した100/200で別々の値を検索できることを削除前後に確認。恒久試験には追加しない
- 全変異後に製品4所有者をバイト単位で復元。対象キャッシュを毎回除去し、書込み禁止で実行した
- 復元後の対象63件が2回成功、関連327件が成功。対象4ファイルのruffと`git diff --check`が成功

関連群は取引集約、出品/受諾/取消/辞退コマンド、通常/公開市場検索、イベントハンドラ、メモリ内/SQLite保存、JSONイベント保存、観測整形/配信である。基準のSQLiteコマンド試験には別監査対象の重複収集が含まれるが、今回の削減成果に数えない。

手元はPython 3.10.22 / pytest 8.4.1、資格情報を除いた通信遮断環境。外部API・LLMを使っていない。全リポジトリ試験と公開後の正確な差分コミットのCIは、この手元確認とは別である。速度改善は主張しない。

## 今後の同じ失敗を防ぐ

- 直接構築と公開生成口を統合する前に、同じ入力・実際の構築経路・全断言の保持先を示す。名前の類似や呼出元不在だけで削除しない
- hashの契約は同値間の整合性であり、不等値間の衝突禁止を足さない
- 別の型の集合試験や、入力イベントを自分で作る保存試験を、値の所有者や集約生成の証拠と混同しない
