# エージェントが、世界に無い行為を試みた記録

実 run で、**エージェントが機構の外側へ手を伸ばした**場面を残す。どれも「バグ」では
なく、**我々が世界を設計したときに想定していなかったこと**である。

直すかどうかは別の判断なので、ここには**起きたこと・なぜ起きたか・直す場合の
選択肢**だけを書く。**直した時点でこの記録は消さない** — 直さない判断をした理由も、
後から読む人に要るため。

---

## 1. 提案の相互デッドロック (v3.2 run, t16–t20)

### 起きたこと

双方が同時に逆向きの提案を出し、**互いの品を凍結し合って両方とも承諾できなくなった**。

```
t16 カイ → トム: 16G ⇄ パン   (カイの 16G が凍結)
t16 トム → カイ: パン ⇄ 16G   (トムのパンが凍結)
t17 両者が承諾を試みる → 両方 TRADE_ASK_NOT_MET
t19 カイが降りる (trade_decline) → トムのパンが戻る
t20 トムが承諾 → 成立
```

### なぜ起きたか

**差し出すものを返事まで凍結する**設計 (経済統合 Phase 2) の副作用。凍結は
「受けたときに確実に渡すため」に入れたもので、**同じ品が別の提案の対価にもなって
いる**状況を想定していなかった。

### エージェントが自力で解いた

カイの独白:

> 俺のオファーとトムのオファーが行き違って両方凍ってる。トムのオファーを断って
> やれば…

**3 手番のロスで解けている。** engine で防ぐと、**この解決そのものが観測できなく
なる**。

### 直す場合の選択肢

- **そのまま**: 自力で解ける。解く過程が観測として面白い
- **逆向きの提案を断る**: 相手からの提案が生きているときは、こちらから逆向きの
  提案を出せなくする。デッドロックは消えるが、**解く場面も消える**

いまは**そのまま**。「エージェントが自力で解けない」実例が出たら、そのとき考える。

## 2. 教わることができない (v3.2 run, t27–t29)

### 起きたこと

トムがレナに**窯の使い方を教える取引**を持ちかけ、レナはそれを受けて待った。

t27 トム:
> 窯の扱いを教える代わりにパン1つ——悪い話じゃないはずだ

t29 レナ:
> トムが「入れてみろ」と言ったけど、窯にはまだ操作が出てこない——教わるって
> 言っても、実際に触らせてもらえるまで待つしかないのか

**レナは永久に焼けない。** 職能は `PLAYER_STATE_IS` で固定されていて、世界に
「教える」という行為が無い。

### なぜ起きたか

職能を**道具ではなく本人の性質**として持たせた判断 (道具ゲートを却下した経緯は
`docs/design_decisions.md` を参照)。道具は取引に出せてしまい、手放されると世界から
職能が消えるため、この判断自体は正しかった。

**想定していなかったのは、エージェントが「教える / 学ぶ」を言語で提案すること。**
世界に無い行為を彼らは自然に思いつき、成立を待ち続ける。

### これは静かな失敗の形をしている

**拒否されるのではなく、待っても何も起きない。** 「できません」という応答すら
返らないので、レナは自分の理解が足りないのだと考え続ける。

### 直す場合の選択肢

1. **そのまま**: 職能は変えられない。ただし「教える」提案が空振りし続ける
2. **教えられるようにする**: `initial_state` を書き換える手段を作る。**世界観が
   変わる** (職能が交換可能になる)
3. **教えられないことを世界が示す**: 窯の行に「焼けるのは焼き手だけ」と出す

3 が有力。**行為を増やさずに、空振りだけを止められる。**

ただし **#1197 で「注記は理由を断定しない」と決めた**判断とぶつかる。当時の理由は
「落ちた理由は職能とは限らず、世界の状態のこともあるので、断定すると別の嘘になる」
だった。

**逃げ道はある。** シナリオはこの条件に `failure_message` を書いている。

> 窯の火加減も捏ね方も分からない。パンを焼けるのはあの人だけだ。

これは**engine の推測ではなく作者の言葉**なので、そのまま出せば嘘にならない。
「理由を断定しない」は engine が理由を**推測しない**という規律であって、**作者が
書いた理由を伝えない**という意味ではない。

## 3. 受け取ることができない (v3.7 run market_town_v37_division, t53–t65)

### 起きたこと

ミナが run で唯一の麦束をトムへ手渡した (t53、`give_item` 成功)。トムは直後に
**ミナに対して `take_item` を試みて失敗**し (t54、そんな操作は無い)、代わりに
選んだ `give_item` で**受け取ったばかりの麦束をミナへ送り返した** (t55)。

t57 のトムのメモ:

> ミナが麦束をくれた（観測では渡された）。しかし俺の持ち物に麦束は無い…？

自分が返したことに気づかないまま、t64 に床を探し (`pickup_item` 失敗)、t65 に
「ミナ、もう一度渡してもらえるか」と頼んだ。麦束は run 終了まで窯に届かず、
**この 1 束が届いていればパンが 2 つ焼けた** (80 tick でパン 0 の一因)。

### なぜ起きたか

**受け取りは自動なのに、トムは「受け取る」という操作が要ると思った。**
`give_item` の成功は渡した側の行動としてしか世界に現れず、受け取った側には
観測が届くだけで、**自分の所持品が増えたことと結びつかなかった**。そこで
「受け取る行為」を探し、`take_item` (無い) → `give_item` (逆向き) と滑った。

give_item を対称な向きに使える (誰でも誰にでも渡せる) こと自体は正しい設計で、
**渡す行為だけがあり受け取る行為が無い**という非対称を想定していなかった。

### 直す場合の選択肢

- **そのまま**: 珍しい混乱で、観測としては面白い。ただし今回は run の経済全体を
  止める一因になった
- **受領を本人の観測に明示する**: 「ミナから麦束を受け取った (所持品に入っている)」
  のように、**自分の所持品が増えた事実**を受け取り側の観測文に書く。行為は
  足さず、観測の解像度だけ上げる (静かな失敗の構造的対処と同型)
- **`take_item` を足す**: 世界に「受け取る」行為を作る。同意の設計が要る
  (勝手に取れてはいけない) ので重い

観測文の強化 (2 番目) が筋が良さそうだが、まだ直していない。1 例しか無いので、
次の run でも同じ滑り方が出るかを見てから決める。

## この 3 つに共通すること

**どれも、エージェントが機構の外側を試みた記録である。**

失敗として trace に残らない。1 つ目は成功として解決し、2 つ目は**何も起きない**。
3 つ目は逆向きの成功として残り、**成功の統計をむしろ汚す**。
**行動の統計を見ても出てこない。独白を読んで初めて分かる。**

0 だった軸について「その行動を検討した独白を探す」を分析の手順に入れたのは
このためで、**同じ理由で、この文書は独白から作られている**。
