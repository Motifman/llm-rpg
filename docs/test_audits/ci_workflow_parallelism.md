# CI 構成試験の監査: 品質検査の並列指定を見逃さない

## 結論

`tests/architecture/test_ci_workflow.py` の全5宣言を監査し、削除せず保持した。
今回採用したのは、品質検査の並列指定を別名で書くと見逃す問題の修復だけである。
対象テストの変更は10行追加・1行削除。本番コード、workflow、依存、goldenは変更していない。

監査基準は `0b51eb28d4692635a932dcf4063ab9b231768bf0`。
検証は2026年10月13日に、その内容を固定した作業領域で行った。
ここでの時刻・所要時間・成否は局所検証の記録であり、GitHub Actionsの全実行を再現した結果ではない。

## なぜ静的な試験を残すか

この5宣言はworkflowを構成として読む。実際の検査とは責任が異なる。

- `secret-leak` jobはcheckoutされたリポジトリを走査する。走査本体のシェル試験は一時リポジトリの合成入力で検出器を試す。どちらも「CIから直接呼ばれる配線が残っているか」の代わりにはならない
- `test` jobは対応下限のPythonと固定依存で通常試験を実行する。別の環境で試験が成功しても、下限・lock・並列化の方針は証明できない
- `quality-goldens` jobは品質用の生成処理を実行し、追跡差分と追跡外ファイルを確認する。生成処理自身が成功することと、保存済みgoldenの鮮度は別の契約である

設計判断111と [PR #1164](https://github.com/Motifman/llm-rpg/pull/1164) は、
漏洩走査を通常試験から独立させ、Python下限と固定依存を守る理由を記録している。
[PR #1166](https://github.com/Motifman/llm-rpg/pull/1166) は通常試験の並列化と品質検査の直列化を導入し、
設定を壊したときに構成試験が失敗することも確認している。
[PR #1157](https://github.com/Motifman/llm-rpg/pull/1157) は生成後の差分検査が必要になった経緯を記録している。
実行が遅い、静的である、コマンドを読むという理由だけでこれらの独立契約を削除しない。

## 全宣言の台帳

Rは保持、Fは契約を保持して検査方法を修復する候補を表す。
発見時の判定はR1/F4。今回はFのうち1件だけを修復し、残り3件は保留した。
統合・削除の候補はない。

| 宣言 | 判定と今回の扱い | 独立契約・捕まえる退行 |
|---|---|---|
| `test_secret_leak_job_runs_for_main_pushes_and_every_pull_request` | R、変更なし | main push、pull_request、secret-leakの定義を保持する。イベントやjobの削除を捕まえる |
| `test_secret_leak_job_directly_runs_the_repository_scanner` | F、保留 | pytestを経由せず実リポジトリの走査を直接起動する。誤ったスクリプトやstaged限定への変更を捕まえる |
| `test_test_and_quality_jobs_use_python_lower_bound_and_frozen_uv_lock` | F、保留 | Python 3.10、uv 0.11.28、uv.lock、locked sync、export、frozen runを保持する。一方のjobだけ環境が変わる退行を捕まえる |
| `test_the_test_job_spreads_pytest_across_the_runner_cores` | F、保留 | 通常試験の並列数をrunnerへ委ねる。autoの削除や固定数への変更を捕まえる |
| `test_the_quality_job_regenerates_goldens_without_parallel_workers` | F、今回修復 | 品質検査にworker指定を持ち込まない。通常の `-n auto` に加え、同じ指定の別名を捕まえる |

先頭宣言の名称には「every pull request」とあるが、assertはキーの存在しか見ていない。
PRのbranches/pathsフィルタやjobの条件による除外までは保証しない。
この不足は後続課題とし、今回の修復へ範囲を広げなかった。

## 採用した修復

以前の品質検査は、空白で区切った文字列の中に `-n` がないことだけを確かめていた。
そのため `--numprocesses=auto` や `-nauto` では並列化されても通ってしまった。

固定依存のpytest-xdist 3.6.1の実装を確認し、`-n` と `--numprocesses` が同じ指定であることを確かめた。
既存のコマンド選別はそのままに、選ばれた品質検査コマンドを `shlex.split` で引数に分け、次を拒否する。

- `-n` とその付着形
- `--numprocesses` とその等号形

値を解釈して許容範囲を広げない。`-n 0` や `-n0` も「worker指定を置かない」という旧方針に従って拒否する。
引用符付きの指定も見逃さない。補助パーサや補助試験群は新設していない。

scanner、sync、通常試験の完全一致と、`actions/setup-python@v5` の検査は変更していない。
品質検査のraw文字列による `startswith` 選別もそのままである。

## 広い書式正規化案を棄却した理由

当初は全コマンドを引数列へ正規化し、worker指定の別名や後勝ちを読む案を検討した。
独立レビューで、旧検査が拒否していた次の4例を新たに許してしまうことが分かったため、この案は棄却した。

| 破壊例 | 失われる保証 |
|---|---|
| 通常試験に `uv run --frozen pytest -n auto || true` | 失敗しても成功扱いにできる |
| scannerの `bash` とスクリプトパスを別のshell行へ分ける | 二つのコマンドを、元の直接実行と取り違える |
| syncの `uv` と `sync --locked --extra export` を別のshell行へ分ける | 二つのコマンドを、元の依存同期と取り違える |
| 品質検査に `uv run --frozen pytest -m quality -n auto; echo -n0` | 後の別コマンドの文字列で、先行pytestの並列指定を打ち消してしまう |

通常試験に `--collect-only` を追加して実行を省く変更も、旧完全一致の保持対象である。
shell全体の意味を解析する仕組みを増やして補修せず、今回の変更を負の引数検査だけへ狭めた。
広い案で得た同義書式の成功結果は、最終案の達成項目や検証結果に含めない。

## 最終案の検証

ネットワークを遮断し、機密環境変数を除去した局所runnerで、対象5宣言を直列実行した。
変異は実workflowへ一時的に加えている。構成を読む試験だけを動かし、
main CI、workflow記載のshellコマンド、golden再生成、依存導入、実APIは実行していない。

最終案の対照・変異は計33実行で、すべて期待した終了コードになった。

| 検証 | 実行数 | 結果 |
|---|---:|---|
| 並列別名5種を旧・新で比較 | 10 | 旧成功、新失敗。失敗はすべて品質直列化の宣言 |
| 独立レビュー4例、collect-only、`-n 0`を旧・新で比較 | 12 | 旧・新とも失敗し、既存の拒否を保持 |
| 既存契約11変異 | 11 | 最終案ですべて失敗 |

別名5種は `--numprocesses=auto`、`--numprocesses auto`、`-nauto`、
引用符付きの `'--numprocesses=auto'`、`'-nauto'`。
各比較で失敗した宣言を確認し、無関係なガードの失敗を修復の証拠にしていない。

既存契約の変異は、secret-leak削除、scannerへのstaged追加、Python下限変更、uv版変更、
lockキャッシュ先変更、locked除去、export除去、frozen除去、通常試験の並列除去、
並列数の固定、品質検査への通常の `-n auto` 追加である。

全変異の後、workflowを元のbytesへ復元して一致を確認した。
復元したworkflowのSHA256は `47bbe52a3dcc6da08d800d161c3080140e78e62a98464f306228974e0391a841`。
最終5宣言をさらに2回実行し、両方5 passedだった。

| 状態 | 全体経過の2反復 | pytest表示の2反復 |
|---|---|---|
| 未編集基準 | 0.3477秒 / 0.3194秒 | 0.08秒 / 0.07秒 |
| 最終案 | 0.3418秒 / 0.3336秒 | 0.06秒 / 0.06秒 |

ruff 0.16.8の対象検査と `git diff --check` も成功した。
時間差は小さく、高速化効果は主張しない。今回の成果は、既存契約を失わずに並列指定の見逃しを直したことである。

## 残る課題と限界

1. scannerの同義書式を安全に許容する修復（宣言2）
2. 固定依存コマンドの同義書式、setup-pythonの同一実装へのSHA固定を許容する修復（宣言3）
3. 通常試験の同義書式を許容しつつ、失敗無視や実行省略を許さない修復（宣言4）
4. PRフィルタとjob条件を含めた起動保証の不足（宣言1）

今回の負の引数検査は任意shellの実行意味を保証しない。
また、pytest.iniや環境変数経由の指定、品質markerの選択、生成後の差分確認段階までは対象宣言が検査していない。
現在の単純なworkflow形式から変える場合は、その時点で責任境界を再評価する。
「静的だから削除する」「すべてのshell書式を許容する」のどちらにも広げない。
