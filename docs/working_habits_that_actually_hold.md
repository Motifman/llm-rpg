# 対策が実際に機能する形

作業中に踏んだ失敗と、その対策の記録。**対策そのものが壊れた回**を中心に書く。

対策は作った時点では効かない。**次に同じ場面が来たときに実行されて初めて効く。**
ここに書くのは「何を対策としたか」ではなく「**その対策がどう壊れたか**」である。

---

## 判断を挟むと、対策は壊れる

1 日のうちに、同じ形で 3 回壊れた。

| 対策 | 壊れ方 |
|---|---|
| 変異試験の前にコミットする | 「今回は小さいから」で飛ばす |
| CI が緑であることを確認してからマージする | 「2 本まとめてだから」で判定を落とす |
| メッセージはファイル経由で送る (引用符がシェルに食われるため) | 「短いから」で直接書く |

**どれも対策を忘れたのではない。対策を持っていて、例外を作った。**

共通しているのは、対策に**「いつやるか」の判断が挟まっている**こと。判断が挟まると、
**負荷が低いときほど省略される**。そして負荷が低いときは注意も低いので、**省略した
ことにも気づかない**。

**常にやる、が唯一機能する形。** 例外の条件を 1 つでも認めた瞬間、その対策は
「気をつける」と同じ強さに戻る。

### 構造にできるものは、構造にする

いちばん強いのは、**判断する場所そのものを無くす**こと。

- ツールの側で「gold を記録する」と決める → 書き忘れる余地が残る
- **呼び出しを包んで前後を測る** → 足す人が何も知らなくてよい (`docs/design_decisions.md`
  「同じ量が動くなら、どのツールから動いても同じ形で記録する」)

**規則を人に守らせるのではなく、構造で守る。** 守るべき人がいなくなったとき、規則は
初めて壊れなくなる。

## 変異が見せるものは 5 通りある

**検査の結果を見ただけでは、どれなのか決まらない。**

| 見たもの | ありうる意味 | 対処 |
|---|---|---|
| 緑 | 検査が弱い | 検査を足す |
| 緑 | 変異が当たっていない | 変異を打ち直す |
| 緑 | **変異が等価** | **何が等価にしているかを特定してから決める** |
| 赤 | 検査が効いた | 進む |
| 赤 | 別の理由で壊れた | 原因を確かめる |

**3 つ目だけ対処が正反対**である。検査を足しても意味がない。ただし
**「削る」と即断してはいけない** — 等価の理由が 2 通りあり、対処が逆になる。

長いあいだ「緑 = 検査が弱い」だけを警戒していた。1 日で赤の側を 4 回、等価な
変異を 1 回踏んで、**変異は弱さの指標であると同時に、死んだコードの検出器でも
ある**と分かった。

### 生き残りを見たら、まず等価かどうかを疑う

`values` の検証にこう書いていた。

```python
if spec is None or not spec.values or spec.allows(value):
    continue
```

「`not spec.values` を消す」変異が生き残った。**検査が弱いのではなく、
`allows()` が既に「列挙が無ければ何でも取りうる」を見ていた** — 消しても挙動が
変わらない、つまり**その条件は何も守っていなかった**。

手順は「検査を足す」ではなく、**まず変異したコードと元のコードで挙動が違うかを
確かめる**。違わないなら、生き残りが正しい。

### 等価の理由が 2 通りあり、対処が逆になる

**「等価なら削る」は間違いだった。** 別の PR で、こう書いた行の変異が生き残った。

```python
expires_in_ticks=(
    self._expires_in_ticks if expires_in_ticks is None else int(expires_in_ticks)
)
```

`is None` を `or` に変えても挙動が変わらない。違うのは `expires_in_ticks == 0`
のときだけで、**0 は入口のガードが落としている**からである。

**ここで削ると、いま安全な方を捨てて危ない方を残すことになる。** `or` は
「0 を既定へ倒す」形なので、ガードが動いた瞬間に静かに壊れる側になる。

| 等価にしているもの | 対処 |
|---|---|
| **その行の中で冗長** (同じことを二度見ている) | **削る** |
| **別の場所のガードが入力を絞っている** | **残す**。ガードが動いたときに、どちらが静かに壊れる側かで決める |

`not spec.values` は前者だった。`is None` は後者。**生き残りを見たら「等価か」
だけでなく「何が等価にしているか」まで見る。**

| 赤を見た場面 | 実際の理由 |
|---|---|
| 変異が落ちた | 変異したシナリオが**そもそも読み込めなかった** (実在しないツール名を混ぜた) |
| 変異が落ちた | `PlayerAttributeSpecs` が**未 import で `NameError`** になっていた |
| 変異が「落ちた」ように見えた | shell の heredoc で `$1` が展開されず、**対象ファイルを 1 つも読めていなかった** |
| 変異が生き残った (緑) | 置換が当たっておらず、**元のコードのまま走っていた** |

### 書き直す試験の、古い方の docstring を先に読む

**消そうとしているファイルの中に、その領域で過去に踏んだ穴が書かれていること
がある。**

板の配信を当事者だけに絞ったとき、「周りの人に見える」を見ていた試験ファイル
を書き直した。自分は**プロンプトの節を切り出して部分文字列で見る**版を先に
書いていた。ところが消す側のファイルの docstring にこう書いてあった。

> プロンプト全文の部分文字列検査は書かない — 同席者の名前も品名も別の節に
> 出るので、観測が 1 件も届かなくても緑になる (PR #1165 で実際に空振り
> していた)

**同じ形を一度踏んで、対策がそこに書かれていた。** 読んで、自分の版を捨てて
古い方の仕掛け (届いた観測そのものを見る) を引き継いだ。

書き直すとき、古いファイルは「置き換える対象」に見える。**中身は読まずに
消せるものだと思いやすい。** 読むのは 1 分で、そこにしか無い記録が入っている
ことがある。

### 変異は 1 行の書き換えでなくてよい

**再現したいのは「人がやりそうな変更」**であって、1 行の置換ではない。

行を消す形の変更は、1 箇所を戻しただけでは再現できない。板をプロンプトから
外した変更は、DTO の欄・組み立て・表示の 3 か所に散っていた。表示だけ戻しても
**データが無いので何も出ず**、変異が当たっていないのと区別がつかない。

3 つを同時に戻して「誰かが板をプロンプトへ戻した」を丸ごと作ると、狙った試験が
1 件落ちた。**その PR の主眼を守っている試験ほど、素直な 1 行変異では確かめ
られない**ことがある — 主眼が「構造ごと消した」ことにあるなら、変異も構造ごと
戻すことになる。

### 赤の側

**対処は緑の側と同じ形になる。**

- 変異を打ったら、**置換件数を検算する** (`count != 1` なら止める)
- 変異したものが**成立するか**を確かめる — シナリオなら読み込めるか、コードなら
  import が通るか
- 落ちたテストの**名前を読む**。狙ったテストが落ちているか、巻き添えか

いちばん危ないのは「落ちたから検査が強い」と読むことで、**落ちた理由を確かめずに
先へ進むと、空振りの検査を「変異で確かめた」と報告することになる**。

## 検査は、狙ったものを見ているとは限らない

ここから下は**緑の側**の話である (上の表の左上)。1 日で 10 件、**書いた検査が
狙った対象を見ていなかった**。すべて変異試験で見つかった。変異を回さなければ
10 件とも通していた。

内訳は 3 種類ある。

| 型 | 例 |
|---|---|
| **別のものを見ていた** | 提供者側の警告を見ていて、最後の砦の警告には届いていなかった |
| **粒度が違った** | 識別子 (`drop_item`) を探していたが、文章は動詞 (`drop`) で書かれていた |
| **基準が緩すぎた** | 「縮める前より短い」を上限にしていたので、ほとんど縮めなくても通った |

3 つ目が特に危ない。**「前より良くなった」を基準にすると、ほとんど良くなっていなくても
通る。** 到達したい値を先に決めて、そこへ置く。

### 一覧で守る検査は、一覧が空でも欠けていても緑になる

既知の語の一覧、既知のツールの一覧、対象の一覧 — **表を作って守る検査は、表を空に
しても通る**。**空の禁止までセットで書く。**

**空だけでは足りない。** 表には 3 通りの壊れ方がある。

| 壊れ方 | 起きること |
|---|---|
| 空になる | 何も守らなくなる |
| **実在しない項目が混ざる** | その項目は何にも一致しないので、集合差が空にならず**何をしても緑**になる |
| **項目が 1 つ減る** | 減った対象だけが検査の外へ出る。**他の項目で件数は足りる** |

3 つ目は、実在の検査を足しても捕まらない。実在の検査は綴り違いを見るだけで、
**欠落は見ない**。

**いちばん確実なのは、表をやめて導くこと。** 「この引数を取る関数」「この定数から
組んだ集合」のように定義から導けば、新しい対象は自動で入り、綴り違いも欠落も
起きない。導けないときだけ表にして、**空の禁止 + 全項目が実在すること**を併せて
見る。

### 否定の試験は、機能そのものが消えても通る

**「X が出ない」を見ている試験は、X を出す仕組みが無くなっても緑になる。**

板をプロンプトの常駐から外したとき、板の文言を見ていた試験 16 件のうち
**落ちたのは 6 件だけ**だった。残り 10 件は「〜が出ない」「〜は数えない」を
見ていたので、**板ごと無くなったことで通ってしまった**。

| 見ていたもの | 板を外したあと |
|---|---|
| 「18G で買える と出る」 | 落ちる |
| 「自分の出品は 18G で買える に数えない」 | **通る** (どちらも出ないので) |
| 「両方打てない品目の行は出ない」 | **通る** (行そのものが無いので) |

落ちた 6 件だけ直せば、**10 件は空振りのまま残る**。しかも見た目は「板の文言を
16 件が守っている」ままなので、次に触る人は守られていると読む。

対策は 2 つある。

**否定の試験の隣には、それが出る条件の試験を置く。** 正の対照が隣に無い否定の
試験は、機能が移動・消滅したときに黙って空振りへ変わる。隣にあれば、正の側が
落ちるので移動に気づける。

**移動させる変更では、落ちた試験の数を「影響範囲」と読まない。** 落ちた数が
少ないことは、影響が小さい証拠にはならない。**落ちなかった側にこそ空振りが
溜まる。** 機能を移した・消した・出所を変えた変更では、その機能を見ていた試験を
**落ちたかどうかに関係なく全部数え直す**。

### 「〜が無い世界」は、明示して作る

試験のために「その宣言が無い状態」を作るとき、**土台に書かれていないことを当てに
しない**。土台が変われば、その試験は黙って別のものを見はじめる。

市場町のシナリオに属性の宣言を足したら、「宣言の無い世界」を作っているつもりの
試験が 2 件、**宣言済みの世界を見ていた**。どちらも上書きしないことを「無い」と
読み替えていた。

```python
# 危ない: 土台に書かれていないことに賭けている
raw = json.loads(SCENARIO.read_text())
if attributes is not None:
    raw["player_attributes"] = attributes

# 明示する: 「無い」を自分で作る
raw = json.loads(SCENARIO.read_text())
raw.pop("player_attributes", None)
if attributes is not None:
    raw["player_attributes"] = attributes
```

このときは 2 件とも落ちて気づけたが、**落ちない側に転ぶ形が普通にある**。否定条件
(「〜が無い」「〜を宣言していない」) を土台任せで作った試験は、土台の変更で
静かに空振りへ変わる。分母の話と同じで、**見ているつもりの母集団を、自分で作る。**

### 穴を塞ぐ作業が、新しい穴を作る

10 件のうち 3 件は、**その PR で新しく書いた検査**が空振りしていた。ラチェットを
広げる PR で広げた部分が空振りし、「1 度だけ書く」PR の中で重複を作っていた。

**直している最中がいちばん危ない。** 直したものは必ず変異で確かめる。

## 結果を見て止まり、一次情報に当たらない

1 日で 3 回。しかもうち 2 回は、**受け取った側にも伝播した**。

- 起動時エラーを読んで「落とせない」と報告 → 実は落とせて、場所が違うだけだった
- 「58 件緑」から「検査の範囲外」と結論 → 実は範囲内で、粒度が違うだけだった

**報告の連鎖では、一次情報から遠ざかる。** 受け取った側は、報告を根拠にさらに
一般化する。誤りはそこで増幅される。

**対策**: 「〜だと分かった」と書くときは、**何を見て言っているかを 1 行添える**。

- **(実行して確認)** — テストや probe を走らせた
- **(コードを読んで確認)** — 実装を読んだ
- **(結果だけ見た)** — エラーや出力から推測した ← **要注意の印**

根拠の距離が見えれば、受け取る側が確かめるかどうかを判断できる。

## 自分の報告する数字にも、分母が要る

### 機能を変えたら、シナリオの自由文まで読み直す

**説明を合わせる対象に、シナリオの自由文が入っていなかった。**

板をプロンプトの常駐から外したとき、ツール定義・DTO・表示は直した。**シナリオ
の掲示板オブジェクトの説明文は残っていた。**

> 何がいくらで買えて、何がいくらで売れるかは、**この場に立てば「市場の掲示板」
> として目に入る**

立っても目に入らない。しかもその文は `掲示板を読む` の結果で、**手番を払って
嘘を受け取る**形だった。

ツール名が本文に残る形は総当たりで守られている
(`test_disabled_tools_vanish_from_the_prompt`)。**挙動の宣伝は守られていない。**
「立てば目に入る」はツール名を 1 つも含まない。

**機械で守れると思ったが、確かめたら守れなかった。** 「節の名前が自由文にある
のに、その節がプロンプトに出ていないなら嘘」という検査を考えた。実物を出して
みると、**その節はまだ出ていた** — 消えたのは節の中身 (他人の値) で、見出しは
残っている。**狙った case を捕まえない検査**を書くところだった。

守り方は手順の側にある。**機能を変えたら、その機能を説明している文を全部読み
直す。** 対象はコードのコメント・docs・PR 本文だけでなく、**シナリオの自由文**
を含む。見つけた経路も手順だった — 別の文 (「この町に直接の受け渡しは無い」)
が嘘になるかを確かめていて、隣に既に嘘になっている文を見つけた。

### 打ち切られたものを、分布に混ぜない

**「まだ終わっていない」を「短い」として数えない。**

板の注文が何手番居座ったかを測るとき、run の終わりまで残っていた注文の寿命は
**分からない**。それを「出てから run の終わりまで」として分布へ入れると、
**run が短かったことが「滞留が短い」に化ける**。

数だけ別に残して、読む人が打ち切りだと分かる形にする。同じ形は、実験の途中で
止めたもの・まだ返事の無いもの・観測の window を跨いだものすべてに起きる。



「全 15,418 件 passed」と報告し続けていたが、**`quality` マーカーは通常の pytest から
除外されている**。prompt を変えた PR がその検査で落ち、main を赤くした。

**数字だけを見せると、範囲を確かめずに信じてしまう。** trace の分析で「分子だけ見て
起きなかったと読む」を何度も戒めておきながら、**自分の報告で同じことをしていた**。

**対策**: 何を回したかを書く。「全 15,418 件 passed (**quality を除く**)」。

## 位置が意味を持つ編集では、位置も意味で指す

自動編集で**挿入先を文字列で探し、別の場所に着弾**することが 4 回あった。

対策を 2 段階で更新している。

1. 「その文字列が何箇所あるか数える」→ **回数は合っていて、その 1 箇所が何であるかを
   見ていなかった** (メソッド定義を目印にして、クラス本体を割った)
2. 「**何の中か**を確かめる」→ AST で着弾先を確認する。**4 回目で初めて、テストを
   走らせる前に気づけた**

いまは、クラスや関数の**行番号を AST から取って**そこへ挿入している。文字列で位置を
探すのをやめた。
