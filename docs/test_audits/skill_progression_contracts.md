## 経験値・通知の主担当

`SkillDeckProgressAggregate.grant_exp` の公開状態と生成イベントを集約試験で確認する。`SkillCommandService` が経験値を与え、観測整形が獲得量・総量・昇格前後を使い、配信先解決が集約IDを使う。手作りイベントを渡す観測試験では生成側の正しさを代替できない。

追加した経験値9/10は昇格閾値の直前と一致を区別する。初期5から20を加える入力は、加算と代入、増分と累積量を区別する。期待レベルや遷移列は製品の経験値計算から生成しない。

昇格の段階列には時系列の意味があるため、old/newを順序付きで確認する。異種イベント間の順序、UUID、現在時刻、獲得通知のdeck_levelが昇格前か後かは新たに固定しない。

## 提案管理と生成の主担当

指定IDの受諾・未選択候補の保持・通知生成は集約、条件選別と空枠選択は生成サービスが主担当。`refresh_proposals` を呼んでいなかった旧集約試験を、接続の証明とは数えない。

集約の準備に使っていた生成入力はサービスの `moved-registration-input` 行へそのまま移した。L10/HUMAN/NEUTRAL/ADVENTURER、空容量.5、前提(1)、枠(1,None,None,None,None)、唯一ADD/99/weight1、table_id=1、max_proposals=1を残し、ADD/99/NORMAL/枠1を確かめる。集約は元の生成結果に相当する値を直接受け取る。

登録通知はCounterで全対象と重複数を検査し、未規定の順序は固定しない。操作前の不変な入力スナップショットから期待内容を作る。受諾は1件だけの通知と対象、戻り値の全内容、残る提案を確認する。

上位の `test_accept_proposal_updates_loadout` は受諾から装備更新へ至る呼出経路を守るため残す。同一参照を返す保存口を使っているので、再saveの欠落を独立検出する証明とは数えない。SQLiteの進行保存試験も所有者・IDの確認であり、経験値や通知内容の代わりにはならない。

条件表では元の入力に追加制約を混ぜない。追加行の範囲外条件は1つだけにし、期待IDを明示する。レベル9/10/20/21、種族の一致/不一致、ロールの一致/不一致、容量.19/.2/.8/.81は各比較の独立した誤りを区別する。理由は種別の意味を確認し、全文や句読点は固定しない。
