## D1984. 人の穴のある文を、宣言の文と人で埋めた文の 2 つの型に分ける

**何を**: `game_world/domain/people/` に、人の指し方 (`PersonHandle`、`PersonRef`、`Unidentified`) と、人の穴のある文の型を 2 つ置いた。

| 型 | 持つもの | 決まり |
|---|---|---|
| `TextWithPersonHoles` | 作者が宣言に書く文 | 穴の名前を `holes()` で答え、`fill(people)` で `TextWithPeople` になる |
| `TextWithPeople` | 文と、穴ごとの人 | 文の穴と `people` の鍵が過不足なく揃う。揃わなければ断る |

**なぜ分けたか**: 設計図の宣言 (`OutcomeDeclaration.announcement` の「{person}は昇降機で外へ出た。」など) は `TextWithPeople` を持っていたが、読み込むときには穴に誰が入るか決まっていない。`TextWithPeople` に人の欠けを許して観測の出口で確かめる案もあったが、検査が型で効かず、穴の空いたままの文が Being に渡る静かな失敗の入口になる。宣言は `TextWithPersonHoles`、刺激・知覚の結果・断られたときの文は `TextWithPeople` にし、誰が入るかが決まったところ (刺激を作るとき、条件を評価するとき) で `fill` する。

文書の直し:

- 作者が書く文の欄を `TextWithPersonHoles` にした。`SpotSectionDeclaration` の `enter_text` / `leave_text`、`OutcomeDeclaration.announcement`、`DiscoverableDeclaration.found_text`、`InteractionDeclaration.success_text`、`AnnouncementTo.text`、`SoundDeclaration` の `clear` / `muffled`、`DayPhaseDeclaration.announcement`、条件のつなぎの `failure_text`
- `SightTexts` は宣言と刺激の両方で使われていたので、宣言の側を `SightTextsDeclaration` に分けた (`SightAt.texts`、`PerceptionDeclaration` の `witness` / `target` / `on_failure`)。刺激の `SightTexts` は `TextWithPeople` のまま
- `FailureReason.text`、`NotNow.reason`、`ActionRefusal.text` は評価の結果なので `TextWithPeople` のまま。条件の種類ごとの決まった文も、評価のときに `TextWithPeople` として作る
- 「物や操作の名前は刺激を作るときに環境が埋める」をやめ、作者が文に直接書くことにした。宣言はどの物体・操作のものか分かっているので、物や操作の穴は要らない

**値の範囲**: `PersonHandle` は 0 以上の整数 (真偽値は断る)。`PersonRef` の `appearance` と、文字列の `visible_name` は、空や空白だけを断る。名前が見えないことは `NoVisibleName` で表すので、空の名前を受ける理由が無い。

**穴の書き方**: `{名前}` だけ。名前は識別子に限り、位置の穴、変換、書式指定、属性や添字、閉じていない括弧は作るときに断る。書式や属性を許すと、文が人の中身を読みに行けてしまう。`{{` `}}` は文字の括弧。

**関連**: Issue #1984、#1978、#1974 の 5. と 8.。
