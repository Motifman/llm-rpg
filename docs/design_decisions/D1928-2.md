## D1928-2. Being の居場所を、環境の識別子と表示の名前で持つ

**何を**: #1928 の 2 本目。

- `BeingAttachment` を、世界とプレイヤーの番号から、環境の識別子 (`environment_id`) と表示の名前 (`environment_name`) に替えた。Being にとって識別子は中身の分からない札で、同じ環境かを照合するのにだけ使う
- シナリオの run の環境は、ゲームの側 (`WorldRuntime._wire_being_stack`) が作る
  - 識別子: シナリオの `metadata.id` と世界の番号から作る (例: `mine_village_v1#1`)
  - 表示の名前: シナリオの `metadata.title` (例: 廃坑の山村)。環境に入るときの紹介 (`environment_entry_for_player`) とエピソードに書く名前と同じ
- `BeingProvisioningService` は、用意した Being をこの環境に入れる
- Being の snapshot は、居場所を `attachment_environment_id` / `attachment_environment_name` に書く。世界とプレイヤーの番号は書かない
- Being の保存先をプレイヤーの番号で探す `BeingRepository.find_all_attached_to` を消した。SQLite の `json_extract` による検索と、JSON1 拡張の起動時の確かめ、`unique_attached_being`、`BeingMultipleAttachmentException` も消した。誰がどのプレイヤーを動かしているかは、ゲームの側の対応表 (`PlayerBeings`、design_decisions D1928) が持つ

**古い snapshot の読み方**:

- 番号の欄 (`attachment_world_id` / `attachment_player_id`) の古い Being の snapshot は、番号を `legacy_attachment_*` に移して読む。番号は「プレイヤー → Being」の対応表を作り直すのと、世界の snapshot の対応表と食い違わないかを確かめるのにだけ使い、居場所にはしない。書き出さない
- 再開したときは、対応表でこの run のプレイヤーを動かす Being を、この run の環境に入れる (`Being.move_to`)。居場所の無い古い Being も、別のシナリオで保存した Being も、居場所がこの run の環境にそろう
- 対応表に載らない Being (今の run にいないプレイヤーを指す古い Being など) の居場所は触らない。誰も動かさないので、居場所の無い古い Being は居場所の無いまま、別の環境で保存した Being はその環境のままになる
- 番号の欄の古い Being は、別の世界の番号でも、世界の snapshot の対応表に載っていれば食い違いとして止める
- `scripts/being_snapshot_cli.py` (SQLite) で番号の欄の古い snapshot を読むと、Being はどの環境にも入らない。捨てた番号を warning に残す
- 対応表の欄が無い古い世界の snapshot で、Being の snapshot も今の形 (番号が無い) なら、起動時に用意した対応表のまま続ける (`player_beings_source="startup"`)。Being の ID はプレイヤーから決まるので、同じ組になる

**なぜ**:

- Being は環境を行き来する主体で、ゲーム以外の環境には世界の番号もプレイヤーの番号も無い。番号のままだと、その環境も無理に 2 つの番号で表すことになる (#1928)
- 同じシナリオの世界が 2 つ同時に立てば表示の名前は重なるので、見分けるのは環境が付けた識別子にした
- 識別子と表示の名前は、エピソードの `environment_name` と `EnvironmentEntry` がすでに使っている言葉で、新しい概念を足さずに済む

**まだしないこと**: `EnvironmentEntry.self_name` を消し、Being の名前を使うのは 3 本目 (D1928-3)。

**関連**: Issue #1928、#1436、design_decisions D1928、D1469-4。
