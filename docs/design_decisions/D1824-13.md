## D1824-13. エピソードの書き起こしを、下書きを書くことと保存することに分ける

**何を**: エピソードを書き起こす部品 (前の `being/application/episode_writing.py` の `EpisodeWriter`) を 3 つに分ける。

| 置き場所 | 持つもの |
|---|---|
| `being/domain/episode_writer.py` | 口 `EpisodeWriter`。範囲の出来事の文から、下書き (`EpisodeDraft`。目次と本文と切り詰めた項目。ID と呼び名はまだ無い) を返す |
| `being/infrastructure/llm_episode_writer.py` | `LlmEpisodeWriter`。指示の文面、LLM の呼び出しの口 (`EpisodeWritingCompletion`)、応答の読み取りと切り詰め |
| `being/application/episode_writing.py` | `EpisodeKeeper`。下書きに ID と、その Being の中で重ならない呼び名を付けて保存する |

今の畳むときと環境を離れるときの書き起こし (`PlayerEpisodeWriting`) は、この 2 つを続けて呼ぶ。文面、読み取りの決まり、trace (`episode_writing`) は変えない。

**なぜ**:

- 口をドメインに、文面と呼び出しと読み取りをインフラに置くのは、#1824 の設計 (ドメインの外に置くもの) のとおり。いきさつ (design_decisions D1824-12) と同じ形にそろえる
- 次の PR で、短期記憶が古いターンのいきさつを頼むとき (`FoldRequested`) に、エピソードも裏のスレッドで書き起こす。下書きを書くのは裏のスレッド、保存はターンを進めるスレッドにする (design_decisions D1837 の 4)
  - 呼び名を決めるのに Being の保存先を読むので、保存と同じ側に置く。裏のスレッドで保存先を読むと、ターンを進めるスレッドの書き込みと重なる (D1824-12 のレビューで見つかったのと同じ形)

**口が出来事の文を受け取ること**: いきさつの口 (`BackstoryWriter`) は出来事 (`Experience`) を受け取るが、この口は描いたあとの文を受け取る。今の書き起こしは、今の短期記憶の出来事 (Being の型ではない) から書くため。3b で今の短期記憶をやめるときに、出来事を受け取る形にそろえるかを決める。

**関連**: Issue #1824、design_decisions D1626、D1824-12、D1837。
