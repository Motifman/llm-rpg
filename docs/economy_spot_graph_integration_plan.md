> 目的: 休眠中の経済系資産 (gold / shop / trade / 装備 / スキル) を、現行の
> SpotGraph 実験経路へ**後付けの汚さなく**段階統合し、小さなシナリオで
> 「経済が回る」を検証できる状態を作る。

## 2. 統合の共通規約 — 「1 ツール = 5 点セット」

経済ツールを 1 つ足す PR は、必ず次の 5 点を同梱して閉じる。
どれかを「あとで」にすると静かな失敗になる (PR #594 の教訓と同型)。

1. **シナリオ宣言**: `disabled_tools` (負の宣言) と対になる**正の宣言**を
   scenario schema に足す (例: `"merchants": [...]`)。宣言の無い世界では
   `ToolExposure.is_exposed` が落とす。実在しない spot / item 参照は
   `create_world_runtime` で fail-fast
2. **ツール定義**: §1.3 の規約に従う。`_CONDITIONAL_TOOL_ORDER` へ追加し、
   常在ブロック (`ALWAYS_PRESENT_TOOL_ORDER`) は触らない
   (プレフィックスキャッシュ不変)
3. **プロンプト統合**: 効果判断に必要な値 (所持金・品揃え・価格) が
   状況確認に出る。位置はキャッシュ不変な先頭部を避ける
4. **trace 観測点**: 発火 / gold の増減 / 未発火理由が `trace.jsonl` で追える
   (`docs/trace_observability_review.md` を通す)
5. **`schedules_turn` の判断を明示**: 相手のターンを起こすか。
   曖昧にすると社会的観測ギャップ (v4 分析) を再生産する

### 2.1 横断の確認事項 (Phase 1 着手前に解消)

- **snapshot・再開との関係**: gold と所持品は per-Being 記憶ではなく
  world 状態。`BeingMemorySnapshotService` (記憶 9 store) の対象外。
  再開 run で gold がシナリオ初期値へ戻る挙動を「仕様」とするか、
  world 状態 snapshot を拡張するかを決める。**当面は「run 内で閉じる経済」
  を仕様とし、trace に snapshot_load 時の gold リセットを明記する**案を推奨
- **通貨の総量**: NPC 商人は通貨の無限の源泉 / 吸収先になる。
  初期実験では単純化 (商人の gold 無限) でよいが、trace で
  run 全体の gold 流入・流出を集計できる観測点を最初から置く

## 3. 設計判断 A: NPC 商人の表現 — 専用ツール vs interact

### 3.1 interact の実態

`INTERACT_DEFINITION` の引数は `target_label` + `action_name` +
自由形式の `parameters` (object)。action ごとの必要キーは
「『現在の状況』の対象行に『text が要る』のように表示」する方式で、
**JSON schema としては構造化されない**。

### 3.2 比較

| 観点 | A1: 専用ツール `buy_item` / `sell_item` | A2: interact の action (`buy` / `sell`) |
|---|---|---|
| 引数の広告 | schema に `item_label` / `quantity` を明示でき、LLM が形を間違えにくい | `parameters` は自由 object。「item と quantity が要る」を prompt 行の文章で伝えるしかない |
| 失敗の質感 | 在庫なし / gold 不足 / 買取対象外を専用の学習可能な失敗として返せる | 汎用 `INTERACTION_PRECONDITION_FAILED` に押し込まれ、原因の切り分けが濁る |
| ツール数 / payload | +2。ただし経済宣言の無い世界では露出しない | +0 |
| trace | tool 名で売買を直接フィルタできる | interact 全体から action_name で二次抽出 |
| 拡張性 | 価格交渉・まとめ買いなど売買固有の進化が閉じる | interact の schema が売買都合で肥大するリスク |
| 商人の存在感 | 商人はオブジェクトとして prompt に出るが、操作は別ツール | 「商人に話しかける」の質感は自然 |

### 3.3 推奨: A1 (専用ツール) + 商人は spot object

- **売買は専用ツール**。金銭が動く操作は、引数の構造・失敗理由・trace の
  すべてで専用の形を持つ価値がツール 2 個分のコストを上回る
- **商人は spot に紐づく存在として置く**。同席していないと売買できない
  (資源の位置と同じく、店の位置が意味を持つ)。表示は既存オブジェクト
  一覧への混載ではなく専用の「商人:」節 (PR-2 実装判断: 未宣言世界の
  prompt 不変を構造で満たし、対象解決と失敗の質感を売買専用に分けるため)。
  宣言した世界では商人の不在も「(この場所には居ない)」と明示する。
  所持金も宣言した世界でだけ「所持金: 30G」のように常時表示する (0 でも出す。
  「金が無い」と「経済の無い世界」を LLM が区別できるようにするため)
- interact は「店を眺める」「商人と雑談する」など**金銭が動かない**
  相互作用に将来使える。境界は「gold が動くか」で引く
- ShopAggregate は SpotId 紐づけなので、NPC 商人 = 「owner が NPC の店」
  として流用できる可能性がある。ただし owner 機能 (出品・取り下げ) は
  NPC には不要なので、**scenario 宣言の価格表だけで始めて、
  ShopAggregate の流用は Phase 2 以降のプレイヤー経営店で再評価**する
  方が小さい

## 4. 設計判断 B: trade (エージェント間取引) の形

3 案を正面から比較する。旧マーケットボード実装 (11 ツールのページ UI) を
そのまま復活させる案は、payload 爆発と「グローバル UI が物理世界を迂回する」
点で除外した。ただし**市場という概念自体は B2 として現行の質感に合わせて
再設計し、候補に残す** (将来のエージェント数スケールで必要になる)。

### 4.1 B1: 同席 offer 型 (同期 1 往復)

- `trade_offer(gives, asks, target_player_label)` → 相手のターンに
  `trade_accept` / `trade_decline`
- give_item の「無償」を「条件付き」へ拡張した形。同席・観測・
  相手ターン起動 (`schedules_turn=True`) と、現行の質感にそのまま乗る
- 物々交換 (item ⇄ item) と金銭取引 (item ⇄ gold) を同じ形で表せる
- 旧 TradeAggregate (1 item ⇄ gold の掲示) とはモデルが違うため、
  **新しい小さな集約 (PendingTradeOffer: 提案・承諾期限・成立/流れ)**
  が必要
- 論点: 提案が承諾されるまでの間、提示アイテムを凍結するか
  (凍結しないと承諾時に「もう手放していた」失敗が起きる。
  凍結する場合は期限切れ解放が必須)

### 4.2 B2: 市場型 (継続的な二重板、物理設置) — Phase 3 で採用

**目的は価格が動的に変わるところを観測すること。** 以下は Phase 3 の着手時に
確定した設計で、当初案 (売り板だけ・旧 TradeAggregate 流用) から変わっている。

#### 形: 締切つきの競りではなく、売り板と買い板を並べる

締切つきの競り (英国式オークション) は採らない。エージェントの手番は非同期で
間隔がばらつくため「締切まであと N 手番」が待つことを強い、待ちの手番が空振り
になる。時間の窓は世界の広さに対して外しやすく (Phase 2 の
`offer_expires_in_ticks` が生産往復 12 手番に対して既定 10 手番で、予約注文が
構造的に不成立だった)、締切はその罠をもう一段深くする。

代わりに、売り注文と買い注文を同じ板に並べる**継続的な二重板**にする。
MMO の「オークションハウス」の実体もこの形である。

実装の段は次のとおり。**PR 2 (#1178 の次) で売り側が動くところまで入った。**

| 段 | 中身 | 状態 |
|---|---|---|
| PR 1 | 宣言 / 板と注文 / snapshot / 初期注文 (ツールなし) | 済 (#1178) |
| PR 2 | 売り板のツール 4 つ + 観測 3 点 + trace + 表示 | 済 (#1181) |
| PR 3 | 買い板 (`market_bid` / `market_sell`) と、表示の買い側の列 | 済 |
| PR 4 | 検証シナリオ v3 (5 人 3 職) と demo 試験 | その次 |

| ツール | 意味 |
|---|---|
| `market_list_item` | 売り注文を出す (品を板に預ける) |
| `market_bid` | 買い注文を出す (gold を板に預ける) |
| `market_buy` | 板の売り注文を受ける |
| `market_sell` | 板の買い注文を受ける |
| `market_reprice` | 自分の注文の単価を変える |
| `market_cancel` | 自分の注文を取り下げる |

`market_reprice` を置くのは、**値を下げるという観測したい行動そのものが
1 手番で打てる**ようにするため。取り下げ + 再出品だと 2 手番かかり、品が
手元へ戻る往復が挟まって板として不自然で、trace 上も「同一人物・同一品目」の
推測でしか繋げられない。

買い板があると、**同じ品の売り手が 1 人でも値付けは動く** (「買い注文が 12G で
出ている、自分は 20G で出している」を見て下げる)。売り板だけの世界では
「同じ品の売り手が 2 人」が価格形成の必要条件になるが、買い板はその条件を
外す。不在の相手に注文を置けることが、市場が `trade_offer` に対して持つ最大の
利点でもある。

#### 値の書き方: 単価で書く

「パン 3 個で 10G」のような割り切れない束は作れない。単価が小数になると価格の
時系列が汚れ、エージェントが値を比べるときの見え方も悪くなる。「パン 2 個で
30G」は単価 15G × 2 で書けるので表現力は落ちない。**意図的な制約**である。

#### 自動約定させない

売り 20G と買い 22G が並んでも engine は潰さない。**線は「手番の外か」ではなく
「引き金に人が居るか」**にある。誰かが自分の注文を取ったから動いたのはよい
(引き金に人が居て、通知も届く)。engine が両者を勝手に選んで約定させるのはだめ
(引き金に誰も居ないので、裁定に気づく機会が消える)。世界が自分の手番の外で
変わること自体は許される — 板越しの取引では、自分が居ない場所で自分の品が売れる。

**交差した注文が板に残るのは欠陥ではなく観測対象**である。「18G で買えて 20G で
売れる」と並んだとき、それに気づいて取れるエージェントが居るか — 裁定取引を
自力で発見できるかという観測点になる。人間が trace を読むと約定漏れのバグに
見えるので、意図であることをここに明記しておく。

#### 表示: 「自分が何をできるか」で書く

```
市場の掲示板:
  "焼きたてのパン"   18G で買える (出品 3件)   15G で売れる (買い注文 2件)
  "薬草"             18G で買える (出品 1件)   売れない (買い注文なし)
  "麦束"             買えない (出品なし)        12G で売れる (買い注文 1件)
  あなたの出品: "焼きたてのパン" ×2 @20G (まだ売れていない)
```

「売り 3件 (最安 18G)」の形は、読んだ人が「買い 1件」を過去の約定か未来の
意思表示か取り違えた。人間が迷う文面はエージェントも迷うので、行動の言葉に
寄せる。利点は 3 つ: 次に打つ手がそのまま文になる / 表示された数字が常に
「自分が払う額・受け取る額」なので視点の混線が起きない / 交差が一目で分かる。

**読み出しは必ず見る人を引数に取る** (`board.rows_for(viewer)`)。いまの規模では
誰から見ても同じ行が出るが、(a) 自分の注文は自分で受けられないので、自分の
注文を除いた値が「その人に打てる手の値」になる、(b) 引き取り待ちの行は他人には
出さない、の 2 点で既に効いている。加えて、品目が増えると全件表示は破綻する
ので、そのとき「関心で絞る」形へ移せるように引数の形を先に決めておく。

#### 個別の注文をどう指すか

- **買う側 (`market_buy` / `market_sell`)**: 最安・最高から順に自動で約定させ、
  引数は品名と数量だけ。自分の注文は自動でスキップする
- **自分の注文 (`market_reprice` / `market_cancel`)**: 自分のぶんだけ個別に
  行を出し、品名で指す。**同じ品目・同じ向きの自分の注文は板に 1 件まで**に
  制限して、指し先を一意にする (番号で指す形は「表示に出ている名前をそのまま
  渡す」規約から外れる)

#### 預けるものと、返せないとき

出品した品と買い注文の gold は**板へ預ける** (Phase 2 の凍結ではない)。凍結は
「持っているが使えない」状態を作って所持品の表示と実際に使える量がずれ、
Phase 2 ではそこで二重減算のバグが生まれた。預ければ物がどこにあるかが観測と
一致する。

期限切れで返そうとしたとき所持品が満杯だと返せない。消すと静かな失敗になるので、
**板に「引き取り待ち」として残す**。他人には買えないので見せず、持ち主には
状態つきで見せる (見えないと、通知を 1 回見落とした時点で取り戻す手がかりが
消える)。約定の側は断る相手が居るので、受ける前に空きを確かめて断る。

#### 商人は世界の外との出入り口

商人が板で買い取った品は世界から消え、商人へ払った gold も世界から消える。
Phase 1 で商人の gold を無限と決めたのと同じ一本の理由による。在庫を持たせると
「商人を経由した転売」が最短の稼ぎ方になり、板での価格形成が商人に緩衝される。

初期注文は商人名義で、数量有限・補充なしで置く。板が空だと相場感がゼロから
始まり、最初の値付けが完全な当てずっぽうになるため。値は屋台の売り買いとは
わざとずらす (同じ値だと屋台と板で同じ取引ができ、板を使う理由が消える)。

#### 旧 TradeAggregate は流用しない

旧集約は「アイテムの実体 1 つ ⇄ gold」で数量も単価も持たず、板に並べたときに
値が個数で割り切れない。Phase 2 の `TradeSide` 寄り (品目 + 数量) に単価を
足した `MarketOrder` / `MarketBoard` を新しく作る。旧実装の削除は §4.4 のとおり
実 run 検証後。

#### 将来のテーマ (Phase 3 では作らない)

- **締切つきの競り**: 高額・希少品だけを競りにかける二本立ての候補。
  日用品は継続的な二重板、特別な品だけ競り、という分け方なら時間の窓の
  問題が「その品を狙う人だけ」に閉じる
- **グローバル取引所**: 全世界の板を統合し、検索・絞り込みが要るもの。
  表示を「関心で絞る」形へ移す設計と一緒に考える
- **約定履歴と相場**: `ItemTradeStatisticsReadModel` は**書き込み経路が存在
  しない** (interface は `find_statistics` 1 本だけで、in-memory 実装が架空の
  相場をハードコードしている)。形は借りられるが実装は作り直しになる。
  板の表示で足りるかを実 run で見てから着手する

### 4.3 B3: 段階導入 (B1 → B2)

- 少人数 (2〜6 体) では市場に流動性がなく、掲示しても誰も買わない
  「静かな空振り」が run を占める懸念がある。まず B1 で
  対面交渉の質感と価格判断を観測し、人数を増やすスケール実験の段階で
  B2 を導入する
- B1 と B2 は排他ではない (対面交渉と市場は MMO でも並存する)。
  導入順の問題として扱う

### 4.4 推奨: B3 (B1 を Phase 2、B2 を Phase 3 以降)

- B1 が give_item の既存規約に最も素直に乗り、検証も 2 体で完結する
- B2 は「掲示板 = spot object + 3 ツール」の形で設計を固定しておき、
  エージェント数を増やす実験の前に導入する
- **旧 trade 実装の扱い**: TradeAggregate と SQLite 配線は B2 の土台として
  残す。ページ UI (`trade_virtual_pages/`, `tool_catalog/trade.py`,
  `trade_executor.py`) は B2 の新ツールが実 LLM run で検証済みになった
  時点で削除する
- **移行期の名前規則**: 新旧の実装が同じ概念を持つ期間、LLM に見せるツール
  名は新実装が占有し、旧実装は名前の担当から外す (併存させない)。resolver
  chain は「None を返したら次へ」の fall-through なので、同じ名前を両方に
  残すと、新経路が何かの拍子に None を返した瞬間、**同名・別引数の旧実装へ
  黙って落ちる**。実装を消すのは上記のとおり実 run 検証後でよいが、名前の
  担当を外すのは新ツールを足すその PR でやる。B2 で掲示板を作り直すときは
  `market_*` の名前空間を使う (§4.2)

## 5. 段階計画

各 Phase は 1〜数 PR。Phase 内の各 PR は §2 の 5 点セットで閉じる。

### Phase 0: 本文書の確定 + 経済宣言スキーマ (ツールなし) — 完了 (#1144)

- scenario schema に `merchants` と `players[].initial_gold` を追加。実在しない
  spot / item_spec 参照、価格 0 以下、片側リスト内の item 重複を読み込み時に落とす
- item は表示名でなく `item_spec` の string_id で参照する (表示名だと同名衝突を
  loader が解けない)。商人の表示名はシナリオ全域で一意にする
- 宣言だけが先に入る状態は `_PENDING_CONSUMERS` で通した (design_decisions #108)

### Phase 1: NPC 商人との売買 (一方向の最小流通) — 実装完了 (#1148 / #1150 / #1151)

- 「商人:」節と所持金の行 (#1148)。宣言の無い世界の prompt はバイト一致で不変
- `buy_item` / `sell_item` (#1150)。数量は 1〜99 で、**部分成功を作らない**
- 失敗は 7 種に分け、remediation まで登録 (design_decisions #105 / #106)
- 同席の第三者への観測 (`schedules_turn=False`)、gold 増減の trace payload
  (`gold_change_source` に `merchant_buy` / `merchant_sell`)
- 検証シナリオ `market_town_v1` (#1151)。広場・土手・井戸端の 3 spot、商人 1 人、
  1 周 6 tick、1 周の収支 -4G。所持金の初期値は「パン 1 つは買えるが 2 つは
  買えない」12G

#### 実 LLM run による観察 (完了)

`market_town_v1` / 80 tick / プロンプト記録つきで 2 本走らせ、どちらも同じ系列を
たどった: 屋台を見る → 土手で薬草を 2 回摘む → 広場でまとめ売り (+12G) →
パンを買う (-10G) → 食べる → 休む → 次の採取で備える。LLM 発火 18 回、
失敗コードはゼロ。

80 tick にしたのは、空腹が +1/tick でバンドが 20/40/60/80% で切り替わり、
40 tick では圧が一度も本気にならないため。短いと「ループを発見できなかった」と
「圧が弱くて動機が無かった」を切り分けられない。

観測点の結果:

| 見たもの | 結果 |
|---|---|
| 売買の発火と失敗の内訳 | 買い・売りとも成立。失敗ゼロ |
| `gold_change_source` 別の流入・流出 | 流入 +12 / 流出 -10 を structured payload から集計できた |
| `inner_thought` の価格判断 | 収支への言及あり (「腹は満たしたし金も少し残った」) |
| 買う直前に商人節を読めていたか | その turn の prompt に商人節・価格・所持金が揃っていた (記録で確認) |
| 取引が記憶へ入り後の判断に出るか | episodic chunk 6 件 / 想起 18 件 |
| 危険域の前に確保する先回り | 空腹が危険域に達する前に食料を確保した |
| 場所の失敗と品の失敗の分布 | **実地では未検証** (失敗が一度も出なかった)。分類はユニットテストで担保 |

「表示 → 判断 → 行動 → 記憶」が 1 本につながっていることは確認できた。
数量 2 のまとめ売りも実地で使われた。

### Phase 2: 同席 offer 型 trade (B1)

  `shop_executor.py`) を削除する独立 PR

### Phase 3: 経済が回る合成シナリオ + 市場 (B2) の判断

## 6. 未決事項の決着

1. **決定: 静的な価格表 + 在庫無限** (Phase 1 の間)。商人の gold も無限にする。
   価格判断の観測が目的で、在庫管理は質感より複雑さが先に立つ。経済ループが
   回ってから再評価する
2. **決定: `buy_item` / `sell_item` に分離**。買いと売りで失敗の形が違う
   (gold 不足 ↔ 非所持、持ち物の空き不足 ↔ 買取対象外)
3. **決定: 既存の `PlayerStatusAggregate.gold` を使う**。gold はアイテムに
   しない。gold を人へ渡す経路は Phase 2 の `trade_offer` が担う
4. **未決のまま**: snapshot 再開時の world 状態 (gold / 所持品) の扱い。
   現状は per-Being 記憶だけが復元され、gold はシナリオ初期値へ戻る。
   §2.1 の推奨 (「run 内で閉じる経済」を仕様とし、trace に明記する) を採るか、
   world 状態 snapshot を拡張するかは、長走 run を始める前に決める
