## D1924. 考えが出力の上限で切れて行動を返せなかった呼び出しは、考えを止めて 1 回だけ呼び直す

**何を**:

- 主ターンの呼び出しで、行動 (ツールの呼び出し) が返らず、考えを有効にした呼び出しが出力の上限で打ち切られた (`finish_reason="length"`) ときだけ、同じメッセージとツールを、考えを止めて (`reasoning_effort="none"`) 1 回だけ送り直す。返った行動を実行する
- 1 段の呼び出し (`one_step`) と、reason-first の 2 段 (`assess_phase` / `action_phase`) の両方に同じ扱いをする。部品は `application/llm/services/world_llm_turn/truncated_output_retry.py`
- 呼び直しも行動を返さなければ、今までどおり `NO_TOOL_CALL` になる。2 回目は呼び直さない。呼び直しが例外で落ちたら、呼び出しの失敗として扱う (design_decisions D1595 のとおり次の tick に回る)
- 呼び直しは段 (1 段の呼び出し、評価の段、行動の段) ごとに 1 回まで (`TruncatedOutputRetryAllowance`)。評価の段は、評価が成立しないと 2 周目を呼ぶ (reason-first の評価の再試行) が、1 周目で呼び直していれば 2 周目では呼び直さない。1 手番の呼び出しは、評価の段が最大 3 回、行動の段が最大 2 回になる
- `tool_choice=auto` の 1 段の呼び出しは、文章で答えたときに強い指示を足して 1 回だけ再試行する (既存)。この再試行は考えを止めずに送り、打ち切られても呼び直さない。打ち切り → 考えを止めた呼び直し → auto の再試行、の最大 3 回になる
- prompt dataset の `attempt_index` は、その段の呼び出しの数で振る。呼び出しが例外で落ちても、次の呼び出しの番号は重ならない
- 上限に届かずに行動を返さなかった手番 (考えずに迷った手番) と、考えを止めた呼び出しが上限で切れた手番は、呼び直さない。後者は呼び直しても同じ呼び出しになる
- 応答の `choices[0].finish_reason` を、呼び出しの計測 (`LlmCallMetrics.finish_reason`)、trace の `llm_call`、prompt dataset の `metrics` に載せる
- 呼び直したら、trace の `llm_output_truncated_retry` を 1 件残す。payload は `phase` / `truncated_llm_call_id` / `retry_llm_call_id` / `reasoning_effort` (打ち切られた呼び出しの段階) / `outcome` (`tool_call` / `no_tool_call` / `invoke_exception`) / `returned_tool` / `retry_finish_reason` / `error_type`
- 呼び直しの呼び出しは prompt dataset に別の行で残る。`attempt_index` は打ち切られた呼び出しの次の番号、`parent_attempt_id` は打ち切られた呼び出しの `llm_call_id`、`reasoning_effort` は `"none"`

**なぜ**:

- run `mine_v1_011_switched` で、主ターンの 139 呼び出しのうち 18 件が、考えが出力の上限 (`LLM_MAX_OUTPUT_TOKENS`=4096) を使い切って、行動を返さずに打ち切られた。昇降機の定員の場面など、難しい判断の場面ほど長く考えるので、山場でエージェントが固まる
- 考えだけに上限を掛ける手段が、DeepSeek には無い。OpenRouter の `reasoning.max_tokens` が効くのは Gemini・Anthropic・一部の Qwen で、effort と同時には送れない (2026-10-31 に再確認。D1595 の 2026-10-11 の確認から変わっていない)。`deepseek/deepseek-v4.1-flash` の `supported_efforts` は `max` / `high` / `low` / `none` で、`none` は使える (`mandatory: false`)
- 同じメッセージを送るので、プレフィックスのキャッシュが効き、呼び直しの費用は小さい。考えの段階は `extra_body` の `reasoning` にあり、メッセージとツールの並びは変わらない

**採らなかった案**:

- 途中までの考えをプロンプトに添えて呼び直す: 切れた考えは同じ所を回っていることが多く、添えると迷いを持ち込むおそれがある。考えは英語で約 4k トークンあり、プレフィックスのキャッシュも崩す。添える値打ちがあると分かったら、あとで足す
- `LLM_MAX_OUTPUT_TOKENS` を上げる: 起きる率が下がるだけで、直らない。D1595 の上限は時間切れを防ぐために決めた
- 呼び直しをクライアント (`LiteLLMClient`) の中に置く: 実行した行動を prompt dataset の行に結び付ける `llm_call_id` は、ターンを進める側 (phase_a) が持つ。クライアントの中で呼び直すと、行動が打ち切られた呼び出しに結び付いてしまう

**打ち切られたことの伝え方**: クライアントは行動 (ツールの呼び出し) しか返さないので、`invoke` の形は変えず、呼び出しの計測の渡し先 (`metrics_sink`) を包む `CallOutcomeWatch` が `finish_reason` と考えの段階を覚える。trace の記録係が無いときも包んで渡し、呼び直すかを trace の有無に左右させない。そのため、trace の記録係が無いときも `metrics_sink` は None にならない (`tests/demos/test_world_runtime_llm_metrics_trace.py` をこの決まりに合わせた)。

**気をつけること**:

- 打ち切られた呼び出しも、呼び出しの失敗の連続の監視 (design_decisions 214) に `NO_TOOL_CALL` として 1 回数えられる。呼び直しが成功すれば、そこで連続は切れる。呼び直しも失敗すると、1 手番で 2 回数えられる
- 行動を決める呼び出しのほかに、補助の呼び出し (いきさつやエピソードの書き起こし、型付き判断) は `invoke` を使わないので、この呼び直しは掛からない

**関連**: Issue #1924、design_decisions D1595、214。
