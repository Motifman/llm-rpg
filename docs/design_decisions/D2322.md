## D2322. 新しい世界の run の終わりに、世界を SQLite のファイルに、Being の記憶を 1 人 1 ファイルに残す

**何を**: 新しい世界 (`game_world`) の run の終わりの状態を、`OUT` の下に残す (#2322、親 #2212)。分析は、LLM の入出力 (#2321) とこの終わりの状態を元にコーディングエージェントが行う。調整役とユーザーが決めた。

| | 決まり |
|---|---|
| 世界 | 世界の保存先 (`SqliteWorldStore`) をメモリの上ではなく `OUT/world.sqlite` に置く。世界は行為ごとに確定するので、遊びの途中で例外が出ても、そこまでの状態がファイルに残る。`SqliteWorldStore.open` に同じシナリオを渡せば開き直せる |
| Being の記憶 | `play()` の最後 (例外で抜けたときも) に、書き起こしを止めて書き終わった分を入れたあと (`MemoryWritingOnThreads.shutdown`)、1 人 1 ファイルで `OUT/beings/<person_id>.json` に書く。中身は人 (`person_id` と名前)、Being (人柄 `Persona` と居場所 `BeingAttachment`)、記憶 (古い世界の `BeingMemorySnapshotService.capture` の JSON: 記憶のターン、知り合い、エピソードと目次、メモ帳、短期記憶、訪れた場所) |
| 置き場所 | `snapshots/` を避ける。新しい世界は snapshot を保存しないと表示している (D2234) ので、読み込みに使えるものと紛れないようにする |
| 書けなかったとき | 1 人ぶん書けなくても、ほかの人の記憶は書く。書けなかった数と残したファイルの場所を `run_end` (`being_memory_files`、`being_memory_files_not_written`) と report.md に出す |
| 同じ OUT | 前の run の `world.sqlite` が残っている OUT は入口で断る。どちらの run の終わりか分からなくなるため |
| 読み込み | 作らない。途中からの再開が要るときに #2236 で扱う。新しい保存先は足していないので、snapshot まで配線する決まり (CLAUDE.md) には当たらない |

- `BeingMemorySnapshotService` は古い世界の application (`application/being`) にあり、ステージ 9 (#2236) で古いコードを消す対象に入る。新しい世界がこれに頼っているので、古いコードを消す前に Being のパッケージへ移す必要がある。この service が import するのは Being のパッケージと例外の型 (`domain.being`、`domain.common`) だけで、ゲームのパッケージは import していないので、移すのは小さい作業で済む
- 記憶を書くのは Being を世界から離したあと (`EndPlaySession`) なので、居場所は離れたあとの値 (多くは空) になる

**関連**: Issue #2322 / #2321 / #2236 / #2212、D2234、D2321。
