作成: 2026-07-15。M7 実走 (m7_v3coop_001) の 2 独立分析 (6 軸分析 + trace 一次分析) の合意結論に基づく。

## コード確認済みの前提 (2026-07-15 時点の main)

- **interact の自由入力は配線済み**: ツールスキーマに `parameters` (パズル用) が既にあり、`SpotInteractionApplicationService.execute_interaction(interaction_parameters=...)` まで届いている。D1 はこれを消費する effect を足すだけ
- **effect type に不足は 1 つだけ**: `InteractionEffectTypeEnum` にプレイヤー入力テキストを object state へ書く効果が無い (`CHANGE_OBJECT_STATE` は静的値のみ、パズル入力は `puzzle_evaluation_service` の別経路)
- **シナリオイベントの SHOW_MESSAGE は全体放送**: m7 trace で実証 (t144 の船影メッセージが山頂のリオ含む 4 人に environment 観測として到達)。一方 v3_coop の `reactive_bindings` は空で、`light_signal` の効果はスポット内のみ → **狼煙が点いても遠方には何も見えない** (煙の可視化はシナリオ JSON の追記のみで実装可能)
- **structured_failure の入口は loop_guard のみ**: 状態破綻 (`PlayerStatusAggregate.is_down`、空腹 max) は prose 観測にしかならず evidence 化経路が無い。m7 では down 系 trace event も 0 件 (#621 系、調査要)
- **清算の判定材料はアクセス可能**: `SubjectiveEpisode.who: Tuple[str, ...]` + chunk 観測テキストで共在を照合できる
- **extract_metrics.py は関数追加式** (`_extract_*` パターン) で協調指標を足しやすい

### Wave 0 — 計測と追試 (実装より先に着手)

**PR-A: 協調指標を extract_metrics に追加**

- 対象: `.claude/skills/trace-analysis/extract_metrics.py` (P1b のパターン踏襲)
- 追加指標:
  1. **ペア別共在 tick 行列**: `position_change` の区分一定展開から全 tick の位置を復元し、ペアごとの同一スポット滞在 tick 数を出す (m7 で「合流 8 回」型のイベント数集計が誤解を招いた反省。実際は浜組 3 人が 160/201 tick 共在、リオは t17 以降 0)
  2. **分断後のグループ間知識移転**: 共在していないペア間の hearsay evidence 数 (m7 は 123 件中グループ跨ぎ 0)
  3. **約束の verdict 別集計** + PR-C の `verdict_rejected` を含む
  4. **狼煙材料の保有分布時系列** (action_result の取得/消費から復元)
  5. **4 人同スポット滞在 tick** と **give_item 実行件数** (003 分析で手計算した勝敗の説明変数。003=35 tick / 001=17 tick、give_item は両 run とも 0)
- 試験: m7_v3coop_001 (敗) と m7_v3coop_003 (勝) の両 trace を入力にした回帰テスト。指標が勝敗を判別できること (共在の均等化・話者別 HEARSAY のリオ 1→15 など) を固定する

**PR-B: 実験実行設定の是正 (小)**

- `--max-world-ticks` を v3_coop の設計値 240 に合わせる (m7 は 200 で打ち切られ、stranded 判定が発火しなかった)。Makefile / 実行手順の該当箇所を更新

**R1: クリーン追試 n=2** (PR-B 後、コスト ~$0.8 / ~50 分)

- 現行 main (#710 down/revive 修正込み) + 240 tick で 2 本。狙い: **修正後クリーン条件での成功率推定** (現戦績は 003 の 1 勝 0 敗。001・002 はバグ下の run で母数に入れない)
- 副目的: down が発生する run を引けたら #710 の revive 経路 (grace timer → 復帰) の実地検証を兼ねる
- 評価: PR-A の自動指標のみ (深掘り分析はしない — 分析経済の反省)

### Wave 1 — 記憶システム側の修正 (質感に副作用なし)

**PR-C: 約束清算の共在ゲート (D3)** — 維持 (優先度は PR-A/PR-D の後)。003 では偽 fulfilled の再発なしだが、001 の t188 という確定した再現ケースがあり修正の正しさは揺らがない

- 対象: `_pending_prediction_resolution.py`
- 内容: verdict が fulfilled かつ `resolution_cues` に `player:X` を含む場合、判定 chunk の `episode.who` / 観測テキストに X が現れることを必要条件にする。満たさなければ verdict を**棄却して約束を保留** (drain しない)。窓超過時は従来の expired 経路
- `TraceEventKind.PENDING_PREDICTION_VERDICT_REJECTED` を新設 (being_id / pending_id / verdict / 棄却理由)
- `player:` cue の無い約束はゲート対象外 (照合材料が無い。従来どおり LLM 判定を採用) — この限界を docstring に明記
- 試験: m7 の t188 ケースを固定入力にした再現テスト (リオの偽 fulfilled 2 件が棄却されること) + 実際に共在した fulfilled が通ること

**PR-D: 状態破綻の structured_failure 化** — run 002/003 で補強された

- 背景: m7 最大の失敗 (空腹 100 での反復戦闘不能、down 観測 prose 90 回) が evidence 化されず、「最も致命的な失敗が最も学ばれない」逆転があった (6 軸分析 D-32)。002 ではエイダの down (t60) が 140 tick 誰の学習にもならず、003 では structured_failure 1→6 件の昇華が失敗率低下 (18.2%→14.5%) と相関 — 「失敗の記憶化は効くが、状態破綻には届いていない」ことが 3 run で一貫
- 内容: `is_down` への遷移と空腹 max 到達を、`structured_failure_evidence_transcriber` 経由の高 salience evidence として積む。フック位置は player status 変化の観測生成点 (実装時に `player_formatter` 周辺を確認して既存パターンに合わせる)
- フラグ: 既定 OFF (`STATE_COLLAPSE_EVIDENCE_ENABLED` 仮)、R2 で ON — 第 2 期の慣例どおり
- 試験: down 遷移 → evidence 1 件 (salience high) / 同一 tick 内の重複防止 / フラグ OFF で no-op

**PR-E: #621 系 down/revive trace event の欠落調査 → 修正** — **完了 (#710 マージ済み)**

- 原因は戦闘不能/復帰ハンドラの current_tick 二重展開クラッシュだった。残件は「down が実際に発生する run で grace timer → revive が回るか」の実地確認のみ (R1/R2 に内包)。PR-D のフック位置検討は #710 後のコードを前提にできる

### Wave 2 — 世界側の機能追加

**PR-F: 看板 — プレイヤーが書き込めるオブジェクト (D1、エンジン側)**

- domain: `InteractionEffectTypeEnum.WRITE_PLAYER_TEXT` (名称は実装時に既存命名と整合) を追加。効果実行時に `interaction_parameters["text"]` を検証 (非空・文字数上限は定数化、P703 の M-2 と同じ思想で超過は切り詰め + 可視化) し、書き手名・tick と共に object state へ保存
- 表示: examine 系 interaction の結果に「『<本文>』 — <書き手名>」を含める (既存の object state 表示経路を確認して合わせる)
- 記憶化: **コード変更なし**で既存 P9 抽出 (話者名つき主張 → heard_claims) に乗ることを狙う。乗るかどうかは品質チェック (docs/quality_checks のプロンプト再生方式) で確認し、乗らなければ抽出プロンプトの 1 行追記を同 PR で
- 上書き・追記の方針: v1 は「上書き」(最後に書いた 1 枚) で最小に。追記式は将来
- 試験: TDD。書き込み → state 保存 / 空文字・超過の拒否と切り詰め / examine で書き手名つき表示 / ローダが JSON の看板定義を VO まで通すこと

**PR-G: v3_coop 調整 — 煙の可視化 + 生存経済 (D2、JSON のみ)** — **凍結**

- 凍結理由: 003 が**無調整でクリア可能**と実証した (D4「無調整先行」の判断が正解だった)。今材料を足すと「協調しなくても解ける」方向に難度が壊れる恐れの方が大きい
- 再開条件: R1 のクリーン成功率が明確に低い (目安 1/3 未満) 場合のみ。その際も D2 の合意範囲内で最小限から
- 再開時の内容 (据え置き): 煙の全体放送 SHOW_MESSAGE / 乾いた海藻 / 貝の緩和。狼煙の材料要件・2 人ゲート・rescue tick は不変、v2 / v2_short 不変保証つき
- 補足: 煙の可視化は「分断時の保険」としては生存経済と独立に価値があるが、003 の勝ち筋 (共在してからの点火) では不要だったため、単独先行もせず R1 の結果待ちに含める

**PR-H: 看板を v3_coop に配置 (PR-F 依存、JSON のみ)**

- 配置案: 山道 or 山麓の「石積みの目印」(書き込み可能・examine 可能)、拠点の「板切れの掲示」あたりの 2〜3 箇所。リオの経路と浜組の生活圏の交点に置くのが狙い (m7 でリオが 7 回 memo に書いた内容が、ここにあれば浜組に届いた)
- 003 の勝因「私的発見の公共化 (t95 の合流の一文)」は発話 + 共在という揮発的経路に依存しており、看板はこれを不在の相手にも届く形で恒常化する — 003 の結果は看板の設計意図をむしろ裏書きする
- PR-G 凍結に伴い依存は PR-F のみ (PR-G が凍結解除された場合は同ファイルのため順にマージ)

## 保留 (R1/R2 の結果を見てから判断)

初版でここに置いた項目の多くは 001 限定の現象を根拠にしていた。003 では以下のいずれも再現しておらず、保留 (= 介入しない) が正解だったことが確認された。据え置く。

- **habituation ペナルティのエスカレーション**: 001 で上限 4 に 72% 張り付き。003 では想起系の量的指標は 001 と差がなく (habituation 平均 3.41 vs 3.48)、勝敗を説明しない — 「検出はあるが圧が無い」問題の緊急度は下がった。R1/R2 で単調ループが再現した場合のみ設計へ
- **知覚できない不可能性の解消** (存在しないレシピへの固執に世界が「その手段は無い」と返す): 001 の架空の布着火材レシピが根拠だったが 003 では固執が起きていない。誤爆リスクもあり保留継続
- **行動変換層への介入** (計画→実行の橋): 001 のリオ (memo 7 回 vs travel_to 0) が根拠だったが、003 のリオは自ら合流を選び発話 13 回。「知識も体力もあるのに動かない」が R1/R2 で再現した場合のみ着手
- **書き置きの HEARSAY 抽出が乗らなかった場合の抽出プロンプト拡張** (PR-F の確認結果次第)
- **単独行動者のターン配分バイアス**: 001 のリオ 63 ターンが根拠だったが 003 は全員 86〜101 で均等 — 分断の結果であって原因ではない可能性が高い。PR-A の指標で常時可視化に留める
- **give_item が 0 件のまま** (003 の 6 軸分析の新規観察): 物資移転なしでも勝てた以上、現時点で問題として観測されていない。インセンティブ設計はいじらず観察継続 (質感優先)

- PR-D のフック位置は実装時に要確認 (down 遷移の一次イベント発生点。#710 マージ後のハンドラを前提にできる)
- 003 の成功が再現可能な水準か、確率的な当たりかは n=1 では不明 — R1 の成功率が PR-G 凍結解除の唯一の判断材料
