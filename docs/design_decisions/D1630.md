## D1630. 環境が渡す説明文の型を足し、ゲームが今の文をそれに詰めて渡す

**何を**: #1630 (作業記憶) の移し方の 1 本目。プロンプトは 1 文字も変えていない。

- 環境との取り決め (`being/contract/description.py`) に 3 つの型を足した
  - `Description`: 見出しの語と文。環境が自分の言葉で書いた説明文 1 つ。見出しは【】で囲まない。囲むのは文にする側の書き方
  - `Orientation`: `Description` の並び。入るときに 1 回受け取る案内
  - `Scene`: `Description` の並び。毎ターン置き換わる、今見えている場面
  - どちらの並びも、同じ見出しを 2 回渡すと断る。空でもよい
- ゲームの側は、今の文をこれに詰めて渡す
  - `WorldRuntime.orientation_for(player_id)`: 【ペルソナ】、【世界の前提】(舞台のタイトルと概要)、概要と見取り図のうち見出しの行で始まる段落 (station_drill なら【このゲームについて】【この場所の造り】【点検の割り当て】【話し合いと投票の決まり】)。システムプロンプトはここから組む (`build_world_system_prompt_for`)
  - 1 ターンのプロンプトの `prompt["scene"]`: 【現在地と周囲】、知らせ (【公開SNS】【進行中の異常】【時間の経過】)。出すツールが決まって候補表を差し込むと (`inject_dynamic_argument_candidate_table`)、【現在選べる対象引数】が【現在地と周囲】の直後に入る
- 説明文を文にするのは、今はゲームの側のつなぎ (`description_text.py`) が、`【見出し】` の行と文で書く。作業記憶 (2 本目) が Being の側で文にするようになったら移す

**詰め方で決めたこと**:

- 見出しの無い段落 (陣営の人数の行など) は、直前の説明文の文に空行を挟んで続ける。シナリオが概要に書いた見出し (【このゲームについて】など) も、今のプロンプトでは見出しとして読まれているので、説明文に分ける
- 「- 行動の制限: …」の行は見出しを持たず、今のプロンプトでは最後の段落 (station_drill なら【話し合いと投票の決まり】) の末尾に付いている。文面を保つため、最後の説明文の文の末尾に付けた。環境の決まりに分けるのは 4 本目
- 【公開SNS】は、見出しの後に改行を入れる形に揃えた。それまでは見出しと本文が同じ行にあった。公開 SNS のシナリオは起動時に止めている (#1920) ので、動く世界の文面は変わらない。#1920 で作り直すときも説明文の形のほうが扱いやすい
- 【現在の目的】は、今のままユーザー文の先頭に置く。案内に入れるのは 4 本目
- ユーザー文の末尾は「現在地と周囲 → 候補表 → 繰り返しの警告 → 知らせ → 締めの一文」の並び。繰り返しの警告は場面に入れず、締めの一文の側に置いたので、場面の途中に指示が挟まる。2 本目で作業記憶が組むときに決める (#1630 のコメント)

**起動時に止まる入力**: 今までは何でも文にしていたが、説明文に詰めると次の入力は起動時に `ContractViolation` で止まる。どちらも今のシナリオ (`data/scenarios` と `tests/fixtures/scenarios`) には無い。黙って続けると、Being が同じ見出しの 2 つの説明文を見分けられなくなるので、止める形にした。

- 概要か見取り図に、同じ見出しの段落が 2 つある (概要に【世界の前提】や【ペルソナ】を書いた場合を含む)。例外の文に重なった見出しを出す
- 人物像 (`persona_prompt` など) が空、または見出しの行だけ

**場面と実際に送る文のずれ**: reason_first の行動の段では、締めの一文を差し替えるので、ユーザー文から知らせが消える。`prompt["scene"]` には知らせが残る。今は場面を読むところが無いので害は無いが、2 本目で場面から文を組むときに合わせる。

**一字一句同じであることの確かめ**:

- `tests/fixtures/prompts/` に、置き換えを始める前の main (`21a33e4c9`) で組んだ廃坑の山村と station_drill のプロンプトを置いた。最初のターンの全員と、1 人目が同じ待機を 3 回繰り返した直後のターン (繰り返しの警告と【時間の経過】が出る) を入れてある
- `test_prompt_matches_baseline.py` が、今のコードで組んだプロンプトと資料を比べる。資料の無いシナリオも含め、`data/scenarios` と `tests/fixtures/scenarios` の全シナリオで、置き換え前と同じ文面になることを手元で確かめた (PR に記録)。文面を変える PR は、`PYTHONPATH=. uv run python -m tests.support.prompt_baseline` で資料を書き直す

**なぜ**:

- 環境は自分の言葉で書いた文だけを渡し、Being は中身の種類を見ずに、どの並びで届いたかだけで置き場所を決める (#1630 の 2026-11-01 の決定)。チャットの場のような別の環境でも、同じ型で入れる
- 取り決めを Being の側に置くのは、Being は 1 種類で環境はたくさんあるため。環境ごとに型を持つと、Being が環境の数だけ違う型を知ることになる
- 1〜3 本目はプロンプトを変えずに置き換えるので、置き換えで質が落ちていないことを run を回さずに確かめられる

**まだしないこと**: `WorkingMemory` と `CurrentWorkingMemory` は 2 本目。ゲームの側の並べる処理 (`context_format_strategy.py`) を消すのは 3 本目。
