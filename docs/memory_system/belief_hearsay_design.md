# 伝聞による学習 (HEARSAY) — 人の話と噂話から belief を作る

## 1. なぜ作るか (実測ベース)

unified_full_001 で、カニの危険を p1・p2・p3 が**それぞれ自分で襲われて
別々に 3 回学んだ**。伝達自体は起きている — リオが「干潟にカニがいる」と
話せばカイの観測に入り、「リオがそう言っていた」という**体験**として
エピソード記憶に残り、想起もできる。しかし evidence の入口が
「自分の予測誤差 / 的中」しかないため、聞いた内容は永遠に belief
(一般化知識) に昇格しない。**人の話から学ぶ経路が構造的に存在しない**。

## 2. 実装 — 4 ステップ、新規 LLM 呼び出しゼロ

### ステップ 1: 抽出 (LLM、chunk 主観補完に同乗)

chunk 主観補完 (その期間の観測を既に全部読んでいる既存呼び出し) の
JSON 応答にフィールドを 1 つ足す。U10 の約束抽出と同型のパターン。

```
heard_claims: [{ speaker: "リオ",
                 claim: "岩礁海岸は山方面に通じていない" }] | null

プロンプト指示: この期間に、他者が「世界や人がどうであるか」
(場所・物事・人物) について語った主張があれば抜き出す。
その場にいない人についての話 (噂話) も含む。
挨拶・依頼・感想は含めない。誰の発言か特定できるものだけ。なければ null。
```

### ステップ 2: 転記 (ルール)

`heard_claims` が非空なら evidence buffer へ:

```
BeliefEvidence:
  source_kind: HEARSAY
  text: claim
  cue_signature: 主張の対象で決める (spot:岩礁海岸 / player:エイダ / tool:...)
  source_speaker: 話者 (メタとして別途保持。cue に混ぜない)
```

**話者と対象を混ぜない**のが唯一の注意点。「リオがエイダについて語った」
なら cue は `player:エイダ` (何についての知識か)、リオは
`source_speaker` (誰から来た情報か)。混ぜると「リオについての belief」に
化ける。

### ステップ 3: 固着判断 (既存の固着パス LLM)

HEARSAY evidence は他の evidence と同列に batch に載る。shortlist には
(a) claim の cue に一致する既存 belief に加えて、(b) **話者についての
人物 belief** (`player:<speaker>` 軸) を載せる。プロンプトに:
「伝聞は自分の体験より弱い証拠である。話者について知っていることを
踏まえ、信じる (create/strengthen) か捨てる (discard) か判断せよ」。

これにより非対称な信頼が数値なしで表現される — unified_full_001 の
カイは「リオは話をちゃんと聞いていない (conf0.8)」と「リオは釣り場の
情報を提供してくれる (conf0.5)」を両方持っており、「あいつは人の話は
聞かないが、地形情報は確かだ」という判断が文脈から可能。

### ステップ 4: 重み (ルール)

confidence 計算で HEARSAY 由来の支持は自分の体験由来より軽く数える
(まず 1/2)。これは source **種別**単位の定数 1 個であり、話者ごとの
数値テーブルではない。

## 3. 噂話 (人物についての伝聞) — 機構の追加なしで乗る

人物モデルはもともと `player:` 軸の belief であり、世界と人は最初から
同じ belief 空間にいる。「干潟は危険だ」と「エイダは頼りになる」は
同じ型のデータなので、抽出対象を「世界や人がどうであるか」に広げる
だけで噂話は同じパイプラインを流れる。

帰結:

- **統一設計シナリオ 2 が閉じる**: 「Bの現在を人づてに聞いて、変わって
  しまったと嘆く」= 伝聞 evidence が高確信の人物 belief と衝突する重い
  誤差 (contradict / revise)。嘆きの実装そのもの
- **自分についての噂**: 「カイは頼りない」とリオが言っていた、を本人が
  聞くと `self:` 軸への evidence になる。**他人の評価が自己認識に
  流れ込む** — 自己像の社会的形成が軸の語彙だけで手に入る
  (設計原則の「他者からの可視性」と接続)
- **噂の訂正のループ**: 誤った噂で歪んだ人物像が、実際に会った体験
  (直接 evidence は伝聞より重い) で訂正される — 再会シナリオの変奏

## 4. ハードコード回避の線引き

なりうる箇所は 2 つあり、両方避ける:

1. **抽出をルールで書かない**: 「〜がいる」「〜は危険だ」のパターン
   マッチは言い回しの無限のバリエーションに敗北し、シナリオ固有語彙が
   ルールに混入していく。抽出は書き込み時の LLM の意味判断
   (salience で「ダメージ=重要」のルールを退けたのと同じ分担)
2. **話者の信頼を数値で管理しない**: 「リオの信頼度 0.6」を持つと
   「何をしたら何点上下するか」のルール表が必要になり破綻する。
   信頼は人物 belief (自然文) が既に持つ情報を文脈判断で使う

ルールで書いてよい部分: 転記のコピー、source 種別の重み (定数 1 個)、
抽出対象を発話カテゴリの観測に絞ること (世界知識ではなく観測が持つ
構造の利用)。「ルールは溜めて・数えて・運ぶだけ、意味判断は LLM が
書き込み時に一度」の既定分担のまま。

## 5. 引き受けるリスク (仕様)

- **乱発** (何でも伝聞候補化): 固着パスの discard が防波堤
  (unified_full_001 実測で素材の 25% を棄却)
- **嘘・勘違いの伝播**: 起きてほしい挙動。誤った噂が広まり、誰かの
  実地の反証 (contradict) で訂正され、訂正がまた伝聞で広まる — まで
  観測できたら集団の知識として最も人間らしい結果
- **人の噂は誤情報率・感情バイアスが高い**: 伝聞の軽い重み +
  discard + contradict がそのまま効く。専用の対策は作らない

## 6. 検証

- L2 replay: unified_full_001 の trace から発話を含む chunk 素材を抽出し、
  heard_claims の抽出品質 (取りこぼし / 乱発 / 話者の特定) を先に収束
- 実走の検証場は協力シナリオ v3 (unified_full_001 分析 R9)。協調指標
  「発話による知識移転回数」= HEARSAY evidence 数がそのまま効果測定になる
- 質感シナリオ pytest: 発話観測を含む chunk → 転記条件 / speaker と
  cue の分離 / 自分への言及が self: 軸に入ること
