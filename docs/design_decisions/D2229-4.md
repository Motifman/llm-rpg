## D2229-4. 誰がどの登場人物を動かすかは、遊びの進行の配役 (`Cast`) が持つ

**何を**: Being を新しい世界に入れる遊びの進行 (`play_session`、#2229) を作り、誰がどの登場人物を動かすかの対応表を、遊びの進行のドメインの集約 `Cast` として作り直した。古い `PlayerBeings` は使わない。

### 1. `Cast` が持つもの

| | 決まり |
|---|---|
| ID | 世界 (`WorldId`)。1 つの世界に配役は 1 つ |
| 配役 | 登場人物 (`PersonId`)・Being (`BeingId`)・Being の名前の組 (`CastMember`)。1 人以上いて、登場人物・Being・名前のどれも重ならない。紹介は名前で渡すので、名前が重なると誰を紹介したかが分からない |
| 入るときの材料 | 登場人物ごとの取り決め (`EnvironmentEntry`) と案内 (`Orientation`)。`brief` で持つ。同じ人に 2 回は渡さない。Being は最初の取り決めで入っているので、渡し直すと Being の受け取ったものと食い違う |
| 紹介 | 世界が返した最初から知っている人 (`PersonId`) を、配役の Being の名前にして `Introduction` にする。配役に無い人なら断り、何も持たない |
| 知らせ | `brief` のたびに `BeingCastInWorldEvent` (世界・登場人物・Being・取り決め・案内) をためる。trace への書き出しは実験 (#2233) がする |

例: 廃坑の山村 v2 で、ゲン (`gen`) が知っている人は世界の問い合わせで `sayo` と返る。`Cast` は `sayo` を動かす Being の名前「サヨ」に変え、ゲンの取り決めの紹介を「サヨ」だけにする。

案内と課す目的を `Cast` が持つのは、Being が案内を持たないため。作業記憶 (`CurrentWorkingMemory`) は、環境から毎ターン案内と課す目的を受け取る。遊びの進行がターンを回すとき (#2232) に、`Cast` から渡す。

**採らなかった案**:

- 古い `PlayerBeings` を使う: 古いパッケージの整数の `PlayerId`・古い `WorldId`・古い `AggregateRoot` を使っており、遊びの進行から import すると古いゲームのパッケージへの依存が入る
- 案内を Being に持たせる: Being の契約が変わる。いまの Being は案内を毎ターン受け取る形で、持つ場面が無い

### 2. Being の snapshot には載せない

`Cast` は `BeingId` を値に持つが、キーは世界で、中身は「この遊びで誰が誰を動かしたか」という遊びの持ち物になる。Being が世界をまたいで持ち越す記憶ではないので、Being の snapshot (`BeingMemorySnapshotService`) には配線しない。遊びを止めて再開するときの保存は、遊びの進行の保存として #2232 以降で決める。

**採らなかった案**:

- Being の snapshot に「どの世界の誰を動かしていたか」を載せる: 別の世界に連れて行った Being が、前の世界の配役を持ち続ける。居場所 (`BeingAttachment`) は Being が持つが、それは環境の識別子と表示の名前だけ (D1928-2)

### 3. 遊びの進行は、世界と Being を入口だけで呼ぶ

| 層 | import してよいもの |
|---|---|
| どの層も | 遊びの進行の domain、`eventing`、Being の契約と `BeingId`、世界の ID の値 (`game_world.domain.value_object`) |
| application | さらに、遊びの進行の application と、入口のモジュール。Being は `prepare_being`・`enter_environment`・`perceive_observation`、世界は `open_world`・`brief_entering_person`。入口を使い始めるときに、境界のテストの一覧に足す |
| infrastructure | さらに、遊びの進行の infrastructure、シナリオの読み込み (`game_world.infrastructure.scenario`) |

`tests/architecture/test_play_session_package_import_boundary.py` が層ごとに見張る。シナリオのファイルを読むのは infrastructure の仕事なので、application は `LoadedScenario` も `WorldDesign` も知らない。遊びを始める `StartPlaySession` は、infrastructure が組んだ `OpenWorldCommand` と役 (`Role`) の並びを受け取る。

### 4. 配役は遊びを始める入力にし、シナリオからは既定だけを作る

どの Being がどの登場人物を演じるか (配役、`PersonId` → `BeingId`) は、`StartPlaySessionCommand.casting` で外から受け取る。シナリオから作るのは、既定の配役 (`casting_by_person_name`、`gen` → `BeingId("gen")`) と、配役に依らない役の材料 (`roles_from_scenario`、人柄・立場・目的) だけにする。

| 配役をシナリオで決めない理由 | 例 |
|---|---|
| 別のシナリオに同じ名前の登場人物がいると、別の人物なのに同じ Being の記憶を引き継ぐ | 別のシナリオの `gen` が、廃坑の山村のゲンの記憶を持って入る |
| 回ごとに組み分けを入れ替える (#1548) と、同じ Being に別の登場人物を当てる | 1 回目にゲンを演じた Being が、2 回目にハルを演じる |

配役を実験の設定で上書きする口は、実験 (#2233) か #2234 で作る。

「役の全員に Being が当たっている」と「Being の名前が空白でない」は配役の規則なので、ドメインの `Casting.member` と `CastMember` が `PersonNotCastException`・`CastValidationException` で断る。遊びを始めるコマンドは値を運ぶだけにする。どちらも世界を開く前に断る。

Being の名前は役の人柄の欄 (`name`) から導き、役は名前を別に持たない。2 つを別々に持つと、紹介に使う名前と、Being が自分の名前として持つ名前が食い違いうるため。

### 5. 断られうる手順は、世界を開く前に済ませる

`StartPlaySession` は、配役を組み、全員に案内を問い合わせて渡し (`Cast.brief`)、全員の Being を用意してから、世界を開き、全員の名前を世界の名簿に付け (D2229-3)、一人ずつ入れる。世界を開いて Being を入れたあとで断られると、同じコマンドでやり直せない (世界はもう開いていて、Being はもう入っている) ため。

例: ゲンが知っているサヨを配役から外すと、ゲンの紹介が組めずに断る。このとき世界は開かず、どの Being も用意しない。サヨを入れた配役で同じ世界を開き直せる。

Being の用意 (`PrepareBeing`) は、もういる Being を変えない (D2229-2) ので、世界を開く前に済ませてやり直しても重ならない。

### 6. ドメイン例外は世界と同じ形にする

`PlaySessionDomainException` を基底に、`error_code` を持つ例外を足す。Being の例外が多重継承するカテゴリ (`ValidationException` など) は古い `domain/common` にあり、遊びの進行からは import できない。世界 (`GameWorldDomainException`) と同じく、カテゴリを持たない形にした。
