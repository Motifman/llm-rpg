# 対策が実際に機能する形

作業中に踏んだ失敗と、その対策の記録。**対策そのものが壊れた回**を中心に書く。

対策は作った時点では効かない。**次に同じ場面が来たときに実行されて初めて効く。**
ここに書くのは「何を対策としたか」ではなく「**その対策がどう壊れたか**」である。

---

## 判断を挟むと、対策は壊れる

1 日のうちに、同じ形で 3 回壊れた。

| 対策 | 壊れ方 |
|---|---|
| 変異試験の前にコミットする | 「今回は小さいから」で飛ばす |
| CI が緑であることを確認してからマージする | 「2 本まとめてだから」で判定を落とす |
| メッセージはファイル経由で送る (引用符がシェルに食われるため) | 「短いから」で直接書く |

**どれも対策を忘れたのではない。対策を持っていて、例外を作った。**

共通しているのは、対策に**「いつやるか」の判断が挟まっている**こと。判断が挟まると、
**負荷が低いときほど省略される**。そして負荷が低いときは注意も低いので、**省略した
ことにも気づかない**。

**常にやる、が唯一機能する形。** 例外の条件を 1 つでも認めた瞬間、その対策は
「気をつける」と同じ強さに戻る。

### 構造にできるものは、構造にする

いちばん強いのは、**判断する場所そのものを無くす**こと。

- ツールの側で「gold を記録する」と決める → 書き忘れる余地が残る
- **呼び出しを包んで前後を測る** → 足す人が何も知らなくてよい (`docs/design_decisions.md`
  「同じ量が動くなら、どのツールから動いても同じ形で記録する」)

**規則を人に守らせるのではなく、構造で守る。** 守るべき人がいなくなったとき、規則は
初めて壊れなくなる。

## 検査は、狙ったものを見ているとは限らない

1 日で 10 件、**書いた検査が狙った対象を見ていなかった**。すべて変異試験で見つかった。
変異を回さなければ 10 件とも通していた。

内訳は 3 種類ある。

| 型 | 例 |
|---|---|
| **別のものを見ていた** | 提供者側の警告を見ていて、最後の砦の警告には届いていなかった |
| **粒度が違った** | 識別子 (`drop_item`) を探していたが、文章は動詞 (`drop`) で書かれていた |
| **基準が緩すぎた** | 「縮める前より短い」を上限にしていたので、ほとんど縮めなくても通った |

3 つ目が特に危ない。**「前より良くなった」を基準にすると、ほとんど良くなっていなくても
通る。** 到達したい値を先に決めて、そこへ置く。

### 一覧で守る検査は、一覧が空でも緑になる

既知の語の一覧、既知のツールの一覧、対象の一覧 — **表を作って守る検査は、表を空に
しても通る**。**空の禁止までセットで書く。**

### 「〜が無い世界」は、明示して作る

試験のために「その宣言が無い状態」を作るとき、**土台に書かれていないことを当てに
しない**。土台が変われば、その試験は黙って別のものを見はじめる。

市場町のシナリオに属性の宣言を足したら、「宣言の無い世界」を作っているつもりの
試験が 2 件、**宣言済みの世界を見ていた**。どちらも上書きしないことを「無い」と
読み替えていた。

```python
# 危ない: 土台に書かれていないことに賭けている
raw = json.loads(SCENARIO.read_text())
if attributes is not None:
    raw["player_attributes"] = attributes

# 明示する: 「無い」を自分で作る
raw = json.loads(SCENARIO.read_text())
raw.pop("player_attributes", None)
if attributes is not None:
    raw["player_attributes"] = attributes
```

このときは 2 件とも落ちて気づけたが、**落ちない側に転ぶ形が普通にある**。否定条件
(「〜が無い」「〜を宣言していない」) を土台任せで作った試験は、土台の変更で
静かに空振りへ変わる。分母の話と同じで、**見ているつもりの母集団を、自分で作る。**

### 穴を塞ぐ作業が、新しい穴を作る

10 件のうち 3 件は、**その PR で新しく書いた検査**が空振りしていた。ラチェットを
広げる PR で広げた部分が空振りし、「1 度だけ書く」PR の中で重複を作っていた。

**直している最中がいちばん危ない。** 直したものは必ず変異で確かめる。

## 結果を見て止まり、一次情報に当たらない

1 日で 3 回。しかもうち 2 回は、**受け取った側にも伝播した**。

- 起動時エラーを読んで「落とせない」と報告 → 実は落とせて、場所が違うだけだった
- 「58 件緑」から「検査の範囲外」と結論 → 実は範囲内で、粒度が違うだけだった

**報告の連鎖では、一次情報から遠ざかる。** 受け取った側は、報告を根拠にさらに
一般化する。誤りはそこで増幅される。

**対策**: 「〜だと分かった」と書くときは、**何を見て言っているかを 1 行添える**。

- **(実行して確認)** — テストや probe を走らせた
- **(コードを読んで確認)** — 実装を読んだ
- **(結果だけ見た)** — エラーや出力から推測した ← **要注意の印**

根拠の距離が見えれば、受け取る側が確かめるかどうかを判断できる。

## 自分の報告する数字にも、分母が要る

「全 15,418 件 passed」と報告し続けていたが、**`quality` マーカーは通常の pytest から
除外されている**。prompt を変えた PR がその検査で落ち、main を赤くした。

**数字だけを見せると、範囲を確かめずに信じてしまう。** trace の分析で「分子だけ見て
起きなかったと読む」を何度も戒めておきながら、**自分の報告で同じことをしていた**。

**対策**: 何を回したかを書く。「全 15,418 件 passed (**quality を除く**)」。

## 位置が意味を持つ編集では、位置も意味で指す

自動編集で**挿入先を文字列で探し、別の場所に着弾**することが 4 回あった。

対策を 2 段階で更新している。

1. 「その文字列が何箇所あるか数える」→ **回数は合っていて、その 1 箇所が何であるかを
   見ていなかった** (メソッド定義を目印にして、クラス本体を割った)
2. 「**何の中か**を確かめる」→ AST で着弾先を確認する。**4 回目で初めて、テストを
   走らせる前に気づけた**

いまは、クラスや関数の**行番号を AST から取って**そこへ挿入している。文字列で位置を
探すのをやめた。
