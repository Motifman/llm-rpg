## D2229-2. Being の入口では、いるかどうかの判断を保存先に任せる

**何を**: 遊びの進行 (#2229) が Being を外から呼べるよう、Being の application に入口を 3 つ足した (`PrepareBeing`・`EnterEnvironment`・`PerceiveObservation`)。そのとき、Being がもういるか・いないかで分かれる処理を、ユースケースではなく保存先 (`being/domain` の `BeingRepository`) に置いた。

| 場面 | 決まり | 置き場所 |
|---|---|---|
| 用意する Being がもういる | 何も変えない。シナリオの人柄で書き換えない | `BeingRepository.add_if_absent` |
| 入れる Being がいない | `BeingNotFoundException` で断る | `BeingRepository.get` |
| 自分を紹介する取り決め | `BeingIntroducedToItselfException` で断る | `Being.enter` |

「もういる Being の人柄を書き換えない」は、同じ `BeingId` ならもういる Being と同じ主体で、人柄は Being が世界をまたいで持つ (D1928-3) という規則。どの Being がいるかを知っているのは保存先なので、「いなければ足す」を保存先の約束にした。ユースケースは Being を読み出して比べず、頼むだけにする。

例: ゲンを snapshot から戻して次の世界に入れるとき、次のシナリオに「一人称: 俺」と書いてあっても、戻したゲンの「わし」のまま入る。

保存先の型は、古い `domain/being/repository/BeingRepository` と同じ名前で `being/domain` に Protocol として置いた。古い型は being から import できない (境界の外) ため。古い型と、その `find_by_id` の呼び出し元は変えていない。古い型は #1469 の移し替えで消える予定なので、同じ名前の型が 2 つあるのはそれまでになる。

**採らなかった案**:

- ユースケースで `find_by_id` の結果が None かを見て分ける: ドメインの規則 (同じ ID は同じ主体) が application の分岐に出る
- `Being` 集約に「人柄を足し直す」操作を置き、同じなら何もしない: 人柄を比べるために Being を読み出すことになり、比べ方 (欄ごとか、全部か) という要らない決まりが増える
