## 見逃しと補強

- 置換拒否は空状態しか用意せず、検証前に状態を消す誤りを見逃していた。
  空の元入力を残し、非空状態の拒否後保持を追加する
- マージ拒否は不正な1項目だけだった。有効な更新・追加の後に不正な値や
  キーがある入力も用意し、部分更新が残らないことを検査する
- 真偽値 `True` は整数 `1` と等値なので、辞書の値比較だけでは型変換を
  見逃す。元の5値の比較を残し、型も確認する
- 資源の併存は満タンHP・所持金0だけで、MPは検査していなかった。
  元のHP100・MP50・金額0を残し、HP63・MP17・金額41の行を追加する。
  HP・MPは現在値と最大値、金額は値を検査する

拒否前の状態は `dict(status.state)` に取り、後の変更と別の辞書にする。
有効項目を先に置いた入力は部分反映の誤りを見せるためのもので、
製品の処理順や辞書の走査方法を契約にはしない。
値拒否の入力は全キーが文字列、キー拒否の入力は全値が有効な基本型なので、
別の入力検証に隠れない。

を呼び、変更前後を観測情報にする。`RECORD_PLAYER_STATE_TICK` も同じ入口へ書く。

- `test_player_state_app_integration.py` の4宣言は実アプリ入口と保存接続を所有し、そのまま残す
- HP・MP・Stamina単体の78件は資源の計算・上限・不変性を所有し、そのまま残す

資源値の既PR #1674、所持品 #1699、ショップ #1673、備蓄条件 #1688の
試験や公開案は変更しない。所持品は今回の自由状態の更新処理に接続していない。

## 検証結果

Python 3.10.22、pytest 8.4.1、固定依存を使用。対象作業木の `src` の読込を
確認し、資格情報を外し、外向き通信を遮断した実行環境で逐次検証した。
実LLMや実サービスは呼ばない。

- 未編集基準：対象12件、関連86件が成功。交差0、一意98件
- 候補：元12宣言を保持し、入力表4行追加によって16件が成功
- 改善6変異：旧12件はすべて成功し、候補は狙った検査で失敗
- 保持7変異：旧版・候補ともに元の契約違反を検出
- 旧新合わせた26実行に準備・後始末の失敗なし
- 各実行は未使用のバイトコード保存先を使用し、変異後は元の製品と候補へ復元
- 製品1601個のPythonファイルの全バイト一致を確認
- 最終：対象16件＋関連86件＝一意102件が成功
- Ruff 0.16.8と差分の空白検査が成功

改善の内訳は、置換の検証前消去、逐次検証による部分マージ、真偽値の整数化、
状態更新後のHP満タン化、MP満タン化、金額0化。部分マージの1変異は、
不正値と不正キーの追加2行だけで拒否後保持の検査が失敗した。

保持の内訳は、非空既定値、初期状態の喪失、防御コピーの撤去、置換のマージ化、
マージの全置換化、構築検証の撤去、空腹更新による状態消去。
これは実在する不具合を修理した結果ではなく、試験の検出力を測る対照である。

試験は143→185行（追加63・削除21）。製品と共有補助の増減は0。
高速化や全リポジトリの成功は主張しない。公開する正確な先端のCIは別途確認する。
