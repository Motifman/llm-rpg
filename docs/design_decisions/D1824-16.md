## D1824-16. 非同期のハンドラの失敗を、run の報告と fuzz に数える

**何を**: 非同期のハンドラの失敗 (trace の `async_event_delivery_failed`) を、次の 2 か所で数える。今は `world_runtime.py` が trace に残すだけで、どちらにも数えていなかった。

| 場所 | 出すもの |
|---|---|
| run の報告 (`report.md` の冒頭の要約、`run_end` の要約、コンソールの `[done]` の行) | 件数の合計と、理由ごとの内訳。0 件なら 0 件、数えられない実行環境なら「未計測」と出す |
| fuzz (`scripts/fuzz_scenario_with_random_agents.py`) | 理由ごとの件数をシードの行に出す (`async_failures=handler_failed:1` の形)。そのうち次の表の理由は、そのシードを失敗にする findings (`exception`。fuzz のスクリプトは、これを「穴」と呼ぶ) にする |

| 理由 | fuzz の findings にするか | なぜ |
|---|---|---|
| `prepare_failed` / `handler_failed` / `application_failed` | する | `prepare`・`handle`・`apply` のどれかが例外を出した。いきさつやエピソードが書かれないか、記憶に入らない |
| `capacity` | する | 結果を反映していない仕事の数が上限 (`max_pending`) に届き、新しい仕事を受け付けなかった。run の途中で起き、記憶が欠ける。でたらめに行動するスタブで起きたなら、別のスレッドで動く処理が追いつかない形がどこかにある |
| `shutdown` / `shutdown_timeout` | しない (件数だけ出す) | run を終えるときに終わらなかったもの。記憶が欠けることはあるが、run の途中で壊れたのではない |

件数は実行環境 (`WorldRuntime.async_event_delivery_failure_counts`) が、失敗を知らされるたびに数える。

- trace の recorder が無くて記録で例外になる run でも数える (記録の前に数える)
- 失敗は別のスレッドからも知らされるので、件数の加算はロックで囲む。fuzz の件数も同じ

**なぜ**: 非同期のハンドラの失敗は、どの段でも `async_event_delivery_failed` の 1 種類に残す (design_decisions D1824-15)。同期のハンドラの失敗 (`world_tick_unit_failed`) とは残る trace の種類が違うので、報告と fuzz の両方で数えないと、読む側は片方だけを見て失敗を見落とす。今の非同期の配送 (今のいきさつを書く処理) の失敗も、これまでは報告にも fuzz にも出ていなかった (静かな失敗)。

**関連**: Issue #1824、design_decisions D1558、D1824-15。
