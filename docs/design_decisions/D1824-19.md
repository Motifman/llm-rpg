## D1824-19. 範囲が埋まったら、非同期のハンドラがその範囲のエピソードを書き、記憶に加える

**何を**: 短期記憶の範囲が埋まったとき (`ShortTermMemoryRangeFilledEvent`) に、その範囲のエピソードを書き起こすハンドラを足す。形はいきさつ (design_decisions D1824-18) と同じ。

| 種類 | 名前 | 置き場所 | すること |
|---|---|---|---|
| 非同期のハンドラ | `WriteEpisodesHandler` | `being/application/handlers/` | 範囲が埋まった (`ShortTermMemoryRangeFilledEvent`) だけを受ける |
| コマンドとユースケース | `WriteEpisodesCommand` / `WriteEpisodes` | `being/application/write_episodes.py` | まとめる出来事を【直近の出来事】と同じ行にして、エピソードの中身を書く (LLM を呼ぶ)。行にならない範囲は書き手を呼ばない |
| コマンドとユースケース | `AddEpisodesToMemoryCommand` / `AddEpisodesToMemory` (今あるもの) | `being/application/episode_writing.py` | 中身に ID と呼び名を付けて記憶に加える。メソッドの名前は `add` のまま、引数をコマンド 1 つにした |
| ドメインイベント | `EpisodeWrittenEvent` | `being/domain/episode.py` | `Episode.write` が、書いたことをためる |
| 同期のハンドラ | `RecordEpisodeWrittenTraceHandler` | `application/being/handlers/` | 書いたエピソードを、エピソードごとに trace `being_episode_written` に残す |

`WriteEpisodesHandler` の 3 つの段:

| 段 | 動くスレッド | すること |
|---|---|---|
| `prepare` | ターンを進めるスレッド | 本人の名前と人格の文と、いま居る環境の名前を引き、まとめる出来事・範囲が埋まったターンとともに `WriteEpisodesCommand` を作る |
| `handle` | 裏のスレッド | `WriteEpisodes` を呼び、書いた中身を `AddEpisodesToMemoryCommand` にして返す |
| `apply` | その Being のターンの始め | `AddEpisodesToMemory.add` を呼ぶ |

- いきさつが遅れている (`ShortTermMemoryBackstoryOverdueEvent`) ときは受けない。同じ範囲のエピソードを 2 回書かない (design_decisions D1824-11)
- 書けなかったとき (LLM の失敗、応答の崩れ) は書き直さない。`handler_failed` として `async_event_delivery_failed` に残り、その範囲のエピソードは無いままになる。今の書き起こしも失敗を残して書き直さないのと同じ
- 本人の名前と人格の文と環境は、Being の `Persona` に移すまで (#1469)、ゲームの側がプレイヤーを走査して引く関数を渡す。引けなければ `prepare_failed` に残る
- `EpisodeWrittenEvent` は、今の書き起こし (今の短期記憶を畳むとき、環境を離れるとき) で書いたエピソードでも出る。どちらの経路でも `being_episode_written` が残る
- 行があるかどうかは、出来事を行にする側の `experience_lines` (行が無ければ None) で問う。「（直近の出来事はありません）」の文と比べない

**trace に残らないもの (残る穴)**: 新しい経路 (範囲が埋まったとき) では、次の 2 つが trace に残らない。

- 書いたエピソードが 0 件だったこと
- 切り詰めた項目と、捨てた件数

切り詰めた項目と捨てた件数は、書いたときの中身 (`EpisodeContent`) にしか無く、エピソードの集約は持たないため。今の書き起こしの経路の trace `episode_writing` (1 回の書き起こしごと) は、その経路を消すまでそのまま残す。欄の意味を途中で変えると、過去の run と比べられなくなるため。run で見えるようにする方法は、`end_turn` を配線する前に決める。書き手の失敗は `async_event_delivery_failed` に残るので、静かな失敗にはならない。

**なぜ**: 今の短期記憶を畳むときの書き起こしは、`end_turn` を配線するときにやめる。その前に、範囲が埋まったときに書き起こす経路を、CLAUDE.md の「コマンド・ユースケース・ドメインイベント・ハンドラ」の形で用意する。trace に残すことは、ドメインイベント (エピソードを書いた) を受ける別のハンドラにする。いきさつと同じく、書く処理が trace のことを知らずに済む。登録の側でハンドラを包んで trace を残す案は、ハンドラの外にもう 1 段の処理ができるので退けた。

**まだしないこと**: `end_turn` はまだ誰も呼ばないので、run ではこの経路は動かない。
