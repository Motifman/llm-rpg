# ギルド金庫の残高と通知の契約監査

## 目的と範囲

ギルド金庫の拒否試験は例外だけを確認し、拒否時に残高が変わったり、
未発行の通知が失われたりしても見逃していた。成功試験にも通知の対象ギルドを
検証する箇所がなく、常に同じギルドへ通知する誤りを検出できなかった。

対象は `tests/domain/guild/aggregate/test_guild_bank_aggregate.py` の全11宣言。
所有者は `GuildBankAggregate`。製品、例外型、通知型、所属集約は変更しない。

基準は `ba942f5a9cad4b6d362c9e2ce59566cc8ce3396f`。
基準試験は11件すべて成功しており、今回の変更は既存実装の不具合修正ではなく、
将来の退行を見逃す検証不足の修復である。

## 全宣言の判断

Rは保持、Fは契約を保持して検証を修復する判断。Cは統合、Dは削除を表す。
今回は R=3、F=8、C=0、D=0。全11宣言を保持する。

以下の宣言名はすべて対象ファイルの `TestGuildBankAggregate` 配下にある。

| 元の宣言 | 判断 | 保護する契約と対応 |
| --- | --- | --- |
| `TestCreateForGuild::test_create_for_guild_success` | R | 指定ギルド、初期残高0、公開される残高が `Gold` であることを保持する |
| `TestDepositGold::test_deposit_gold_success` | F | 入金100後の残高と通知1件、数量・入金者を保持し、通知の対象ギルドを追加検証する |
| `TestDepositGold::test_deposit_gold_multiple_times` | R | 50に30を追加して80になる累積契約を保持する。単発入金では上書きの誤りを検出できない |
| `TestDepositGold::test_deposit_gold_zero_amount_raises` | F | 0入金の例外と診断を保持し、残高・既存通知の保存を追加検証する |
| `TestDepositGold::test_deposit_gold_negative_amount_raises` | F | -1入金の例外と診断を保持し、残高・既存通知の保存を追加検証する。0とは別の境界 |
| `TestWithdrawGold::test_withdraw_gold_success` | F | 200から50出金して150となること、通知1件、数量・出金者を保持し、対象ギルドを追加検証する |
| `TestWithdrawGold::test_withdraw_gold_all_balance` | R | 残高100から100出金できる等値境界を保持する。部分出金で代替しない |
| `TestWithdrawGold::test_withdraw_gold_insufficient_balance_raises` | F | 残高50から100出金する既存入力、専用例外、現在額と要求額の診断を保持し、残高・通知保存を追加する |
| `TestWithdrawGold::test_withdraw_gold_zero_balance_raises` | F | 新規残高0から1出金する既存入力を保持し、取引後の残高0も追加して通知保存を検証する |
| `TestWithdrawGold::test_withdraw_gold_zero_amount_raises` | F | 残高100で0出金する既存入力・例外・診断を保持し、残高・入金通知の保存を追加する |
| `TestWithdrawGold::test_withdraw_gold_negative_amount_raises` | F | 残高100で-1出金する既存入力・例外・診断を保持し、残高・入金通知の保存を追加する |

## 入力の保存と追加

宣言を増やさず、既存宣言の表に次の5例を追加する。元の11例を新しい入力で
置き換えない。変更後は11宣言、16実行例になる。

- 成功2宣言: 元の `GuildId(1)` に `GuildId(17)` を追加する。
  共有の識別子fixture全体は展開せず、この2宣言だけを対象にする
- 入金拒否2宣言: 元の新規残高0・空通知に、正常入金100後の行を追加する
- 残高0の出金拒否: 元の新規金庫に、正常入金50→全額出金50後の行を追加する。
  後者は入金・出金の未発行通知2件を持つ

拒否前後で比較するのは公開されている残高と通知列である。`Gold` と通知は
不変値で、`get_events()` はリストのコピーを返す。比較元が操作後の状態へ
追従してしまう問題はない。通知は正常な公開操作で生成し、試験用の手作り通知や
非公開属性への代入は使わない。

## 保持する層と代替できない理由

金庫の残高計算、数量境界、通知生成、拒否後不変性は集約試験を主な所有者とする。
退役するファイルや、削除できる試験専用の製品口はない。

- `tests/application/guild/services/test_guild_command_service.py` は権限、
  金庫保存、プレイヤー側の金額操作との接続を保護する。サービスは数量0以下と
  残高不足を集約の呼出し前に拒否するため、集約の拒否分岐を代替検証できない
- `tests/infrastructure/repository/test_sqlite_guild_bank_repository.py` は
  残高の保存・復元を保護する。通知生成や拒否処理の証明ではない
- インメモリの保存処理は通知を UnitOfWork へ回収し、複製の通知を消す。
  保存後の金庫を読むだけでは、操作直後の通知列の保存を確認できない
- ギルドの観測文・配信先の試験は通知を直接作るため、集約が通知へ設定した
  `aggregate_id` の誤りを検出しない。配信先はこの識別子でギルドのメンバーを
  取得し、観測文も同じ値を利用する

## 既存仕様を保持する理由

金庫は [導入時の変更](https://github.com/Motifman/llm-rpg/commit/931ca4834dfffce71456b419f8dfd26f9d3d1bf4)
で0以下の入出金額に `ValueError` を使っていた。
[残高を Gold へ移行した変更](https://github.com/Motifman/llm-rpg/commit/40ef94a05c43a805b054e26445e50b31593262c8)
で現在の11試験が追加され、その例外も維持されている。

この例外型は現在の一般的なドメイン例外規約とは一致しないが、今回の監査で
製品や期待例外を変更する根拠にはしない。通常のサービス経路では数量0以下を
先に `GuildCommandException` で拒否する。例外体系の整理は別件として扱う。

`Gold` 型の確認はこの移行契約を保護しており、単なる実装の写経として削除しない。

## 検証結果

既存の依存環境で通信を遮断した pytest を実行し、対象作業木の製品を読み込むことを
確認した。以下の標準コマンドと同じ試験対象を使っている。

```sh
uv run --frozen pytest tests/domain/guild/aggregate/test_guild_bank_aggregate.py
uv run --frozen pytest tests/domain/guild \
  tests/application/guild/services/test_guild_command_service.py \
  tests/infrastructure/repository/test_sqlite_guild_bank_repository.py
```

| 段階 | 対象 | 結果 |
| --- | --- | --- |
| 変更前 | 金庫集約 | 11件成功 |
| 変更前 | ギルド領域・サービス・SQLite保存 | 71件成功 |
| 修復後 | 金庫集約 | 16件成功 |
| 意図的な製品変更からの復元後 | 金庫集約 | 16件成功 |
| 最終 | ギルド領域・サービス・SQLite保存 | 76件成功 |

関連71件には変更前の対象11件、関連76件には変更後の対象16件を含む。
それぞれを足して独立した被覆として数えない。すべて失敗・収集例外・省略は0件。
変更対象の Ruff と `git diff --check` も成功した。全体試験はローカルでは実行していない。

### 意図的な製品変更による旧新対照

同じ製品変更を元の11試験と修復後の16例へ適用した。8種類すべてで元の試験は
11件成功し、修復後だけが次の検査で失敗した。

| 意図的な製品変更 | 旧試験 | 修復後の失敗数 | 失敗した検査 |
| --- | --- | --- | --- |
| 入金通知の対象ギルドを1に固定 | 11件成功 | 1 | 通知の対象ギルド |
| 出金通知の対象ギルドを1に固定 | 11件成功 | 1 | 通知の対象ギルド |
| 入金数量の拒否前に通知を消去 | 11件成功 | 2 | 通知列の保存 |
| 入金数量の拒否前に残高を1増加 | 11件成功 | 4 | 残高の保存 |
| 出金数量の拒否前に通知を消去 | 11件成功 | 2 | 通知列の保存 |
| 出金数量の拒否前に残高を1増加 | 11件成功 | 2 | 残高の保存 |
| 残高不足の拒否前に通知を消去 | 11件成功 | 2 | 通知列の保存 |
| 残高不足の拒否前に残高を1増加 | 11件成功 | 3 | 残高の保存 |

残高不足の変更では、変更前の現在額・要求額で例外を作り、その後に残高を変更して
送出した。元の診断文字列の確認が別理由で失敗する形にはしていない。

すべての失敗位置を確認し、準備・収集・別例外による失敗を数えていない。
通知追加や通知順序変更の意図的な変更は実行しておらず、この表の実証範囲に含めない。

各確認後に製品と候補試験のバイト列を完全復元し、最後に通常の試験を再実行した。
製品の復元後SHA-256は
`173acdf20782316a49a788ffae2a99b41801d8c5473e984db7e34d8cfe7916e6`。
`uv.lock` も変更していない。
