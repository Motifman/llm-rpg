# 大型機能を Project と Issue で管理する

この文書は、大型機能を複数の Issue と PR に分け、複数の人間・AIエージェントが安全に進めるための共通ルールを定める。

運用例として [3D観察クライアントと非同期世界基盤](https://github.com/users/Motifman/projects/1) を参照できる。

## 基本単位

- **Project**: 一つの大型機能の進捗と優先順位を管理する。別の大型機能を混ぜない。
- **大型 Issue**: なぜ作るか、最終的な体験、成功条件、非目標を保持する。実装単位にはしない。
- **子 Issue**: 原則として一つの PR で完了する振る舞いを保持する。
- **PR**: 一つの目的に対するコード、試験、必要な文書をまとめる。

Project は進捗、ラベルは Issue の意味、親子関係は機能の分解、依存関係は着手可否を表す。同じ情報を複数の場所で管理しない。

## ラベル

ラベルは少数の安定した分類だけに使う。進捗、優先度、規模は Project の項目で管理する。

### 種別

| ラベル | 用途 |
|---|---|
| `kind:epic` | 複数 Issue を束ねる大型機能 |
| `kind:design` | 契約・責務・選択肢を確定する設計作業 |
| `kind:task` | 原則として一つの PR で完了する実装 |
| `kind:experiment` | 仮説と条件を固定した実験 |

### 作業領域

`area:runtime`、`area:llm`、`area:intent`、`area:world-content`、`area:3d-client`、`area:observability` を必要な範囲だけ付ける。担当者を表すラベルとしては使わない。

### 着手条件

- `agent-ready`: 追加判断なしでAIエージェントが単独着手できる。
- `needs:decision`: 実装前に設計判断または利用者判断が必要である。

この二つは同時に付けない。

## 親子関係と依存関係

親子関係は「何の一部か」を表す。大型 Issue の子に、設計 Issue、実装 Issue、実験 Issue を置く。

依存関係は「先行 Issue が終わらなければ着手できない」ときだけ使う。単に先に行うと分かりやすい、同じ段階に属する、といった関係には使わない。依存を増やしすぎると並行作業できる Issue まで直列化される。

Issue 本文には検索しやすいように `Blocked by #123` を書き、GitHub の依存関係も設定する。依存が解消したら `実装可能` と `agent-ready` を見直す。

## Issue を切る基準

次の問いにすべて答えられる単位へ分ける。

1. 一文で「何ができるようになるか」を説明できるか。
2. 一つの公開入口から結果を確認できるか。
3. 一つの PR で試験と一緒に完了できるか。
4. 主な所有範囲を一人または一つのAIエージェントへ渡せるか。
5. 失敗時の理由を観測できるか。

複数の公開入口、独立した設計判断、DB変更と大規模なアプリケーション変更、機能追加と広いリファクタリングが同居する場合は分割する。

目安は 200〜400 行、10ファイル前後、30分でレビューできる大きさとする。ただし、行数を守るために同じ振る舞いのコードと試験を別 PR にしない。

## `agent-ready` の条件

AIエージェントへ渡す前に次を満たす。

- なぜ必要かと実現する振る舞いが具体的である。
- 親 Issue、依存 Issue、対象外が明記されている。
- 変更する層、バウンデッドコンテキスト、主要な公開入口が分かる。
- 関連する設計判断と守るべき不変条件が示されている。
- テストリストが一件ずつ Red → Green で進められる。
- 完了条件と検証コマンドが具体的である。
- 発火、効果判断の値、未発火理由の観測方法が定義されている。
- 並行作業中の別 Issue と所有ファイルが不用意に競合しない。

判断が残る場合は `needs:decision` を付け、先に設計 Issue を作る。AIエージェントに設計判断を暗黙に委ねない。

## Project の状態

| 状態 | 入口 | 出口 |
|---|---|---|
| 構想 | 問題や案が登録された | 決める問いと次の調査が明確 |
| 設計中 | 設計 Issue に着手した | 契約、成功条件、分割が確定 |
| 実装可能 | 依存が解消した | 担当者が着手した |
| 実装中 | 作業ブランチまたは下書き PR がある | 実装と必要な試験が揃った |
| レビュー中 | PR がレビュー可能 | 指摘が解消し、結合確認へ進める |
| 検証中 | 結合試験または実験を行う | 成功条件と観測性を満たした |
| 完了 | PR がマージされ、受け入れ確認済み | なし |
| 停止中 | 意思決定または外部条件待ち | 再開条件が満たされた |

Project の `Status` を更新するときは、Issue または PR に根拠が残る状態にする。「ほぼ完了」のような曖昧な状態は追加しない。

## 複数のAIエージェントで進める

1. 大型 Issue から、依存のない `agent-ready` な子 Issue を選ぶ。
2. Issue ごとに作業ツリーとブランチを分け、所有範囲を明示する。
3. 着手時に Project を `実装中` へ移し、下書き PR から親・依存 Issue を参照する。
4. 他の作業の変更を戻さず、競合を見つけたら Issue の分割か順序を見直す。
5. PR ごとに試験根拠と trace 観測性を記録する。
6. マージ後に子 Issue を完了し、大型 Issue の成功条件と残作業を更新する。

同じ大型 Issue を複数エージェントへそのまま渡さない。大型 Issue は調整の単位であり、実装の所有単位ではない。

## 完了の定義

子 Issue は、コードが書かれただけでは完了しない。

- 公開入口から期待する振る舞いを確認できる。
- 正常系だけでなく、境界値と失敗理由を試験できる。
- 静かな失敗を残さず、必要な trace と指標を確認できる。
- 新しい設計判断を該当文書へ記録している。
- PR が親 Issue と関連 Issue を参照している。
- Project の項目と親 Issue のチェックリストが実態に追従している。

大型 Issue は、すべての子 Issue が閉じただけで機械的に完了させない。最初に定めた利用者体験と成功条件を、結合経路または実験で確かめてから閉じる。
