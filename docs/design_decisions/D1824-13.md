## D1824-13. エピソードの書き起こしを、中身を書くことと記憶に加えることに分ける

**何を**: エピソードを書き起こす部品 (前の `being/application/episode_writing.py` の `EpisodeWriter`) を 3 つに分ける。

| 置き場所 | 持つもの |
|---|---|
| `being/domain/episode_writer.py` | インタフェース `EpisodeWriter`。範囲の出来事の文から、LLM が書いたエピソードの中身 (`EpisodeContent`。目次と本文と切り詰めた項目。ID も呼び名も持たない) を返す |
| `being/infrastructure/llm_episode_writer.py` | `LlmEpisodeWriter`。指示の文面、LLM を呼び出すインタフェース (`EpisodeWritingCompletion`)、応答の読み取りと切り詰め |
| `being/application/episode_writing.py` | `AddEpisodesToMemory`。中身に ID と、その Being の中で重ならない呼び名を付け、エピソードとして記憶に加える |

今の畳むときと環境を離れるときの書き起こし (`PlayerEpisodeWriting`) は、この 2 つを続けて呼ぶ。文面、読み取りの決まり、trace (`episode_writing`) は変えない。

**なぜ**:

- インタフェースをドメインに、文面と呼び出しと読み取りをインフラに置くのは、#1824 の設計 (ドメインの外に置くもの) のとおり。いきさつ (design_decisions D1824-12) と同じ形にそろえる
- 次の PR で、短期記憶が古いターンのいきさつを頼むとき (`FoldRequested`) に、エピソードも裏のスレッドで書き起こす。中身を書くのは裏のスレッド、記憶に加えるのはターンを進めるスレッドにする (design_decisions D1837 の 4)
  - 呼び名を決めるのに Being の保存先を読むので、記憶に加える側に置く。裏のスレッドで保存先を読むと、ターンを進めるスレッドの書き込みと重なる (D1824-12 のレビューで見つかったのと同じ形)

**名前**: LLM が書いたものは `EpisodeContent` (中身) と呼ぶ。「下書き」はあとで直す含みがあるが、実際はそのままエピソードの中身になる。記憶に加える部品は `AddEpisodesToMemory` と呼ぶ。`Keeper` では何をするかが読めず、「保存」と呼ぶと保存先の操作に見えるため。

**インタフェースが出来事の文を受け取ること**: いきさつのインタフェース (`BackstoryWriter`) は出来事 (`Experience`) を受け取るが、このインタフェースは描いたあとの文を受け取る。今の書き起こしは、今の短期記憶の出来事 (Being の型ではない) から書くため。3b で今の短期記憶をやめるときに、出来事を受け取る形にそろえるかを決める。

**その後 (design_decisions D1824-17)**: 上の「次の PR」で受けるイベントの名前は、`FoldRequested` から `ShortTermMemoryRangeFilledEvent` (範囲が埋まった) に変わった。

**関連**: Issue #1824、design_decisions D1626、D1824-12、D1837。
