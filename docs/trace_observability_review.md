# trace 観測性レビュー

この文書は、新しい実験機能を追加するときに「実験後にその機能が測れるか」を確認するためのレビュー観点です。実験設定の仕様ではなく、Claude Code / Codex などのコーディングエージェントに差分レビューさせるための作業メモです。

## 目的

実 LLM run は費用と時間がかかるため、機能を追加したあとに「trace を見ても効果を測れない」と分かる手戻りを避けます。

ここで守りたいのは、すべての機能に大きな計測基盤を足すことではありません。新機能が実験上の観察対象になるなら、その発火・入力・出力・失敗が trace から最低限たどれる状態にしてから run します。

## レビューの入口

次の変更を含む PR では、この文書を参照して観測性を確認します。

- エージェントの判断、記憶、目的、信念、想起、推論、行動選択に影響する変更
- 実験 profile から切り替える機能の追加
- trace 分析で見たい指標を増やす変更
- 既存 trace イベントの意味や payload を変える変更
- **エージェントへ届く観測を足す・変える変更** (新しいドメインイベント、配信先の規則、観測文)

UI 文言修正、ドキュメント修正、明らかに実験挙動へ影響しない内部整理では不要です。

## 確認すること

新しい実験機能を追加したら、PR 作成前に次を確認します。

- その機能が発火したことを trace から分かるか
- 効果判断に必要な値が trace payload に入っているか
- 機能が発火しなかった場合に、設定ミスなのか条件未成立なのかを trace から区別できるか
- 内部 metrics に届いた値が、必要なら trace へ転記されているか
- trace に出す値の粒度が、実験後の分析で使える粒度になっているか
- 観測点が増えたことを保証するテストがあるか
- エージェントへ届く観測を足したなら、発火・配信・表示の 3 点が揃っているか (後述)

## エージェントへ届く観測: 発火 → 配信 → 表示

trace は「観察する側 (人間) が見えるか」で、ここは「**世界の中の誰かが見えるか**」です。前者が出ていても後者が黙って落ちていることがあり、しかもその失敗は run が終わるまで気付けません。

新しい出来事をエージェントへ届けるときは、次の **3 点が揃っているか**を確認します。1 つでも欠けると、書いたつもりの観測が誰にも届きません。

| 点 | 何をするか | 欠けると |
|---|---|---|
| **発火** | ドメインイベントを実際に publish する | 何も起きない。他の 2 点が完璧でも届かない |
| **配信** | recipient strategy が「誰に届くか」を決める | 届く人が居ない / 届いてはいけない人に届く |
| **表示** | formatter が観測文と `schedules_turn` を決める | 文面が空、または手番の起き方が意図と違う |

**3 点は別のファイルにあるので、揃っているかを構造で検出できません。** 経済統合 Phase 2 では formatter・recipient strategy・observed_event_registry を全部書いたのに、executor からの publish だけが無く、交渉が誰にも見えない状態でマージ直前まで気付きませんでした。

配信を決めたら、**誰に届かないか**も同時に決めます。「その場の第三者に見せる/見せない」「当事者だけ」は世界の質感そのもので、既定に倒すと決めていないことになります。

### 書かれているコードは、繋がっているとは限らない

**この 3 点検査は新機能のためだけではありません。** 既存コードにも、表示と配信
だけがあって発火が無い箇所が実在しました。

所持品の**溢れ** (持ちきれない品を受け取ったとき) がそれです。集約は
`InventorySlotOverflowEvent` を作り、formatter には文面があり、recipient
strategy にも「本人だけに届ける」規則がありました。**発火だけが無く**、所持品
集約のイベントを publish する経路はどこにもありませんでした。結果、品は黙って
消え、結果メッセージにも観測にも trace にも残りませんでした。実 run では、
ある人が「乾いた流木を一本拾い上げた」で 36 回成功しながら手放したのは 6 回で、
20 枠に収まっていません。本人は「十八本ある」と信じたまま拾い続けていました。

さらにもう一段ありました。溢れた品を地面へ落とす `InventoryOverflowDropHandler`
も**書かれていました**。ところがそれが書き込む先は `PhysicalMap` — 既に外した
タイルマップ世界で、いまの runtime には `physical_map_repository` すら配線されて
いません。「配線すれば動く」と読んで手を付けると、**存在しない世界へ繋ごうと
する**ことになります。

- **対処コードが書かれていることは、繋がっていることを意味しない。**
- **繋がっていないコードは、繋ぐ先が今も存在するとは限らない。**

デッドコードを見つけて「配線すれば動く」と判断する前に、**繋ぐ先の世界がまだ
あるか**を確かめてください。

`schedules_turn` は**受け取る人ごとに**決めます。イベントの種類だけで決めると、見えるだけでよい第三者まで手番が起きます。同席者全員が動くと行動密度が跳ね上がり、しかも起こされた側には打つ手がありません。

## レビューで聞く質問

Claude Code / Codex に差分レビューさせるときは、次の観点で見てもらいます。

```text
この PR を trace 観測性の観点でレビューしてください。
新しい実験機能、または既存実験機能の挙動変更がある場合、
その機能が発火したこと、効果判断に必要な値、失敗や未発火の理由が
trace から確認できるかを見てください。

エージェントへ届く観測 (ドメインイベント / 配信先 / 観測文) を
足すか変える差分がある場合は、発火 (publish している)・配信
(recipient strategy がある)・表示 (formatter と schedules_turn) の
3 点が揃っているかを、それぞれ実際のコードで確認してください。
3 点は別ファイルにあるので、揃っていなくても import は通ります。

観測のテストが「プロンプト全文に文字列が含まれるか」で書かれていたら
指摘してください。同席者の名前や品名は別の節からも出るため、観測が
1 件も届いていなくても緑になります。

不足がある場合は、どのファイルにどの trace イベントまたは payload を
追加すべきか、どのテストで守るべきかを指摘してください。
実験挙動に関係しない変更なら「観測性レビュー対象外」と明記してください。
```

## テストの考え方

単体テストでは、内部状態だけでなく観測の出口も確認します。

- buffer や store に入るだけでなく、対応する trace イベントが出ること
- 機能フラグや profile の組合せで、機能が黙って無効化されないこと
- metrics オブジェクトに入った値が、必要な trace payload に残ること
- 未発火が正常な条件分岐なら、その判断材料が trace から読めること

### 新しい観測を足したら、届いた観測そのものを見る

観測を足す PR では、**届いた観測を取り出して本文を見るテストを 1 件**書きます。

**プロンプト全文の部分文字列検査で代用しないでください。** プロンプトには同席者の名前も品名も場所名も別の節から出ているので、`"レナ" in prompt` や `"薬草" in prompt` は**観測が 1 件も届いていなくても成立します**。実際、Phase 2 の第三者観測テストはこの形で書かれていて、publish が丸ごと無い状態で緑でした。

```python
# NG: 観測ゼロでも緑になる
assert "レナ" in prompt_of(bystander)

# OK: 届いた観測の本文を見る
seen = " ".join(e.output.prose for e in drain_observations(bystander))
assert "レナ" in seen
```

同じ理由で、`schedules_turn` も**届いた観測のフラグ**を見ます。「起きるはず」の人と「起きないはず」の人を両方置くと、条件を受信者によらず返す実装で落ちます。第三者役を置けない世界では第三者観測を検証できないので、テスト用シナリオに 1 人足してでも置きます。

「届いていない」を検出するには**正の対照**が要ります。「観測に X が無い」だけを見るテストは、観測が 1 件も無くても緑になります。届くはずの観測が届いていることを先に確かめてから、届かないはずのものが無いことを見ます。

高コスト run を使って確認しません。まずは低コストの単体テスト、配線テスト、短い確認 run で確認します。

## やりすぎないための基準

次のものは、この文書の目的ではありません。

- すべての機能に新しい trace イベントを強制すること
- すべての実験で厳密な比較対象を要求すること
- 研究段階の仮説ごとに設定仕様を増やすこと
- trace payload を将来使うかもしれない値で膨らませること

必要なのは、「この run が終わったあと、見たかったことを見られるか」を PR 時点で確認することです。
