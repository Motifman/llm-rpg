# モンスター集約の二重収集を除く

## なぜ

`TestMonsterAggregateBehaviorState` は共通の準備を使うため、試験クラス
`TestMonsterAggregate` を継承していた。そのため、親の88試験も子の名前で
再収集されていた。独立した108宣言に対し、同じ入力の196件が走っていた。

この変更は、試験を含まない `MonsterAggregateFixtures` を共通基底にし、
既存の2試験クラスを兄弟にする。準備をコピーせず、同じ88試験の再実行だけを除く。

## 変える範囲

- 対象は `tests/domain/monster/aggregate/test_monster_aggregate.py` の継承構造
- 親の88宣言と子固有の20宣言、合計108宣言をすべて保持する
- 試験名、入力、検証内容、例外型を変えない
- 共通準備7個、成長段階の準備2個、子固有の準備1個の計10個を保持する
- 製品、共有補助、pytest設定、CI設定の変更はない
- 攻撃間隔・環境被害の既存監査PR #1696には触れない

## 二重実行と判断した根拠

親子88対は、同じ試験関数、同じ準備関数と依存関係、同じスコープを使う。
パラメータ化による実装や入力の切替はなく、別の永続化実装を試しているわけでもない。
子固有の `spawned_monster` は、親88件が使う準備を上書きしない。

pytest 8.4.1のクラス継承からの収集も確認した。試験を含まない共通基底を
`Test` で始まらない名前にすることで、準備の共有を維持しながら再収集を避ける。
親の試験を非収集にする方法は、正規の88件や子の収集まで落とす危険があるため採らない。

## 保存を確認したこと

- 全108宣言の抽象構文木を比較し、引数・装飾・本文が同一
- 全10準備関数の抽象構文木も同一。共通7個は所有クラスだけを移した
- 新しい収集列は、旧196件の収集列から記録済みの重複88件だけを除いた108件と、順序も含めて一致
- 残る108件の準備関数の解決と依存関係は、所有クラス名と行位置の変更を除いて同一
- モンスター領域全体の実行列も、旧版からその88件だけを除いたものと一致

削ったのは88回の重複実行であり、88宣言や88契約を削除したわけではない。

## 検査が効くことの確認

同じ製品の誤変更2種類を、旧版と変更後へそれぞれ一時適用した。

1. 被害通知の現在HPに1を加えると、親の `test_apply_damage_success` が両版で失敗
2. 移動意図通知の時刻に1を加えると、子固有の `test_record_move_success` が両版で失敗

いずれも狙った値の検証で失敗した。起動失敗や例外による代用ではない。
誤変更後は製品と変更後試験をバイト単位で復元し、下記の最終試験を実行した。
これらは試験の保存性を確かめるための誤変更であり、現行製品の不具合報告ではない。

対象作業木の製品コードが読み込まれていることを確認した。実LLMは使っていない。
