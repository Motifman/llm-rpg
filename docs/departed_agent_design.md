**C. 5 と 6 は「盤上に居て観測も届き投票もできるが、手番だけ回らない」。**

## 設計の骨子

### 概念 1: 存在の層 (plane)

Being が今どの層に居るか。ただし **plane は行動可否そのものではない。**
問いは分けて持つ (段階 2 で `PlayerLifeQuery` として導入済み)。

    can_take_turn                    いま手番を回してよいか
    can_receive_world_observation    世界の観測を届けてよいか
    can_vote                         投票母数に入るか
    has_reportable_body              通報・略奪の対象になる身体があるか

plane が答えるのは「**誰から誰が見えるか**」だけ。

### 概念 2: 知覚の行列

| 観測する側 ＼ される側 | 生者 | 去った者 |
|---|---|---|
| **生者** | ○ | **×** |
| **去った者** | ○ | ○ |

**「去った者は両方を知覚する」は全知ではない。** 既存の距離・照明・音の規則の
中で、対象の層を両方許すという意味に限定する。

置き場所は 1 つの policy にまとめ、**観測の配布 / 同席者行の構築 / 発話の到達**の
3 つが同じものを見る。actor の無い世界イベント (天候など) は層の対象外。

### 効果は共有、知覚は分離

```
幽霊が配線を締める  → task_wiring フラグが立つ    世界は 1 つ。共有される
その行為の観測       → 生者には届かない            知覚は層で切れる
```

**結果状態は共有し、実行者を示す観測だけ配らない。** 幽霊が変えた扉や物の状態は
生者にも見える。そうしないと共有世界と矛盾する。

勝利条件 `FLAGS_SET_AT_LEAST` は誰が立てたかを見ないので変更不要。

### 能力は interaction ごとに宣言する

`interact` は 1 つの tool なので、tool の露出制御だけでは「作業はできるが
ランタン取得・略奪・妨害はできない」を表せない。**シナリオ宣言側で interaction
ごとに実行できる層を持たせ、候補表示と実行拒否が同じ判定を使う。**
action name の hardcode はしない。

**表示から消すだけでは執行側の防御にならない** (CLAUDE.md の tool_exposure と
同じ教訓)。

## 死体と主体の分離 — D を採る

幽霊が動くと死体も動く。**死体の位置 = グラフ上の entity の位置**だったから。
段階 3 で位置の真実の源を分離したので、この前提は解けた。残るのは
**幽霊の位置をどこに置くか**である。

| 案 | 内容 | 状態 |
|---|---|---|
| A | 幽霊に別の `EntityId` を与える | **却下**。`entity.value == player_id` の前提がコード全域にある |
| B | 死体を実行時に作る world object にする | 物は静的宣言のみ。実行時生成の仕組みが無い |
| C | 幽霊が既存 entity でグラフ上を動く | 却下 (下記) |
| D | 幽霊の位置を別 store に持ち、物理グラフに入れない | **採用** |

### 私が撤回した主張

当初 C を推し、「変更は 9 関数に閉じる」と書いた。**これは誤り。**

私が洗ったのは「**死体を消費する側**」で、本当に問うべきだったのは
「**幽霊が物理世界に混ざる側**」だった。実例:

- `presence_at(...).present_entity_ids` の長さが `PLAYERS_AT_SPOT` に渡り、
  **幽霊が協力人数に数えられる**
- 照明の解決と現在状況の構築が presence を直接読む

**位置と生死の近接検索では、この種類は原理的に拾えない。** 監査の方法が
問いに合っていなかった。

### 費用を同じ尺度で数えた

    C が監査すべき面 (「そこに誰が居るか」を読む側)      53 件 / 18 ファイル
    D が差し替える面 (「自分はどこか」を引く側)          43 件 / 21 ファイル

**数では決まらない。** ほぼ同じ大きさである。

### C の「1 か所に畳む」は成立しない

在席が `SpotPresence` という値オブジェクトになっているので、そこで層を絞れば
1 か所で済むように見えた。**成立しない。**

`SpotPresence` は生の集合 (`present_entity_ids`) を公開する**入れ物**であって、
問い合わせの窓口ではない。53 か所はその集合を直接読んでいる。

- 構築時に絞ると、グラフ自体が幽霊を知らないことになる。**それは D である**
- 読み出し時に絞るには、53 か所を絞り込み付きの窓口へ通す改修が要る。
  **D と同じ大きさの作業に加えて、以後の規律が要る**

### 結論: D

費用が同じなら、**構造で保証される側を採る。**

    C  今後 presence を読むコードが増えるたびに、誰かが filter を思い出す
    D  幽霊はグラフに居ない。読む側は何も知らなくてよい

このプロジェクトが繰り返し踏んでいるのは前者の形 (任意の配線が忘れられる)。
段階 1 で見つけた snapshot の欠落も、段階 2 で分けた 3 つの門も、同じ形だった。

なお D で差し替えが要るのは 43 か所すべてではなく、**幽霊が通る経路だけ**
(移動 / 物への操作 / 現在状態 / 発話の到達 / 探索)。正確な部分集合は実装時に
数える。**ここを「N か所に閉じる」と先に書かない。** 同じ誤りを 2 度した。

- 立った作業フラグの数 (`world_flag_changed` で誰がいつ何を立てたか読める)
- `tighten_wiring` が 1 度でも成功するか (5 run 通して**試行すら** 0 回)

## 決めたこと (2026-08-09)

1. **幽霊のプロンプト。** user 側の現在状態に、毎回導出した短い文を置く。
   能力と非対称性を事実として書く。system prompt を状態遷移で書き換えると
   プレフィックスキャッシュが飛ぶので触らない
2. **範囲は DEAD だけ。** EJECTED はグラフから外れていて位置が無く、「どこに
   湧かせるか」の規則が別途要る。**後から広げる前提**で順序として先送りする
3. **知覚は既存の距離・照明・音の規則のまま。** 全知にしない

### なぜ全知にしないか

本家が幽霊に全部見せるのは**人間の待ち時間を退屈にしないため**で、その理由が
ここには無い。幽霊は生者に話せないので、知った事実を使う先も無い。

決め手は別にある。**観測には「体験した」と「観戦した」を区別する印が無い**
(区分は `self_only` / `social` / `environment` の 3 つだけ)。全知にすると死後に
見たものが生前と同じ資格でエピソード記憶へ入る。自己の連続性を壊すのは全知
そのものではなくこれである。

局所にすると**幽霊同士の発話が意味を持つ**。全知なら全員が同じことを知っている
ので相談する内容が無い。知覚の範囲と能力の選択はここで噛み合っている。

**後戻りの向きが違う。** 局所 → 全知は後から広げられるが、逆はできない。既に
書き込まれた記憶が snapshot に残る。

### この先の枠 (忘れないこと)

この人狼世界は最終形ではない。**AI キャラクターが暮らす広い世界があり、その住人が
一時的にゲームへ参加して終わったら戻る**、という入れ子にする構想がある。その枠だと
シナリオ内の死は死ではなく**そのラウンドからの脱落**で、`being` は世界を跨いで
永続するので主体は最初から死んでいない。幽霊は死者ではなく**観戦者**に近い。

面白くする余地は知覚の範囲ではなく**印の側**にある。観測に「これは観戦だった」を
つけられれば、範囲の選択は後戻りできる決定になり、外の世界で「見ていたが生きては
いなかった」という語りの資格の差も表せる。**いまは入れないが、知覚の配布を 1 つの
policy にまとめておけば、後から印を足す場所が 1 か所で済む。**
