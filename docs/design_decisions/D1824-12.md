## D1824-12. 短期記憶が頼んだいきさつは、裏で作り、その Being のターンの始めに入れる

**何を**: 短期記憶が「いきさつを頼む」イベント (`BackstoryAsked`。`FoldRequested` と `BackstoryRequestedAgain` の共通の型) を、イベント基盤の非同期の配送 (design_decisions D1837 の 4) で受けるハンドラ (`application/being/being_backstory_writing.py` の `BeingBackstoryWriting`) を足す。

| 置き場所 | 持つもの |
|---|---|
| `being/domain/backstory_writer.py` | インタフェース `BackstoryWriter`。頼まれた範囲の出来事と前のいきさつから、いきさつを 1 つ作る |
| `being/infrastructure/llm_backstory_writer.py` | `LlmBackstoryWriter`。LLM への指示の文面、呼び出し (無ツールの JSON 完了を渡して使う)、応答の読み取り |
| `application/being/being_backstory_writing.py` | ハンドラ。ターンを進めるスレッドで本人の名前と性格を引いておき (`note_person`)、裏のスレッドでいきさつを作るだけにし (`write`)、ターンを進めるスレッドで短期記憶に入れて保存する (`apply`) |

- 本人の名前と性格は、Being からプレイヤーを引くときに Being の保存先を走査するので、裏のスレッドでは引かない。保存して配送器に渡すとき (ターンを進めるスレッド) に、非同期のハンドラより先に登録した同期のハンドラ (`note_person`) が Being ごとに 1 度引いて覚える。run の中で人格は変わらない
  - 頼みごとを名前と性格を添えた別の値で包んで配送に渡す案は退けた。非同期の配送は、失敗を trace に残すときに配送したものをドメインイベントとして読む (`event_id`、型の名前)
- 指示の文面と読み取りの決まり (流れ 300 字、気分 120 字まで) は、今の短期記憶の【ここまでのいきさつ】の要約と同じ。文面が同じことは試験で見る。今の要約と違うのは次の 4 つ
  - 出来事の見出しは「【まとめる N 件の出来事 (古い → 新しい)】」で、ターン数を出さない。範囲はターンで決まり、出来事の無いターンもあるので、件数だけを出す
  - 出来事は【直近の出来事】と同じ行 (`experiences_text`) で、`recent()` と同じ順に並べる。今の要約は起きた時刻 (`occurred_at`) の順
  - まとめる出来事が無い範囲は、LLM を呼ばずに前のいきさつの流れと気分を引き継ぐ (前のいきさつも無ければ「出来事は無い」と書く)。今の要約は例外を投げる
  - 書けなかったとき (LLM の失敗、応答の崩れ) は、決まった文に縮退しない。ハンドラが例外を投げ、非同期の配送が `async_event_delivery_failed` に残す。頼みごとは残るので、短期記憶が頼み直す (D1824-11)
- 行を作る `experiences_text` は Being の表示の層 (`being/application`) にあり、インフラがそれを import する。層の向きは逆だが、【直近の出来事】と同じ行にそろえるためにこうしている。3b でプロンプトを Being の側に切り替えるときに置き場所を見直す
- いきさつを入れたら `being_backstory_written` を残す
- 実 LLM を呼ばない run では、まとめる範囲の最初の出来事を流れにするスタブ (`stub_backstory_completion`) を使う
- LLM の費用の記録は、今の要約と同じ部品の名前 (`AuxLlmComponent.SHORT_TERM_SUMMARY`) で残る

**なぜ**: インタフェースをドメインに、文面と呼び出しと読み取りをインフラに置くのは、#1824 の設計 (ドメインの外に置くもの) のとおり。書くのをターンを進めるスレッドに限るのは、短期記憶を書く人を 1 人に決めて、ロック無しで上書きを防ぐため (D1837 の 4)。

**まだしないこと**: 誰も `fold` を呼ばないので、run ではいきさつは作られない。エピソードの書き起こしのハンドラは次の PR。

**その後 (design_decisions D1824-17)**: 書けなかったとき、短期記憶は頼み直さない。いきさつを待ち続け、待ち始めてから 10 ターン経っても届かなければ、遅れていることをイベント (`ShortTermMemoryBackstoryOverdueEvent`) で知らせ、それを受けて書き直す。受けるイベントは、範囲が埋まったこと (`ShortTermMemoryRangeFilledEvent`) と、いきさつが遅れていること (`ShortTermMemoryBackstoryOverdueEvent`) の 2 つになった。同じか前の範囲までのいきさつは、短期記憶がドメイン例外で断るので、`apply` の失敗として `async_event_delivery_failed` に残る (`being_backstory_discarded` はもう出ない)。

**その後 (design_decisions D1824-18)**: ハンドラ `BeingBackstoryWriting` と `note_person` は消し、非同期のハンドラ `WriteBackstoryHandler` (`being/application/handlers/`) に置き換えた。本人の名前と性格は、`prepare` (ターンを進めるスレッドで動く) の中で引く。いきさつが入ったことの trace (`being_backstory_written`) は、短期記憶の `ShortTermMemoryBackstoryAddedEvent` を受けるハンドラ (`RecordBackstoryAddedTraceHandler`) が残す。

**その後 (いきさつの字数)**: run `mine_v1_010_end_turn` で、8 件中 1 件のいきさつの流れが 300 字で途中で切れたまま保存された。指示には「2-3 文」としかなく、字数の上限を伝えていなかった。指示に、流れ (`FLOW_MAX_CHARS`、300 字) と気分 (`MOOD_MAX_CHARS`、120 字) の上限と、超えた分は途中で切れることを、定数の数字で書いた。切り詰めた項目と切り詰める前の長さは、書いたいきさつと組 (`WrittenBackstory`) で返し、いきさつが入ったイベントに載せ、`being_backstory_written` の `truncated` に残す (エピソードの `truncated` と同じ形)。

- これで、指示の文は今の短期記憶の【ここまでのいきさつ】の要約 (`short_term_memory_summary_service.py`) と同じではなくなった。同じであることを見張っていた試験は外した。今の要約にも同じ 300 字の切り方があり、プロンプトに出ているのは、まだ今の要約の文 (切り替えは #1630)
- 今の要約の指示には字数を足さない。#1630 でプロンプトを新しい短期記憶に切り替えるときに、今の要約はやめるため (#1824 でユーザーと決めた)

**関連**: Issue #1824、design_decisions D1824-11、D1837。
