# 消費効果と腐敗計算の契約監査

## 範囲と基準

2026-10-14 の `main` (`ba942f5a9cad4b6d362c9e2ce59566cc8ce3396f`) を基準とする。
対象は `tests/domain/item/value_object/test_item_effect.py` と
`test_spoiled_consumption.py` の全33宣言。判断は **R25 / F7 / C1 / D0**。
Rは保持、Fは契約を残して検査を補強、Cは主試験へ元入力を移す統合、Dは削除を表す。

製品コード、共有補助、効果の値や適用順序は変更しない。
隣接する `ItemSpec`、`ItemAggregate`、`ItemInstance`、`StackingPlan` は本監査の変更対象ではない。

## 見つかった見逃しと修正

### 腐敗ダメージの期待値が製品定数へ追従していた

6試験は計算結果を同じ製品モジュールの `SPOILED_FOOD_DAMAGE_HP` と比較していた。
10を9へ変えると結果と期待値が一緒に変わり、6試験とも通る。
期待値を明示的な10とし、空腹回復量の0/17と元の全入力を保持した。

10 HPと空腹回復の半分切捨ては `docs/design_decisions.md` の120節にある決まりである。
[導入時の変更](https://github.com/Motifman/llm-rpg/commit/bae35304545fcecc7db70b470602b5fdf6f61456)
では118節だった。今回、新しい釣り合いの値を決めたわけではない。

### 書換拒否後の値を確かめていなかった

蘇生効果の不変性は `raises(Exception)` だけで検査されていた。
値を書き換えた後に例外を投げても、無関係な実行時例外を投げても通る。
`AttributeError` での拒否と、その後も `hp_rate == 0.4` であることを確認した。

Python3.10の `FrozenInstanceError` は `AttributeError` を継承する。
固有のdataclass例外、内部辞書、frozenフラグを固定せず、公開属性の書換拒否を検査する。

### 不正な複合子の検査基準を揃えた

文字列と整数の拒否は同じガードを別の宣言で検査していたが、整数側には位置の検査がなかった。
元の `invalid` と `1` を第2要素へ置く2入力をそのまま主試験の行に残し、
両方で例外型、効果型の違反、不正位置 `effects[1]` を確認する。
呼出回数や初期化回数は減らない。統合の価値は、拒否の検査基準が揃うことに限定する。

## 全宣言の判断

| 元の宣言群 | 宣言数 | 判断 | 保持する契約 |
|---|---:|---|---|
| Heal / RecoverMp / Gold / Exp の正量・0・負量 | 12 | R12 | 入力量の保持、0の許可、型ごとの負量拒否 |
| Composite のlist・空・tuple・None・文字列拒否・入れ子 | 6 | R6 | 入力形、空とNoneの区別、全要素の検証、木構造と順序の保持 |
| Composite の整数拒否 | 1 | C1 | 文字列拒否の主試験へ元入力を移し、同じ診断基準を適用 |
| ItemEffect 基底の直接生成拒否 | 1 | R1 | 実効果でない基底型を直接作れないこと |
| Revive の0.4・0・1・負率・1超 | 5 | R5 | 蘇生率の保持、両端の許容、範囲外拒否 |
| Revive の書換拒否 | 1 | F1 | 属性書換として拒否され、拒否後も元値を保つこと |
| 腐敗計算のNone・Heal・HUNGER35・FATIGUE・複合魚・HUNGER1 | 6 | F6 | 10 HP、型選別、半量切捨て、0への切捨て |
| 入れ子のHUNGER合算 | 1 | R1 | 入れ子内外の10+25を35とし、HealやFATIGUEを混ぜないこと |

単純な値の保持や構築時検証でも、独立した契約なら残した。
基底型の製品からの直接生成が0件であることは削除理由にしていない。
[#1387の変更](https://github.com/Motifman/llm-rpg/commit/7e6701095c85440cbf3f0dbc2e1f9486222f5f39)
は、抽象宣言を生成ガードへ変えた際に、この試験を仕様保持の根拠として明記している。

## 層ごとの所有者

- `item_effect.py`: 値の保持、構築時の許可・拒否、不変性。JSONの構築は `parse_economy.py`、保存復元はSQLite codecから呼ばれる
- `spoiled_consumption.py`: 腐敗の数値とHUNGER選別。適用は `SpotGraphToolExecutor` が行う
- `ConsumableEffectHandler`: HP/MP/金/経験値/欲求/蘇生/複合効果の適用。構築時の0や範囲外の検査とは別契約
- 実runtimeの `TestUseItemEndToEnd`: 消費と効果保存の取消し、確定後に状態を読む通知、腐敗ラベルの対象選別
- シナリオとSQLiteの試験: 形式変換・保存入口の契約。ドメインの小さな検査を置き換える根拠にはしない

入れ子HUNGERを35と確かめる主試験も保持した。最終的な半量17だけでは、
合計を誤って34にする退行を区別できない。単純な魚1個の上位試験は代替にならない。
退役ファイルや撤去可能な製品用の関数・試験用公開関数はない。

## 検証結果

- 未編集基準: 対象33件、対象を除く関連67件が成功。実行識別子の交差0
- 変更後対象33件が成功。宣言は33→32、実行ケースは33→33
- 改善4種で旧対象は全件成功、新対象は意図した検査で失敗
  - 10→9: 腐敗の6件が `9 == 10` で失敗
  - 書換後に属性例外: 不変性の1件が `0.5 == 0.4` で失敗
  - 無関係な実行時例外: 不変性の1件が期待した例外型と異なるため失敗
  - 整数だけ不正位置を0と報告: 整数行の1件が `effects[1]` の検査で失敗
- 保持対照6種を旧新双方で検出: 蘇生率の書換許可、空腹半量の切上げ、不正な第2要素の見逃し、基底型の生成許可、蘇生率0の拒否、蘇生率1の拒否
- 同じ変異を旧新それぞれに適用した全20実行で、失敗は試験本体の段階に限定。準備段階の失敗なし
- 変異用の独立作業木で製品2ファイル・試験2ファイルの完全復元をSHA-256と差分0で確認。候補の製品コードも基準と一致
- 復元後の対象33件＋関連67件、計100件が成功。ruff 0.16.8、`git diff --check` が成功

試験はPython3.10.22 / pytest8.4.1の固定依存環境で、APIの秘密情報を除去しネットワークを遮断して直列実行した。
各実行に未使用のバイトコードキャッシュ先を割り当て、既存キャッシュを読む取り違えも防いだ。
全リポジトリ試験と公開commitのCIは、この局所検証とは別に確認する。

## 変更量と限界

対象試験286→280行、追加14行・削除20行。製品・共有補助の増減0。
削除量や速度改善を目的とせず、元入力を残して検出力を補強した。
