# 空間グラフの経路試験の責任分担

## 対象と判断

基準は `ba942f5a9cad4b6d362c9e2ce59566cc8ce3396f`。対象2試験ファイルと製品所有者2ファイルを、この公開mainの本文と照合した。

対象は `service/test_spot_path_finder.py` の10宣言と `test_spot_graph_navigation_service.py` の14宣言、計24宣言・580行。引数表を展開した基準は26件で、全件成功した。

全24宣言を読み、独立した第二読でも保持22・修復2・統合0・削除0と判断した。修復は既存2宣言へ対照の行を加える変更に限った。保持22宣言の本文は元のまま。製品・共有準備の変更や試験専用入口の削除はない。

対象は24宣言のまま、表展開後は26→28件、580→611行。試験は追加39行・削除8行で、監査文書の追加は別に数える。ファイルの廃止はない。

## 決定性の入力を登録順から切り離す

`find_next_hop` の主担当は `TestDeterminism.test_multiple_id`。

[導入時の説明](https://github.com/Motifman/llm-rpg/commit/114249c1072488e951475432d7d2b0ac85018b4c) は、同じ長さの経路では接続ID昇順で選択することを明記している。元試験は2辺の経路を2つ用意するが、接続を20、30、40、50の順に登録している。この入力ではID順ソートを外しても登録順と一致し、5回繰り返しても誤りが見えない。

修復後は、元の登録順・グラフ・期待する接続20・5回反復をそのまま残し、50、40、30、20の逆順登録を別の行に加えた。同じ経路構造で登録順だけを変えるため、ID順の契約を独立して検査できる。

## 一本道では見えない最短経路の誤りを検査する

`SpotGraphNavigationService.calculate_route` の主担当は `TestSpotGraphNavigationServiceRoute.test_shortest_path`。

元入力は1→2→3だけで、キューから取り出す順を変えても唯一の道を返す。修復後はこの元入力を残し、1→4→5→3という長い迂回路を追加する別の行を設けた。どちらも期待する場所列は `[1, 2, 3]`。

`find_next_hop` 側の `TestMultiHop.test_returns_hop` は、既に2辺と3辺の競合を作っている。そこまで「最短性を検査していない」と一括して扱わず、保持する。2つの探索は戻り値も所有者も別であり、一方の故障を他方の試験が必ず捕えるとは主張しない。

## 保持する契約

- `find_next_hop`: 同一場所のNone、接続IDの戻り値、最初の辺の逆追跡、短い経路、通行不能辺の除外と迂回、孤立先、距離制限と包含境界、同距離選択
- `calculate_route`: 始終点を含む場所列、同一場所、孤立先、未知目的地、閉じた辺の除外
- `can_pass`: 閉鎖の拒否と理由、ALWAYS、所持品とフラグ、作者の失敗文、共通評価核への入力変換、評価不能を通常不成立へ潰さない例外

単純な同一場所や既定の通路による成功も、異なる公開戻り値や条件種別を守るため保持する。

### 共通評価核への委譲

[世界フラグの共通化](https://github.com/Motifman/llm-rpg/commit/7f13d9e75b8d72c1923cdbaa85af4ae6faab723c) と[所持品目の共通化](https://github.com/Motifman/llm-rpg/commit/22d422ff0b3927e0953502db412563e71983e1df) は、同じ意味の判定を共通核へ集め、用途固有の文面や評価順を残す判断だった。

偽物の共通核を使う4宣言は、単に内部呼出を固定するための試験とは扱わない。2宣言は渡す名前・品目・解決済み集合を検査し、残る2宣言は各2行で入力不足と未対応を検査する。後者では偽物が例外を出しているのではなく、実サービスと実 `require_satisfaction` が結果をドメイン例外へ変換する。

共通核の試験だけでは通行側の変換や作者の理由文を保証できず、通常の成功結果だけではローカル判定へ戻す改変を見つけられない。この責任分担を残す。

### 上位の移動と群れ処理

プレイヤーの移動予約・tick進行・到着、モンスターの追跡から1辺の実移動、追跡設定0から無制限への変換は上位試験が担当する。グラフ通行照会と実移動の再評価も別の入口なので残す。

`find_hop_distance` は群れの警戒・援護から呼ばれる。関連試験で半径の包含境界を調べるが、今回の24宣言が整数距離の全契約を直接検査しているとはしない。

## 故障を入れた旧新対照

元試験と候補を別作業木に置き、対象の関数だけを1箇所ずつ変更した。各実行は対象2ファイル全体を通し、狙った行以外に失敗がないことを照合した。

| 故障 | 元26件 | 候補28件 |
| --- | --- | --- |
| `find_next_hop` の接続IDソートを外す | 全件成功して見逃す | 逆順登録の行だけ失敗、接続30を返す |
| `calculate_route` を後入れ先出し（LIFO）探索に変える | 全件成功して見逃す | 迂回ありの行だけ失敗、場所列 `[1, 4, 5, 3]` を返す |
| `find_next_hop` のID順を降順にする | 元の決定性試験が失敗 | 登録順2行とも同じ期待値で失敗 |
| `calculate_route` の場所列を逆順にする | 元の一本道試験が失敗 | 一本道と迂回ありの2行とも同じ期待値で失敗 |

4種8実行。`find_next_hop` のソートは `find_hop_distance` へ波及させず、経路の故障は `calculate_route` に限定した。別の所有者が同じ故障を捕えた結果を、この修復の証明にはしていない。

各回の終了後、製品を元のバイト列へ戻した。両作業木で製品・試験のPython3,158ファイルを照合し、元側は全件一致、候補側は対象試験2ファイル以外が一致した。

## 限界と今後の規則

- プレイヤー移動結合試験の `_DirectScopeFactory` は通知収集を捨てるため、最終配送の証明ではない
- 2つの経路APIの戻り値を統一したり、所要tickを使う経路へ変更したりする設計変更は含めない
- 製品不具合は修正しない。全リポジトリ試験・実LLM・有料API・性能比較も対象外
- 最短経路には長さの異なる競合経路を置く。決定性には期待される選択順と登録順が反対になる入力を置く。元の入力と期待値を残して対照を加え、公開戻り値で判定する
- `tests/domain/world_graph/AGENTS.md` は配置監査の変更と競合するため、今回は編集していない
