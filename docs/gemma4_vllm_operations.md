# Gemma 4 vLLM 常駐運用

v108 の H100 4 枚へ Gemma 4 31B の独立レプリカを1つずつ常駐させる。
端末から直接起動したプロセスに依存せず、夜間実験や Codex App Server から
開始・確認・安全停止できることを目的とする。

モデルやvLLM自体の固定構成は
`/home/minagawa/gemma4-vllm/AI_RUNBOOK.md`を正本とする。この文書は
`llm-rpg`側から常駐プロセスをどう管理するかだけを扱う。

## 構成

| 枠 | GPU | API | systemdサービス |
|---:|---:|---|---|
| 0 | 0 | `http://127.0.0.1:8100/v1` | `gemma4-vllm@0.service` |
| 1 | 1 | `http://127.0.0.1:8101/v1` | `gemma4-vllm@1.service` |
| 2 | 2 | `http://127.0.0.1:8102/v1` | `gemma4-vllm@2.service` |
| 3 | 3 | `http://127.0.0.1:8103/v1` | `gemma4-vllm@3.service` |

各レプリカは`127.0.0.1`だけで待ち受ける。外部へ直接公開しない。
4サービスは`gemma4-vllm.target`でまとめて操作する。

## 初回導入

```bash
make gemma4-vllm-install
```

次を行う。

1. `ops/systemd/user/`の定義へ現在のリポジトリとvLLM環境の絶対パスを埋め込む
2. `~/.config/systemd/user/`へ配置する
3. `systemctl --user daemon-reload`を実行する
4. 1分間隔の死活監視タイマーを有効化する

リポジトリまたは`gemma4-vllm`を別の場所へ移動した場合は、再度installする。

### ログアウト後も維持する

夜間にログインセッションが閉じる環境では、ユーザーsystemdを維持するため
lingerを一度だけ有効にする。

```bash
loginctl enable-linger "$USER"
loginctl show-user "$USER" -p Linger
```

`Linger=yes`を確認する。現在のv108は調査時点で`Linger=no`だったため、
ログアウトを跨ぐ運用ではこの設定が必要になる。Codex App Serverを動かした
ログインセッション自体が朝まで残る場合でも、有効化しておく方が停止条件を
セッション寿命から分離できる。

## 開始

```bash
make gemma4-vllm-start
```

コマンドはsystemdへ開始を依頼しただけでは成功にしない。4レプリカすべてで
次を確認してから終了コード0を返す。

- 対象GPUに既存の計算プロセスがない
- `/health`が成功する
- `/v1/models`に`gemma-4-31b-it`が存在する

モデル読み込みと初回コンパイルに時間がかかるため、準備完了待ちは最大15分。
1台でも準備できなければJSONで失敗理由を出し、終了コード1を返す。
既存のGPU実験が動いている場合は、そのPID、プロセス名、使用量をログへ出して
4サービスを1つも起動せず直ちに拒否する。既存処理を自動終了したり、
その上へvLLMを重ねたりはしない。

## 状態確認

```bash
make gemma4-vllm-status
```

各レプリカについて次をJSONで出す。

- systemdサービスが稼働中か
- HTTPで要求を受けられるか
- 実行中の要求数
- 待機中の要求数
- API接続先

4台すべて正常なら終了コード0、1台でも異常なら終了コード1となるため、
夜間の自動化からそのまま成否判定に使える。

ログは次で確認する。

```bash
journalctl --user -u 'gemma4-vllm@*.service' -f
```

監視による再起動履歴は次で確認する。

```bash
journalctl --user -u gemma4-vllm-monitor.service
```

## 頑健な維持

2段階で異常を扱う。

1. vLLMプロセスが異常終了した場合、各サービスの`Restart=on-failure`で
   15秒後に再起動する
2. プロセスは残っているがHTTP死活確認が3回連続で失敗した場合、
   1分間隔の監視タイマーが該当レプリカだけを再起動する

一時的なコンパイル遅延や短い負荷上昇で再起動しないよう、HTTP失敗1回では
何もしない。監視結果は1回ごとにJSONでsystemdログへ残る。

systemdの起動失敗回数には10分間で5回の上限を設けている。モデルや環境が
恒常的に壊れた状態で無限再起動しないためである。

## 安全停止

```bash
make gemma4-vllm-stop
```

停止前に4レプリカの`/metrics`を読み、次が両方0になるまで待つ。

- `vllm:num_requests_running`
- `vllm:num_requests_waiting`

既定の待ち時間は10分。要求が残ったまま上限を超えた場合、サービスを強制停止
せず、要求数を含むJSONエラーと終了コード1を返す。メトリクスが読めない場合も
「要求0」とは解釈しない。

要求の排出待ち中は死活監視を休止する。計画停止と障害復旧が競合して
レプリカを途中再起動しないためである。停止成功時も排出失敗時も監視タイマーは
最後に戻り、停止済みレプリカは監視対象から除外される。

待ち時間を変える場合:

```bash
make gemma4-vllm-stop GEMMA4_VLLM_DRAIN_TIMEOUT=1800
```

排出完了後、systemdがサービスの全プロセスへ`SIGTERM`を送り、最大3分待つ。
それでも終了しない場合だけ`SIGKILL`へ進む。正常な`systemctl stop`は
`Restart=on-failure`の再起動対象にならない。

## 夜間実験との接続

推論サーバーの管理と実験プロセスの割り当ては別の責務とする。

- 本機能: 4レプリカを開始・維持・停止する
- 後続の実験起動器: 空いている枠を`flock`で確保し、1実験を同じ接続先へ固定する

要求ごとの単純なラウンドロビンは使わない。同じ実験を同じレプリカへ固定し、
プレフィックスキャッシュとKVキャッシュをそのレプリカ内で再利用する。

安全な夜間処理の順序は次の通り。

1. `make gemma4-vllm-start`
2. `make gemma4-vllm-status`
3. 複数の実験をGPU枠へ固定して実行
4. 全実験プロセスの終了を確認
5. `make gemma4-vllm-stop`

停止処理だけでは、新しい実験の受付を禁止できない。後続の実験起動器では
「新規割り当て停止 → 既存実験終了待ち → vLLM要求排出 → サービス停止」の順を
一つの操作として実装する。

## 既知の別課題

`LiteLLMClient`の強制時間上限は、タイムアウト後に
`ThreadPoolExecutor`の終了を待つため、現状では実処理を時間内に中断できない。
これは推論サーバーの常駐管理とは変更目的が異なるため、本機能には含めない。
夜間の完全自走へ進む前に、キャンセル可能な非同期HTTP呼び出しとして別途修正する。
