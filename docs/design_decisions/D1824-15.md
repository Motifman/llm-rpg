## D1824-15. 裏のスレッドで動くハンドラは、準備・仕事・反映の 3 つに分ける

**何を**: イベント基盤 (`eventing`) に、非同期のハンドラの基底 `AsyncEventHandler[E, C, R]` を足す。

| メソッド | 動くスレッド | すること |
|---|---|---|
| `prepare(event) -> C` | 配送器 (`EventDispatcher`) にイベントを渡したスレッド (ゲームではターンを進めるスレッド) | イベントから値を取り出し、要る材料を集めてコマンドを作る |
| `handle(command) -> R` | 裏のスレッド | コマンドを受けて仕事をする (LLM を呼ぶユースケースなど) |
| `apply(result) -> None` | 宛先の結果を反映するスレッド (Being ならそのターンの始め) | 結果を記憶に入れるユースケースなどを呼ぶ |

登録は `EventDispatcher.register_async_after_commit(event_type, handler, channel=, guarantee=, executor=, recipient_key=)`。配送器にイベントを渡すと、`AsyncEventExecutor.submit_handler` が、渡したスレッドで `prepare` を呼び、できたコマンドで `handle` を裏の仕事として受け付ける。

- どの段の失敗も、受付を断ったこと (受付の上限、停止のあと、停止の期限切れ) も、`AsyncFailure` で知らせる。知らせには、元のドメインイベントとハンドラそのものと理由 (`prepare_failed` / `handler_failed` / `application_failed` / `capacity` / `shutdown` / `shutdown_timeout`) を入れる。ゲームの trace (`async_event_delivery_failed`) に、イベントの型とハンドラのクラス名が出る
  - `prepare` の失敗は、配送器 (`EventDispatcher`) の失敗の知らせ先には渡さない。配送器の知らせ先は、ゲームでは `world_tick_unit_failed` に残すが、ハンドラを捨ててイベントの型だけを残すので、同じイベントに複数のハンドラがあると、どれが落ちたか分からない。非同期のハンドラの失敗は、どの段でも `async_event_delivery_failed` の 1 種類で読めるようにする
  - そのため、同期のハンドラと非同期のハンドラで、失敗の残る trace の種類が分かれる。run の報告 (report.md) と fuzz の findings に `async_event_delivery_failed` を数える直しを、ハンドラを配線する前に入れる (今は、どちらも `world_tick_unit_failed` しか数えていない)
- 再送必須 (`DURABLE_RETRY`) との組み合わせは、登録のときに断る (受け付けただけで届いたと誤認しないため。今の `AsyncDelivery` と同じ)
- `apply` が失敗しても、`application_failed` を知らせるだけで、反映を呼んだ側 (ゲームではその Being のターンの始め) へは例外を投げない。同じ宛先の残りの結果も続けて反映する
  - 非同期の登録は、失敗しても続けてよい保証 (`BEST_EFFORT`) しか受けない。配送の保証はほかに `DURABLE_RETRY` (必ず届けたい) があるが、非同期では上のとおり断る
  - 前は投げ直していた。そのため、反映が 1 つ失敗すると、その Being のターンが例外で抜け、同じ宛先の残りの結果も次のターンまで反映されなかった
  - 続く PR で、短期記憶は古い範囲のいきさつを例外で断るようになる。いきさつが遅れて書き直すと、遅れて届いた 1 つ目と書き直した 2 つ目がそろい、2 つ目は古い範囲になる。これは珍しくない流れで、投げ直したままだと、そのたびにターンが止まる
  - 失敗は `async_event_delivery_failed` に残り、run の報告と fuzz にも数える (#1911)。続けても静かな失敗にはならない
  - 反映の失敗で止めたい場面 (保存先が壊れているなど) ができたら、非同期で必ず届けたい保証を決め、そのとき保証で分ける
- 宛先の鍵 (どの宛先が反映を呼んだときに反映するか。Being なら `BeingId` の文字列) は、登録のときに渡す

**なぜ**:

- 裏のスレッドが、保存先や実行環境の変わる状態に触らないようにするため。いきさつを書くハンドラが、本人の名前と性格を引くために Being の保存先を裏のスレッドで走査しかけた (D1824-12 のレビュー)。そのときは、別の同期のハンドラで先に引いて取っておく形 (`note_person`) で避けた。これは、1 つのハンドラの仕事が 2 つの登録に割れ、片方だけが失敗したときに元の原因が見えにくくなる (エピソードを書き起こすハンドラ #1895 のレビュー)
- 3 つに分けると、裏のスレッドが読むのは `prepare` が作ったコマンドだけになる。CLAUDE.md の「コマンド・ユースケース・ドメインイベント・ハンドラ」の、ハンドラはイベントからコマンドを作ってユースケースを呼ぶだけ、という決まりとも合う
- 退けた案:
  - 今の `AsyncDelivery` (裏で呼ぶ関数と、結果を反映する関数を別々に渡す) のまま使う。準備の段が無いので、上の取っておく形が残る
  - 頼みごとを、材料を添えた別の値で包んで配送に渡す。非同期の配送は、失敗を知らせるときに配送したものをドメインイベントとして読むので、失敗が残らなかった (D1824-12)。この基底では、配送に渡すのは元のイベントのままで、コマンドは別に持つ

**まだしないこと**: 今の `AsyncDelivery` と `AsyncEventExecutor.submit` は、今のいきさつを書く処理 (`BeingBackstoryWriting`) が使っているので残す。いきさつを書くハンドラ (`WriteBackstoryHandler`) に置き換える PR で、使う箇所が無くなれば消す。
