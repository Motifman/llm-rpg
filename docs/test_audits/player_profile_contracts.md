## 変更状態と通知を同じ操作で確かめる

名前・役割・種族・属性の単独変更は、同じ入力を状態試験と通知試験で二度実行していた。
状態の断言を先に `test_change_*_emits_event` へ移し、その後で状態だけの宣言を除いた。

- 名前: `OldName` → `NewName`、`profile.name == new_name`
- 役割: `CITIZEN` → `ADVENTURER`、`profile.role == Role.ADVENTURER`
- 種族: `HUMAN` → `GOBLIN`、`profile.race == Race.GOBLIN`
- 属性: `NEUTRAL` → `FIRE`、`profile.element == Element.FIRE`

元の通知件数・通知型・旧値・新値・無関係項目の `None`・対象IDの断言は残す。
通知だけ正しくて状態が保存されない実装でも失敗する必要がある。
同値変更の通知抑制、一括変更の1件通知、保存層の通知収集と確定後配送は別の契約として残す。

## 見逃していた契約を主所有者で補強する

1. 操作主体の既定値
   - 元の補助関数は `HUMAN` を明示していたため、製品の既定値を検査していなかった
   - 元の明示経路を残し、直接構築と `create` の省略経路も `HUMAN`、LLM判定偽を確かめる
2. 部分更新の保持
   - 名前・種族の変更後状態と、省略した役割・属性を確かめる
   - 元の `CITIZEN` / `NEUTRAL` 入力を残し、`MERCHANT` / `WATER` の行で既定値への誤初期化を検出する
3. 操作主体の同値指定
   - `LLM` を再指定したとき、元の状態保持に加えて通知が空であることを確かめる
4. `Message` の同値比較
   - 元の同値・ID差・送信者差・異型の入力と断言を残す
   - 送信者名・宛先・本文・日時それぞれの単独差も検査し、手書き比較からの項目脱落を検出する
5. `Message` のハッシュ
   - 同値のハッシュ一致、集合の重複除去と異値保持を残す
   - 異なる値のハッシュが必ず異なるという制約は外す。合法な衝突でも集合の契約は成立する
6. `Message` の不変性
   - 元の読取操作と全6項目の値保持に加え、各公開項目への外部代入を拒否する
   - 全項目が公開の同値比較・ハッシュに参加するため、書換えは集合の鍵の意味を壊す
   - `AttributeError` を検査し、特定のデータクラス実装や専用例外名には固定しない
7. `PlayerName` の型境界
   - 元の `"not a name"` は内容も違うため、値が同じ生文字列との混同を見逃していた
   - 旧断言を残し、`PlayerName("TestPlayer")` と `"TestPlayer"` が非同値であることを確かめる

## 保持する契約と境界

- `PlayerName` の2文字名 `AB` / `リン` は別入力として残す。「リン」の拒否は
  [Issue #264](https://github.com/Motifman/llm-rpg/issues/264) に由来する実障害で、
  [最低長の修正](https://github.com/Motifman/llm-rpg/commit/9d1d2b5db12dab729cc31d3d02d5cde923e2939d)
  は1文字拒否・上限16を維持している
- 明示引数の保持、単純な照会、表示、同値比較、ハッシュ、不変性を、実装が短いという理由で削除しない
- `Message.create` と直接構築は別の入口であり、1001文字拒否の両試験を残す
- `Message` の3つのID拒否試験は実入力0なので、名前も `zero` に合わせる。負数を試したとは主張しない
- `get_content_length` はASCIIの13文字を検査している。Unicodeの文字数とバイト数を区別する証明とはしない
- `WorldProfileRepositoryAdapter`、クエストの名前解決、プロフィールの保存と再構築は実際の利用境界
- `BeingIdentity` は世界を跨いで残る主体の名前・一人称。文字数制限と空白保持の異なる
  `PlayerName` の代わりにはならず、両者の試験を重複と扱わない
- `Message` と一部のプロフィール照会は本番呼出しを検索で確認できなかったが、公開APIの廃止判断はしない。
  `Message` は [値オブジェクト整理](https://github.com/Motifman/llm-rpg/commit/a1c01bcd009bce48197a51b16d19244d55d2f69f)
  以前から不変として定義されていた。今回の補強を実配送や実保存の証明とは扱わない

- 17種類の製品変異を直列に旧64件と新73件へ適用

    （両生成入口の既定値、役割/属性の誤初期化、同値操作の通知、比較4項目、不変性、名前の型境界）
  - 5種類: 旧・新とも失敗。4つの状態保存欠落と、同値ハッシュの破損を引き続き検出
  - 1種類: 定数ハッシュによる合法な衝突は旧試験だけ失敗し、新試験は成功
- 各変異の後に製品の元バイト列へ復元し、最終の対象・関連試験を再実行した
- 独立の第二読で全宣言と統合先を照合。名前の同内容文字列との比較不足を追加で修復した
- 全リポジトリの試験や実LLM通信は、この局所検証の成功に含めない

## この所有者で守る規則

- 状態試験を通知試験へ統合するときは、同じ元入力・操作・状態断言を先に移す
- 既定値を検査するときは、その引数を製品の入口で本当に省略する。補助関数の既定値を代用品にしない
- 部分更新の保持試験には未指定項目の非既定値も置き、無変更と初期化を区別する
- 型付き値と生値の非同値性は、内容が同じ組で検査する
- 同値ハッシュの保証と、異値のハッシュ衝突を区別する
- 不変性の試験は読取後の値保持だけで済ませず、公開値の外部変更を試す。生成ライブラリの内部構造は検査しない
- 試験名、説明、報告は実際に与えた入力と断言の範囲を越えない
