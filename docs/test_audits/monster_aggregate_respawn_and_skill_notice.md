## なぜ既存の入力だけでは足りないか

### 復活後の群れの役割

元の役割は `False` だけだった。復活時に役割を常に `False` にしても成功する。
出現時の `test_spawn_with_pack_id_sets_pack_and_leader` はリーダーを確認するが、
出現後に値を受け取る経路と、復活時に既存値を保持する経路は異なる。
元の一般個体を残し、同じ出現・死亡・復活操作をリーダーでも通す。

### 通常と成長段階付きのMP回復

元は出現時のMP50、幼体のMP40を一度も使わず死亡していた。
復活が消費後のMPを誤って上限として渡しても、未消費の入力では正しい回復と区別できない。
追加行は公開 `use_mp(20)` を出現後・死亡前に呼び、通常は30、幼体は20まで消費してから復活する。
元の未消費行では `use_mp` を呼ばず、元の操作列を維持する。私有状態への代入は使わない。

値オブジェクト側の `test_with_spawn_reset_full_recovery` は、MP50から新上限60への回復を
既に保持している。ここで補強するのは、その下位処理へ集約が正しい実効上限を渡す接続である。
上限値そのものの検証をむやみに足さず、既存のMP50/40の検証で誤りを観測する。

### 技能通知の引数

元はスロット0・標的なしだけだった。通知が常にその値を返しても成功する。
`MonsterBehaviorCoordinator` は解決した技能スロットと行動標的を集約へ渡す。
既存の `test_records_skill_and_interact_actions` はこの呼出しを模擬モンスターで確認するため、
実集約が通知へ値を転記することは今回の試験が所有する。
元のスロット0・標的なしを残し、スロット2・標的 `WorldObjectId(99)` を追加する。
技能そのものの実行・命中判定をこの通知試験へ混ぜない。

## 見逃しを再現する誤変更

以下を同じ製品へ一時適用し、旧ファイル全108件と候補全112件をそれぞれ実行した。

| 誤変更 | 旧版 | 候補で失敗した追加行 |
| --- | --- | --- |
| 復活後だけ役割を `False` に戻す | 108件成功 | リーダー1行 |
| 復活時だけ、実効MP上限の代わりに死亡時の現在MPを下位初期化へ渡す | 108件成功 | 通常の30≠50、幼体の20≠40の2行 |
| 技能通知スロットを0に固定する | 108件成功 | 非既定スロット・標的付き1行 |
| 技能通知標的を `None` に固定する | 108件成功 | 非既定スロット・標的付き1行 |

MPの誤変更は死亡時刻がある復活経路に限定し、最初の出現を壊すものにはしていない。
全て意図した値の検証で失敗し、準備・後始末は成功した。ほかの行の失敗はない。
これは検査の見逃しを確かめる実験で、現行製品の不具合を示すものではない。
製品と候補試験をバイト単位で完全復元した後、次の最終試験を行った。
